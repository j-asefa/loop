# PR 4: outbound webhooks, one event kind

Depends on PR 3. Split as 4a (subscriptions, outbox, delivery) and 4b (Settings and docs) if the capture requires it.

## Goal

An owner registers a receiver URL and a signing secret in Settings. When a run stops, Loop records one delivery per subscription in an outbox, signs and POSTs it, retries on a bounded schedule with the same delivery identity, and dead-letters visibly. Loop never guesses whether a timed-out delivery arrived: it retries with the same identity and the receiver deduplicates.

## Current state (reuse, do not reinvent)

- Web Push has the outbox pattern: `push_subscriptions`, `push_deliveries(subscription_id, artifact_id, attempts, available_at, delivered_at)` with a pending index, `push_messages`, a lease claim in `deliverNotifications` (`src/server/notifications.ts` around 189) so restarts and multiple workers cannot claim the same row concurrently, `MAX_ATTEMPTS = 5`, and the worker's maintenance pass. A lease prevents concurrent sends; it does not prevent a second delivery after an uncertain send, which is why the delivery identity and receiver deduplication exist here.
- Notification categories (#184): `needsYou`, `completed`, `reminders`, `social` in `push_preferences`. "Needs you" and Done are the two Feed states; Feed pages read `feed_cards`.
- Network policy: `src/server/mcp/network.ts` (`safeUrl`, `publicAddress`, `publicNetworkDispatcher`, "Private network addresses are not allowed") and the public-HTTPS-only rule in `src/server/feed-sources.ts`. Both reject local http; they stay as they are.
- Installation kind: `companionMode` (`src/server/profile.ts`) and `config.authMode` (`single-user` default, `multi-user`) in `src/server/config.ts`.
- Secrets at rest: connection secrets are sealed through `src/server/secrets.ts`; webhook signing secrets use the same sealing, never a digest, because Loop must sign with them.

## Event kind

`run.stopped`, version 1. Produced by the run state transition itself, independent of Feed display filtering, in the same transaction as the state change, so the outbox row commits with the state it describes. Using `RUN_TRANSITIONS` (`src/shared/run-state.ts`), the destination state determines the reason from any permitted source state: `completed` → `finished`; `failed` → `failed`; `cancelled` → `cancelled` (including `queued → cancelled`, which the Feed never flags as Done or Needs you); `interrupted` → `interrupted`; `paused` → `paused` (from `pausing` or `queued`); `awaiting_approval` → `needs_input`. Transitions into `queued`, `running` or `pausing` produce nothing. A run that pauses, resumes and later completes produces two events. Event identity: `event_id` is the committed change-log event id of that state transition, so two projections of the same transition write one event, and a later stop after a resume writes a new one. Payload, all fields declared in a zod schema in `src/shared`:

- `id` (delivery identity, stable across retries), `event_id`, `kind: "run.stopped"`, `version: 1`, `occurred_at`
- `reason: "finished" | "failed" | "cancelled" | "interrupted" | "paused" | "needs_input"`; `needs` present only for `needs_input`, as `{ kind: "approval" | "answer", id }` when a durable approval or decision row exists, otherwise omitted
- `run_id`, `conversation_id`, `agent` (name and id), `project_id`, `team_id` where present
- `title` (conversation title, plain text, bounded), `result_preview` (first 180 plain characters of a text result, as `resultNotification` builds it, or empty), `url` (the conversation's Feed link on the public URL)

No message content beyond the preview, no credentials, no owner id, no source database identity.

Control deliveries (`ping` on activation and on the Settings test action) are not event kinds: they are a separate `control` message type with its own schema (`{ id, type: "ping", sent_at }`), signed and recorded in the same outbox so the receiver sees the same headers, and never enabled or counted as a subscription kind.

## Work

1. **Subscriptions.** Table `webhook_subscriptions(id, owner_id, url, secret_sealed, kinds, state, created_at, activated_at, revoked_at, failed_at, last_delivered_at, last_status)` with `state` in `pending_activation | active | failed | revoked`. Lifecycle, persisted and documented: creation inserts `pending_activation` and its `ping` control delivery under the creation `request_id`, so a lost response or a ping timeout leaves the same subscription and control-delivery identity recoverable and a client retry returns them instead of creating a second subscription; the subscription becomes `active` only when that ping returns 2xx while the subscription is still `pending_activation` and not revoked; no event delivery is sent before activation. The worker claims activation-control deliveries for `pending_activation` subscriptions (the only deliveries eligible in that state) on the same retry schedule as events, with the same control-delivery id each time, so a crash before the first send or a timed-out ping is recovered by the ordinary claim. When activation attempts are exhausted the subscription stays `pending_activation` with the attempts and last error shown in Settings; its Retry action re-arms the same control delivery and never activates the subscription by itself. `failed` is set by the event delivery schedule below and cleared by the Settings retry action; `revoked` is terminal. Queued control deliveries are cancelled before dispatch. In-flight attempts cannot activate the subscription or schedule another retry after revocation; their observed outcome is retained, or marked uncertain when no response establishes it, never labelled not sent. Session-only contracts with request identities as card-token creation has: list, create, update kinds, test, retry, revoke, and a deliveries list (recent delivery history for one subscription). Destination rule, read from server-owned state only, with no configuration variable and no client-supplied override:
   - `companionMode === true`: loopback (`127.0.0.0/8`, `::1`), RFC 1918 and unique-local addresses are accepted over plain http on any port; public addresses require HTTPS; link-local addresses (`169.254.0.0/16`, `fe80::/10`) are refused.
   - `companionMode === false`, whether `authMode` is `single-user` or `multi-user`: HTTPS only, public addresses only, port 443 only.
   - Everywhere: no embedded credentials.
   The rule is applied at creation, test, every attempt and every retry against the address actually connected to: resolve, check, then connect to the checked address with redirects disabled, as a webhook-specific policy beside `network.ts` that does not change `safeUrl` or `publicNetworkDispatcher`. Creation sends a signed `ping` control delivery and refuses to activate until the receiver returns 2xx within 10 seconds, as Manus does. Settings shows the rule that applies to this installation and labels local receivers.
2. **Outbox.** Table `webhook_deliveries(id, subscription_id, event_id, kind, payload, attempts, available_at, leased_until, delivered_at, last_status, last_error)` with the pending index pattern from `push_deliveries`. The producer inserts one row per activated, non-revoked subscription (`active` or `failed`) whose `kinds` include the event, in the same transaction as the state change, so a failed subscription keeps accumulating deliveries for the owner to retry. The worker's maintenance pass claims event deliveries with a lease only for `active` subscriptions (activation-control deliveries follow Work 1's `pending_activation` eligibility and exhaustion rules), re-reads the subscription state immediately before each send and each retry, POSTs, and settles; revocation stops every queued retry, and the Settings retry action makes the accumulated rows eligible again. After a non-2xx, timeout or connection failure the delivery is retried after 30 s, 60 s, 5 min, 15 min and 60 min; after the sixth failed attempt of an event delivery the subscription is marked failed (activation exhaustion keeps `pending_activation`, as Work 1 says), further event deliveries for it are recorded but not sent, and Settings shows it with a retry action that resets attempts. A delivery that times out is retried with the same `id`; the receiver's job is to deduplicate on it, and the docs say so.
3. **Signing.** Headers `X-Loop-Delivery` (delivery id), `X-Loop-Event` (kind, or `control`), `X-Loop-Timestamp` (unix seconds), `X-Loop-Signature` as `v1=<hex HMAC-SHA256 over "<timestamp>.<raw body>">` with the subscription's secret, following the Standard Webhooks shape that OpenAI uses and Cursor approximates. Receivers reject timestamps older than five minutes; document a verification snippet in the Integration API page.
4. **Settings.** Webhooks section on the integration tokens page: URL with the destination rule for this installation shown inline, kinds (only `run.stopped` offered), secret shown once at creation, status (pending activation with attempts and last error, active, failed with last error and attempt count, revoked), recent delivery history, test button, retry button for pending-activation (re-sends the same ping) and for failed. Everything the owner can set or inspect about webhooks is here; nothing is exposed to tokens, no CLI, no configuration file. Management is session-only.
5. **Docs.** Integration API page gains the webhook section: event schema, control messages, headers, retry schedule, deduplication rule, destination rule per installation. `docs/architecture.md` adds one paragraph under "Workspace updates" naming the outbox and that it shares the worker's maintenance pass. `docs/server.md` gains no variable.

## Tests

As `verification.md` for PR 4, with an in-process receiver. In addition: the producer writes exactly one outbox row per subscription per transition even when the transition is projected twice, and a second row for a later stop of the same run; every `reason` value is produced by a fixture transition, including `queued → cancelled`; a run stopping during a subscription's failed period enqueues a row that is sent only after the Settings retry; a creation whose ping times out leaves one `pending_activation` subscription and one control delivery, and the client's retry with the same `request_id` returns them without a duplicate; a crash after persistence and before the first ping send is recovered by the worker claim with the same control id; a timed-out ping followed by a receiver that accepts the same-id retry activates the subscription; Retry on an exhausted pending subscription re-sends the ping and does not activate without a 2xx; a ping in flight when the subscription is revoked does not activate it, even when the receiver records having received it, and the delivery history shows its observed or uncertain outcome rather than claiming it was unsent; no event delivery goes out before activation; revocation with pending deliveries sends nothing further and `needs` is omitted when no approval or decision row exists; a receiver that accepts the ping then refuses leaves the subscription failed after the sixth attempt with the attempts recorded; on `companionMode === false` a URL resolving to a private address at send time is refused and recorded, not retried; on `companionMode === true` a loopback http receiver is accepted at creation and delivered to with the same signing and retry behaviour, and a link-local address is refused; a redirect is not followed; the signature verifies with the documented snippet and fails with a changed body or timestamp; the payload schema rejects any object carrying an owner id or secret-like key; a lease held by a killed worker is reclaimed and the retry carries the same `id`.

## Acceptance

One event kind, delivered at least once with a stable identity, never silently dropped, sent only to destinations the installation's rule allows, signed, and visible in Settings when it fails. The Web Push path is unchanged.
