# PR 1: integration tokens with scopes, reads

Depends on contract-discipline PR 11 (#244, `d1a6677f`, merged 2026-10-28). Verified against `5bcecd0d` (origin/main, 2026-10-28).

## Goal

Card tokens become integration tokens. A token holds a set of scopes; a contract declares which admission values admit a bearer; both admission paths (server middleware and paired host) look the matched route's contract up instead of calling `cardReadRoute`. This PR admits reads only: the `write` and `approvals:decide` scopes exist in the type but no contract declares them and Settings does not offer them until PR 2 lands with request identity.

## Current state

- Table `card_tokens` (migration 098) with `card_token_reads` and `card_token_ids`; secrets stored as SHA-256 digests; creation idempotent on `request_id`; at most 50 active; 120 requests per token and 600 per owner per minute; `last_used_at` approximate.
- `CardGrantSchema = z.enum(["results:read", "cards:read"])` in `src/shared/card-token-schemas.ts`; secret prefix `loop_card_` plus 43 URL-safe characters.
- Server admission: `src/server/index.ts` middleware on `/api` (comment "Card bearer identities never enter the general session-authorized API") admits an `Authorization` header only when `cardReadRoute(method, originalUrl)` matches and no method-override header is present, refuses cross-site origins unless `companionMode`, authenticates with `authenticateCardToken` (server) or the host-supplied `cardAuthorization` symbol (companion, owner must be `OWNER`), sets `res.locals.owner`, `cardScope`, `cardToken`, and dispatches to the `cards` mount. `index.ts:80` treats `cardScope === undefined` as a session request for bookkeeping.
- Host admission: `src/host.ts` also calls `cardReadRoute` (around line 505) before forwarding bearer requests, and dispatches `agentSources`, `mcpSharing`, `mcpSharingUpdate`, `workspaceDevices` and `workspaceRevoke` through a contract table without the Express registrar.
- Cards selection: `src/server/card-routes.ts` registers a registrar middleware on `/v1/cards` that re-checks the grant and enforces `results:read` → Results view only, `cards:read` → Results, Saved and Sent, and denies the Done view to any bearer; `cardDetail(owner, id, cardScope)` takes the scalar grant.
- Contracts: `RouteContract.access` is `"session" | "card:results" | "card:cards" | "peer:enrollment" | "peer:handoff" | "peer:directory" | "device:fleet"` (`src/shared/workspace-api.ts:163`). The three `peer:*` kinds are dedicated peer HTTP and `device:fleet` is local paired-device fleet administration, from fleet PRs #236, #237, #238 and #239. The fleet registries (`fleetAdminApi`, `fleetPeerApi`, `fleetDirectoryApi`, `fleetHandoffApi`, `fleetPendingDirectoryApi` in `src/shared/fleet-*-api.ts`) have their own generators (`scripts/fleet-openapi.mjs`, `scripts/fleet-admin-openapi.mjs`) that emit `route.access` verbatim as `x-loop-access`.
- Generator: `scripts/openapi.mjs` maps `access.startsWith("card:")` to the `CardBearer` scheme (around lines 231 and 395) and requires an `Origin` header on non-transport writes.
- Settings: `src/client/CardTokens.tsx` reached from `SettingsHome.tsx`; routes `cardTokens`, `cardTokenCreate`, `cardTokenRevoke` in the registry.
- `runAction` (`POST /runs/:id/:action`, `core-routes.ts` around 424) accepts cancel, dismiss, pause, resume and retry. Withdraw, reorder and move are separate contracts `runWithdraw`, `runReorder`, `runMove`.

## Work

1. **Scopes and admission values.** `src/shared/token-scopes.ts` exports two zod enums and a catalog:
   - `TokenScope = z.enum(["read", "write", "approvals:decide"])`: the values an owner can select.
   - `TokenAdmission = z.enum([...TokenScope.options, "results:read", "cards:read"])`: what a stored credential may hold and what a contract may list. The two legacy grants keep their exact current meaning and are never selectable.
   - `SCOPE_CATALOG` with one line per selectable scope for Settings and the generated document.
   A token's stored value is a non-empty JSON array of `TokenAdmission`; a migration rewrites each existing scalar grant into a one-element array. Creation accepts `scopes: TokenScope[]` from the Settings page, and still accepts the old singular `scope: CardGrant` from old clients, producing a legacy-grant token (compatibility exception, documented).
2. **Contracts declare admission.** Replace the two `card:*` literals: `access: "session" | PeerAccess | "device:fleet" | { admits: readonly TokenAdmission[] }`, where `PeerAccess` names the three existing `peer:*` literals. A route with `{ admits }` admits a session as before plus any bearer whose stored values intersect `admits`. `kind: "stream"` GET routes may declare `admits` (the registrar validates inputs and the response writer streams bytes unchanged); `kind: "transport"` routes may not, enforced by the type. `peer:*` and `device:fleet` routes may not declare `admits` and refuse every bearer exactly as `"session"` routes do. In this PR declare `{ admits: ["read"] }` on: bootstrap, agent reads, Feed pages, conversation page and message reads, run list, approvals list, native-decisions list, Results and artifact reads including file download, and `{ admits: ["read", "results:read", "cards:read"] }` on the three Cards reads. Everything else stays as it is. List the final table in the ledger's scope catalog. Fleet registries keep string-only `access`; their contract type does not accept the object form, and both fleet generators fail loudly if one reaches them, so `docs/fleet-openapi.json` and `docs/fleet-admin-openapi.json` do not change.
3. **Admission by contract, both paths.** The registrar records, for every mounted route, its contract and mount. The server `/api` bearer middleware resolves the request to a mounted route the same way Express will (method, path pattern, HEAD-to-GET parity), reads the contract, and admits the bearer only if the token's values intersect `admits`. The paired host forwards workspace requests to the app; its own `pairedHostRoutes` table (`host.ts:43`) holds only the five host-local contracts (`agentSources`, `mcpSharing`, `mcpSharingUpdate`, `workspaceDevices`, `workspaceRevoke`), none of which admits a bearer. So the host cannot match bearer requests against that table: it uses the same contract-derived matcher the server uses, built from the mounted workspace registry, to decide before forwarding whether the request resolves to a route whose `admits` intersects the token's values. The matcher preserves each router's matching options (the Cards router is `strict` and `caseSensitive`; others are not). The five host-local routes keep their session-only admission and refuse every bearer. This replaces the host's `cardReadRoute` call. Unmatched routes, `"session"`, `peer:*`, `device:fleet` and transport routes, method-override headers and cross-site origins are refused with the existing 403 text generalized. Rate limits, revocation checks, companion owner checks and `Retry-After` stay as they are. Every admitted bearer request carries `res.locals.bearer = { tokenId, admission: TokenAdmission[] }`; nothing infers a session from an absent grant: `index.ts:80` and `card-routes.ts` test the bearer marker, not `cardScope === undefined`. Delete `cardReadRoute`. Keep the registrar middleware in `card-routes.ts` that enforces selection, keyed on the bearer's admission: `results:read` → Results view only; `cards:read` → Results, Saved and Sent; `read` → the same views as `cards:read`; the Done view stays session-only for every bearer in this PR (record as a decision). `cardDetail` receives the admission array.
4. **Token table.** Rename nothing. Secret prefix for new tokens is `loop_token_`; `loop_card_` secrets remain valid. The read-disclosure bookkeeping (`card_token_reads`, `card_token_ids`) applies to any route that returns card identities; extend `recordCardRead` to Results and artifact reads admitted by `read`, keyed per token as today.
5. **Settings.** `CardTokens.tsx` becomes the integration tokens page: name and the `read` scope in this PR (PR 2 adds `write` and `approvals:decide`, the latter last with its warning and unchecked by default). Existing tokens with a legacy grant show that grant labelled legacy and cannot be edited; the owner creates a new token instead. The creation receipt behaviour (secret shown once, pending receipt retained, reconciliation) does not change. Management stays session-only and in Settings.
6. **Generated document.** Security scheme `IntegrationBearer` replaces `CardBearer`; each `admits` operation lists `x-scopes` and the bearer security requirement. Keep `CardBearer` as an alias for one release and say so in `docs/cards-api.md`.
7. **Docs.** `docs/cards-api.md` becomes the canonical "Integration API" page: tokens, scopes, the admission rule, limits, and the Cards collections as one section. `docs/architecture.md` "Workspace HTTP contracts" replaces "Cards bearer access remains confined to the three Cards reads and their existing grants" with the admission-by-contract rule and links the page. `docs/contracts.md` access bullet gains the `{ admits }` form and the rule that transports, peer and fleet routes never admit bearers.

## Tests

As `verification.md` for PR 1, at both production entrypoints (server `app`, paired host), plus: an `admits` contract on a transport, a `peer:*` route and a `device:fleet` route fails to compile (`@ts-expect-error`); a bearer on a `"session"` route, a `peer:*` route and a `device:fleet` route gets 403 and no handler runs; HEAD parity on every admitted GET; both legacy grants, with the browser's cookies also present, read exactly what they read before through GET and HEAD, proven against the existing Cards tests unchanged, including the Done-view refusal and per-token read bookkeeping; a `read` token is refused on `submit`, `runAction` and the approval decision routes (not admitted until PR 2).

## Acceptance

No separate hard-coded bearer path allowlist remains in either admission path; the only matcher is derived from the mounted contracts. Every token-reachable route is reachable only because its contract says so. Old card tokens pass the existing Cards suite unchanged. No token can write. The ledger's scope catalog is complete.
