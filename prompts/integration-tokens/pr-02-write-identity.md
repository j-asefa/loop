# PR 2: request identity, writes open

Depends on PR 1.

## Goal

Token writes open in this PR, and a write made with a token is never performed twice. Every contract that admits `write` or `approvals:decide` and has a mutating method names its request identity; the type refuses such a contract without one; the server records the identity before dispatching the effect and never re-dispatches on a replay, including after a crash between effect and response.

## Current state

`submit` already requires `idempotencyKey` (8 to 150 characters) and `runs.idempotency_key` is unique per owner. `runAction` has an optional `idempotencyKey`. Approval and native-decision answers carry `commandId` or generation fields in some routes and not others; inventory them. `runWithdraw`, `runReorder` and `runMove` are separate contracts; `runAction` accepts cancel, dismiss, pause, resume and retry.

## Work

1. **Type rule.** `RouteContract` gains `identity?: string` naming a body field. A contract whose `admits` includes `write` or `approvals:decide` and whose method is POST, PUT, PATCH or DELETE must declare `identity`; GET and HEAD routes (the approval and decision lists admitted by `read`) are not affected. `"session"` routes may declare it but need not.
2. **Which writes.** Declare `{ admits: ["write"] }` on `submit`, the reply route, `runWithdraw`, `runReorder`, `runMove`, and `runAction` restricted to the `cancel` and `dismiss` actions for bearers (pause, resume and retry stay session-only: retry re-dispatches a run and the others are interactive controls; record the decision). Declare `{ admits: ["approvals:decide"] }` on the approval decision route and the native-decision answer route. Later and scheduled sends are not admitted in this bundle. Where the session path allows omitting the identity (`runAction`), the registrar requires it when the caller is a bearer and leaves session behaviour unchanged. Where no identity exists today, add an optional body field for session callers and required for bearers, with a compatibility note. No existing browser call changes shape.
3. **Identity record.** Table keyed by owner, token id and identity, storing the operation (contract name), a hash of the validated params and body, state (`pending` | `complete`), the response status, a result locator, and timestamps. The result locator is contract-specific and is recorded atomically with completion: the run id for `submit` and `runAction`, the newly created run's id for `runMove` (its target is the old run but it returns the new one), for `runWithdraw` the original run id together with the `PublicWithdrawnDraft` response persisted at completion (`withdrawQueuedRun`, `queued-runs.ts` around 141–187, cancels the run and returns the draft content without creating any draft row, and the browser merges it into the composer, so there is no durable draft to re-project; the response is owner-scoped and credential-free, so persisting it is safe; `withdrawQueuedRun` is never invoked again and no draft subsystem is introduced), the approval or decision id and its generation for the decision routes. Each contract declares how a replay projects its locator with the route's own response schema; a replay never invokes the effect handler to reconstruct a response. Rule, in order:
   - A new identity is inserted with state `pending` before any effect. When the effect is a local database write, insert, effect and completion (with the locator) commit in the same transaction. When the effect leaves the database (native dispatch, steering), the row is committed `pending` first, the effect runs, then the row is marked `complete` with its locator.
   - A replay with a different operation or hash returns 409 conflict, matching the card-token creation rule.
   - A replay that finds `pending` returns 409 with a problem stating the original request's outcome is uncertain; nothing is re-dispatched, and a pending identity never becomes new work. The owner inspects state through the ordinary reads.
   - Only a `complete` row replays successfully: it returns the recorded status with the current projection of the locator through the route's response schema. If the located result no longer exists (deleted run, withdrawn draft gone), the replay is refused with 409 stating the result is unavailable; the effect is never repeated.
   - Full replay data (hash, status, locator) may be dropped 24 hours after completion, but a compact marker (owner, token, identity, state) is retained for as long as the credential can authenticate, so an old client key is never indistinguishable from a new one. A replay that finds only a marker is refused with 409 (expired identity), never executed; a pending marker stays pending.
   - `submit` keeps its owner-wide `idempotencyKey` semantics: the identity table records the call, and a second token presenting the same key receives the existing run's projection with no second run. Record this reconciliation; the "two tokens, two requests" behaviour is explicitly not provided for `submit`.
4. **Generated document.** Each bearer-admitted write documents its identity field, the replay rule, the uncertain-outcome 409 and the bearer security requirement. `scripts/openapi.mjs` currently marks the `Origin` header required on every non-transport write; change it so the requirement is documented for session and paired-device callers only and is not required under the `IntegrationBearer` security requirement, matching the admission middleware: a bearer call does not require an `Origin` header or session/paired-device CSRF credentials, while the existing explicit rejection of a disallowed supplied `Origin` or cross-site Fetch Metadata at the owning entrypoint (`index.ts` around 135–136, `host.ts` around 513–517) stays exactly as it is. Session and paired-device Origin/CSRF documentation is unchanged.

## Tests

As `verification.md` for PR 2, at the HTTP boundary with a real token. Add: same identity, different body, 409; same key on `submit` from two tokens yields one run; crash after a local effect and before the response (commit the effect, throw before replying) then replay returns the projection without a second effect; crash between `pending` and completion of a non-transactional effect then replay returns the uncertain 409 and dispatches nothing; a `runWithdraw` whose response is lost replays the persisted draft response for the same identity with the run cancelled exactly once; expired identity refused; a `read`-only token is refused on every write with 403 and no identity row written; the Settings page offers `write` and `approvals:decide` and the latter is unchecked by default with its warning.

## Acceptance

No bearer-admitted mutating contract compiles without an identity. Every token write replay in the suite shows at most one effect and never a second dispatch after uncertainty.
