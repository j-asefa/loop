# PR 3: token reads of the event stream

Depends on PR 2.

## Goal

A token with `read` can learn about committed changes without a browser session: first through the existing HTTP event page, then through a dedicated token endpoint with a durable cursor stored with the token. The browser socket does not change.

## Current state (verified at `5bcecd0d`)

- `GET /api/events` (`workspaceApi.events`, `index.ts` around 302) takes an `after` query value and returns a bounded array of `PublicHttpEvent` rows (`app-contract-schemas.ts`): id, owner_id, run_id, type, serialized `payload` text, created_at, optional subject fields. There is no cursor envelope and no per-response byte budget on this page; the caller's cursor is the last `id` it saw.
- `src/server/event-sockets.ts` serves `/api/events/ws` for cookie sessions and rejects any `Authorization` header. Cursor state is connection-local: the reconnecting browser supplies epoch, cursor, clock and projection in the URL; for version 2 a fresh server epoch (random per process) resets it, while version 3 uses the durable epoch from `change_watermark` (`workspace-events.ts:44`, `currentEpoch = v3 ? bounds.epoch : epoch`), so an ordinary server restart does not discard v3 catch-up. Version 3 frames carry projected content, including message content and decision payloads, within the socket's per-event and batch byte limits.
- The change drain (`src/server/changes.ts`) is wakened by local inserts and a 250 ms `data_version` check for foreign commits; it is not a periodic delivery tick, and a token revocation on its own produces no event a stream would see.

## Work

1. **Page.** Declare `{ admits: ["read"] }` on `workspaceApi.events`. Bearer callers receive the same array shape and the same owner-scoped rows. Add a byte budget for bearer responses only: return fewer whole rows, never alter a row. If the first unread row alone exceeds the budget, return that one intact row (documented policy), so the caller always receives a next id and nothing is skipped and no empty success is returned while rows remain. Document that the browser's behaviour is unchanged. Rate limits apply per token as for any route.
2. **Stream.** Add a token endpoint. Choose between Server-Sent Events on `GET /api/events/stream` and a bearer-authenticated WebSocket path separate from `/api/events/ws`; decide, record why, and keep the browser path untouched either way. The endpoint delivers the same v3 frames from the same ordered change drain, so a `read` token sees what a `read` token can already read through the routes; document that the stream carries message content and decision payloads. Cursor semantics distinguish offered from confirmed. The stream tracks the last event id written to the connection (offered) in memory, but the durable resume checkpoint stored with the token advances only when the client confirms receipt: for SSE by the client sending the cursor back (a lightweight `GET /api/events/stream/ack` with the id, or the `Last-Event-ID` header on reconnect), for WebSocket by an acknowledgement frame. A frame written but never confirmed is replayed on the next connect. On connect without parameters the stream resumes from the confirmed checkpoint; a client may pass `after` to resume earlier; the v3 reconciliation rules apply unchanged: a server restart with a valid checkpoint under the same durable epoch resumes; a changed durable epoch, a checkpoint older than the earliest surviving change-log row, a checkpoint beyond the current bounds, or a missing log tail (`workspace-events.ts` around 45–54 and 105–110) each send the same explicit reset signal the browser socket sends, after which the client must reconcile through the routes. Deleted rows are never promised; a reset moves the offered cursor to the tip, and the stored checkpoint advances only when the client confirms under the confirmation rule. One live connection per token; a second connect closes the first, and a late confirmation from the replaced connection cannot advance the replacement's checkpoint (bind confirmations to the connection that offered the frame).
3. **Revocation.** Revoking the token closes its stream within 30 seconds even when idle: the stream re-checks the token on every frame and on a 30-second timer, because the drain has no periodic tick. Document the bound.
4. **Registry.** Describe the endpoint as a channel, as the browser socket is described since contract-discipline PR 10; the generated event-channel companion includes it with the bearer security requirement.
5. **Docs.** The Integration API page documents the page, the stream, offered versus confirmed cursors, and that v3 events carry projected content (message content and decision payloads) so a token that can read the stream reads what a `read` token can read through the routes; where a payload is bounded or omitted, the client reads the route.

## Tests

As `verification.md` for PR 3. Add: a token without `read` (a legacy grant, or after PR 2 a `write`-only token) is refused on both endpoints; a revoked idle stream closes within the bound; two tokens of one owner hold independent cursors; a frame written after which the connection dies before the client confirms is delivered again on bare reconnect; a process restart resumes from the confirmed checkpoint under the unchanged v3 epoch; a replaced connection's late confirmation does not advance the replacement's checkpoint; a durable epoch change resets; a checkpoint whose history has been pruned under the same epoch resets explicitly rather than replaying or silently skipping; a first unread row larger than the bearer budget is returned alone and intact; the stream carries no field the browser socket does not; browser socket bytes are unchanged on the existing fixtures.

## Acceptance

Browser socket bytes unchanged. Token stream and page deliver the same committed events under the documented budgets, with a durable cursor and bounded revocation.
