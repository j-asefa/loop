# Local ACP connection and compatibility

Loop starts one opt-in local Agent Client Protocol v1 process per active conversation. On the desktop hosting Loop, use an absolute executable path and sign in with the agent's own CLI first:

```sh
loop acp --executable /absolute/path/to/codex-acp --billing existing
```

The first executable and argument list are pinned to the `native-acp` connection in a workspace. The browser cannot choose a process path. ACP agents use their own authentication and billing. Loop advertises neither ACP filesystem nor terminal host methods; a terminal reference is marked unavailable. An agent can still run its own local tools, so ACP is not a process sandbox. Only agents advertising HTTP MCP receive the local workspace-tool bridge. Its credential belongs to the native conversation generation and is invalidated on disposal.

A conversation resumes only if its agent advertises `session/load`; a failed load never starts a replacement session. Load history is not assigned to a new Loop turn. Durable prompt intent is recorded before dispatch; an uncertain dispatch is never automatically replayed. ACP permissions expose only advertised one-shot allow/reject options. Cancel and process exit settle pending decisions; late answers expire. Setting writes use revisions at serialized dispatch, wait for agent confirmation, and cannot overlap prompts. Incoming JSONL frames are limited to 8 MiB before SDK parsing; display records have the smaller shared activity limits. See [local workspace architecture](companion/NATIVE-ADAPTERS.md) for host and transport boundaries.

The four-harness integration scope is Pi, Codex, Claude Code and OpenCode across their existing direct transports and optional ACP connections. Published ACP entry points include [Codex ACP](https://github.com/agentclientprotocol/codex-acp) (`codex-acp`), [Claude Agent ACP](https://github.com/agentclientprotocol/claude-agent-acp) (`claude-agent-acp`), and [OpenCode ACP](https://opencode.ai/v2/docs/cli/acp/) (`opencode acp`); their presence does not establish live Loop compatibility. The installed `codex` 0.157.0 and `claude` 2.1.280 CLIs do not themselves expose an ACP flag. Pi's [official RPC mode](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/rpc.md) is separate; available `pi-acp` bridges are independently maintained, so Pi ACP is not certified here. Do not substitute `pi --mode rpc` for an ACP subprocess.

Reproduce the Codex ACP setup on a host with Node/npm and Loop installed:

```sh
npm install -g @agentclientprotocol/codex-acp@1.13.1
codex-acp --version
loop acp --executable "$(command -v codex-acp)" --billing existing
```

The adapter package includes a compatible Codex dependency. It starts as a stdio ACP agent; `codex acp` is not the command. On this host `codex-acp --version` reported 1.13.1, and Loop's real adapter completed `initialize` plus `session/new` without a prompt. It reported `ready`. No credential was read or printed, and no paid model call was made. The current host reports an existing Codex ChatGPT login, but that does not make an authenticated prompt free or authorize model usage. Claude Code reports no login; Pi and OpenCode are absent. No remaining real prompt validation can be completed here within the no-paid-call constraint.

The external live gate needs a test workspace, a supported ACP executable and its own authorized authentication and billing. Start the pinned Codex adapter with the command above; verify the conversation reaches `ready` (`initialize` and `session/new`). Then send an actual prompt and verify its response and activity records. In separate real turns, cancel an in-flight prompt and verify interruption, trigger a permission request and select an advertised one-shot option, and invoke a Loop workspace tool through the HTTP MCP bridge. Finally, restart/resume the same conversation and verify `session/load` preserves its identity and history without replaying a prompt. Record the adapter version, advertised capabilities, results and billing authorization. A prompt alone does not establish permission, HTTP MCP or load support; if the agent does not advertise a capability or the scenario cannot be induced, record it as unverified. Fixture tests below cover Loop's boundary only and cannot close this live gate.

Registration and command-catalog probes perform ACP `initialize` only; they never create or load a session. ACP commands are discovered from `available_commands_update` on a live session. Until then the command catalog is empty and its capability remains undiscovered.
