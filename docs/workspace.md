# Workspace features

Provider connections determine authentication, models and execution. Agents add instructions and settings; conversations retain their runtime binding. Use [harnesses](harnesses.md) for native execution and [server operation](server.md) for managed subscription/API setup.

## Conversations and organization

Messages and result bodies render LaTeX math with `$…$` inline, `$$` on separate lines for display equations, or a fenced `math` block. KaTeX and its local styles load when a message may contain math; the original Markdown stays readable while loading. Wide equations scroll within the message on phones. Ordinary code stays literal, invalid math falls back to readable source, and `\$` escapes a literal dollar sign.

**New agent** opens a simple **New chat** screen. With an account connected, choose **Start chatting** to create an agent with an automatic name and open the message box. The optional **Opening message** sends only when you choose **Start chatting**. **Model & connection** shows the selected model, provider and computer. Expand it to choose a connection card with its account and destination, then a model; larger catalogs can be searched. Effort appears when the model offers adjustable levels. **Customize** reveals the name, instructions, project and Markdown definitions. Both sections start collapsed. Loop55 selects a connected account and its default model when available. If setup is needed, **Connect an account** leads to it.

New chat uses the connection’s saved model catalog immediately. **Refresh models** checks for provider-side changes; a connection without saved models loads its catalog automatically. Discovery failures require an explicit retry or another connection. A disconnected selected account requires reconnection or an explicit choice of another account. Creation checks the account, model and reported effort levels against the server’s current stored catalog. Opening the form never creates an agent or sends a message.

The **+** button opens the composer with your current or last-used agent, or the same simple creation screen when you have no agents. Write a message and send; photos, files and dictation remain alongside the input. **Chat options** reveals model and effort, native commands and scheduled sends. Closing the composer or changing conversations hides those options again.

The phone layout has five tabs: **Feed**, **Projects**, **Pull requests** ([below](#github-pull-requests)), **Search** and **Your profile** (on desktop the same five sit in the sidebar). The gear at the top right opens Settings, a drawer from the right holding every setting: appearance, connections, tools, agents, memory, notifications, search, import and install, with your account at its foot. Projects organize conversations and artifacts; projects open on Threads and offer Agents, Activity and Files. Each project has a search inside the project (its subfolders and threads included) and routes to its recent outcomes, saved decisions and unfinished work. Native project bindings also select an existing execution directory. Files can be attached to messages or published as private artifacts with versions. Public intermediate progress and structured activities are distinct from completed answers. Replies and follow-ups retain their selected-message context.

Teams coordinate manager/worker agents through bounded delegation and messages between their agents (see [Teams](#teams)). Deleting a team preserves its agents and history. Dismissing a Done card removes only that card from Done; the conversation and its other results are unaffected. Imports bring existing chat exports into Loop55; connecting a provider account does not automatically import website history.

Keyword search works without a provider. Semantic search can use a local embedding model/runtime and reports readiness or failure. Optional OpenAI embeddings require an explicitly selected API connection; subscription connections do not authorize embedding API usage. In the All scope, Search also finds agent profiles by partial name, with or without an `@` prefix, as you type; selecting a match opens that profile. Project and agent filters apply to these matches. Search groups content matches by thread, remembers recent searches on the device and has a **Your prompts** scope for your own sent messages.

The default **Workspace** project collects work without a named project, including ordinary folders outside a project. It appears alongside named projects in Projects. Existing work is included when the default project is first opened; its saved task locations stay intact. Each linked workspace has its own default project.

### Feed and reading position

The Feed tab shows the total of Working, Queued, unread Replies and unread Done (9+ above nine). The Feed keeps completed results in Done and lists active conversations by latest activity ([mobile-return.ts](../src/server/mobile-return.ts)). Each card shows the agent, project, run status and the message for that card's run. Checkout totals, branch details and observed test results stay out of Feed cards. The reading sheet shows the conversation’s current [pull requests](#github-pull-requests), including review information. Work started by teammates, delegated tasks and workflow steps also appears in the Feed, moving through Queued, Working, Done or Needs you with its run. A card's model and [computer name](pairing.md#unified-agents-and-feed) or **Docker** badge come from the connection its run used. The badge appears only for a location Loop55 recorded when it registered the connection; Loop55 running in the companion container counts as Docker, and remote runners have no badge. What needs you (approvals, native decisions, messages that could not be sent, and paused, failed or interrupted work) appears above the filters only while something waits: one card with the rest stacked behind it, so acting on it brings up the next, and **Show all** displays only the cards that need you. **Collapse** restores the previous feed; choosing a filter also closes the expanded list. Its filters are **Done** (the default: every completed result, ordered by when it finished, plus threads with nothing open; each result stays there until you swipe it away, including after later runs finish or the conversation is snoozed), **Working** (only what each current run has written so far), **Queued**, **Replies** (published answers to messages sent during a run), and **Threads** (saved card groups and one latest card per conversation, ordered by latest activity, including working and queued threads; snoozed conversations wait until their reminder is due); old `?filter=all`, `?filter=needs` and `?filter=status` links open Done. Double-tapping **Feed** in the tab bar returns to the top of Done from any filter or tab. A card's heading is the prompt of the run it shows (on Done, the prompt its answer replies to; while a run works, the prompt that started that task), with whitespace collapsed and at most 200 characters; imported history and an empty prompt fall back to the thread title. The card shows the agent's output so far, or says no update has arrived yet and, for work Loop55 started, which watched pull request or teammate started it; it never repeats your prompt as an agent preview. Project thread lists follow the [team visibility setting](#teams); agent thread lists retain team history. Result cards with their files and previews stay on agent profiles and project pages. Tap a Done, Working, Queued, Threads or Replies card (or **Read update**) to open a reading sheet with the same agent header, content layout and fixed **Reply** button as saved results. Finished and queued messages load their full text on opening; live output shows the latest preview, with a conversation link when it reaches the preview limit. **Reply** opens the matching conversation and focuses its composer. **Review result** also opens the reading sheet. In **Threads**, cards whose latest content is your prompt open the conversation directly so the message keeps its original author. Requests such as **Approve request**, **Answer question** and **Continue draft** still open the conversation directly at the required action; project and agent thread lists retain direct navigation. Swipe a **Done** card left to remove only that card from Done; **Undo** restores that same card. Dismissal does not affect the conversation, other views, activity counts or future results; an unread dismissed result leaves the Done badge. Failed and interrupted cards in **Needs you** can also be swiped left to acknowledge that failure; this leaves their run state, conversation and Done results intact. Running, queued and waiting cards cannot be swiped away. Long-press for card actions and run controls. A card's menu also has **Save**, which keeps its latest message — and the result card that message produced — in Later → Saved, exactly as saving it inside the thread would. A “while you were away” card summarizes what finished, failed or needs you since the last visit. Done results are unread until you open them, as replies are: an unread result shows **Unread**, and the Done badge counts unread results in the current project, team or agent view, including members of saved groups. Opening a result marks it read across devices; opening a saved group reads all of its members. A saved group shows **Unread** while any member is unread, including members outside the current view or removed from Done, which the badge does not count. Results from before read tracking start read, and threads without a result have no read state. Threads, Working and Queued have no read or unread state. Replies track unread publications separately.

Use **All**, **Unread** or **Read** beneath the Done tab to filter results, and **All agents** to narrow them to one agent. The agent picker searches partial names with or without an `@` prefix, and workspace labels when multiple workspaces are connected. The two filters work together with the current project and team scope, including older pages. Agents from connected workspaces are labelled by environment and keep their source identity. **Clear filters** restores all read states and agents. Opening a result or saved group moves it out of Unread and into Read; a group stays unread while any member is unread. Choose **Mark unread** from a result card’s actions to put it back in Unread and update the Done badge across devices. On a saved group, this marks every member unread. An older pending read from another tab or device cannot undo a newer unread choice; opening the refreshed result or group reads it again. Idle conversations and agent exchanges have no read state and appear only under All. These choices apply to Done; other Feed tabs and Needs you keep their own scope.

On Done, hold a result card and release for **Reply**, **Save**, **Remind me**, **Mark unread**, **Select cards**, **Move to…**, **Combine with another card**, and **Remove from Done**. Hold and move onto another Done result to open grouping options; a desktop mouse can drag directly. The destination is highlighted before release. Choose a name and **Combine into a new thread**, or move the selected cards into an existing thread. **Select cards** supports multiple selections followed by **Move to…**; **Combine with another card** provides a menu alternative to dragging. Loop55 stores these groups directly, without starting an agent run. Each group occupies one Done card and also appears in **Threads**, alongside the original conversation threads. It previews its latest selected result and opens the full original results in chronological order with links to their conversations. In a project, agent or team view, the group appears when it contains a matching result and previews the latest matching member. Its Threads entry remains available when an original conversation has newer work or is beyond the loaded page. Grouping persists across reloads and devices in the same workspace. A thread can contain up to 100 cards from that workspace; future results remain separate until moved into it. **Remove from thread** removes an individual membership; **Ungroup cards** removes the saved group. Dismissing an individual result does not remove it from a saved group, and ungrouping preserves those dismissal choices. An open group reader follows membership changes from other devices and closes if the group is removed. Original messages and conversations are preserved.

Agent exchanges appear automatically as **Agent thread** cards in Done and Threads. Done includes exchanges with at least one dispatched message; Threads also includes exchanges awaiting their first delivery. A card previews the latest mail message and opens the full exchanged messages in chronological order, with earlier history available on demand. New replies update that same card and an open reader. Membership follows the stored mail `threadId` only: sharing a conversation or run never imports its other messages or final output. Two exchanges interrupting the same running task remain separate. Original run results remain individual cards and can be grouped manually. Direct exchanges follow the visibility of their linked conversations in the selected project or team; selecting an agent or team explicitly includes its hidden activity. Delivery labels update when recipient runs or steering receipts change. Attached-file links and links to the exact original incoming messages remain available in the reader. Paused or uncertain mail is displayed without resending it.

If a run stops while waiting for approval, Needs you shows its failure or interruption instead of an obsolete approval action. Requests that were never approved are closed; records of calls with uncertain outcomes are preserved and never automatically replayed. Dismissing the interruption acknowledges it without restarting the task.

A completed result requires a nonempty final assistant answer; prompt-only, commentary-only and empty turns do not become historical result cards. Each run result uses that run’s project for its label and project filtering; an explicit Workspace selection stays in Workspace even if the conversation is assigned to a named project later. Threads without results retain their idle-thread fallback with no answer preview.

**Replies** sits beside Done, Threads, Working and Queued. When you send a message into a running task, Loop55 delivers its durable message ID and tells the agent to answer with `loop55_reply { replyTo, body }`. Each successful publication becomes its own finished reply card, headed by your message, even while the task continues. The reading sheet shows the original message preview and links to it; **Reply** quotes the published answer and steers the same conversation's active task where supported. Older connected environments show an update notice in Replies; supported environments still show their replies. Refreshing recognizes an upgrade. Reading a reply marks it read across devices and reduces the Replies badge. It never removes the card. Swipe left or choose **Archive reply** to remove that reply; **Undo** restores it. Later replies, task completion, snoozing and archiving a Done result do not replace or remove published replies.

Replies require an explicit tool publication: Loop55 validates that `replyTo` belongs to a user message addressed to the same run and conversation and is no longer pending delivery. A native call can arrive while its steering receipt is still being confirmed, or after acknowledgement failed even though the harness received the message. Publishing the reply does not retry that delivery or change its receipt. Repeating a tool call returns the same reply; a new call creates a new reply, including another answer to the same message. Plain transcript output, quoted message IDs and agent mail do not create Replies cards. Existing transcript history is not retrospectively classified, and an agent that does not call the tool still has its output in the conversation. Ordinary task answers and follow-ups queued as new turns remain results in Done. Steering guidance requests publication only when the runtime offers the tool; API workflow turns and snapshot review agents retain their restricted tool catalogs.

The Threads tab uses `/api/feed?filter=all` to page through one current card per conversation, and retains loaded history during refreshes. Saved card groups are read separately from `/api/feed/threads` and sorted into that list using their latest matching result. Agent exchanges use the paginated `/api/feed/agent-threads` list and `/api/feed/agent-threads/:id` reader, scoped to the requesting owner and source with project, agent and team filters. Its browser link is `?filter=threads`. The Feed requests `/api/feed?filter=done&expand=results` for independent result cards. Requests without `expand=results` keep the previous single-card-per-conversation response and two-field cursors for older open tabs. Updated Loop55 sources are required to serve the expanded history. Each refresh reads the newest page and at most one page of already-loaded history per source; untouched cards stay visible, and older changes reconcile across subsequent refreshes. Swiping, Undo and saving update the local cached card immediately.

A thread remembers where you stopped scrolling and reopens there, saying **Resumed where you left off** with a **Latest** button; at the latest output it opens at the latest messages. Opening a specific message (from Saved, Search, a notification, the Feed or Jump to) highlights it and offers **Back to where I was**. That detour is kept apart from the reading position: the position changes only when you go back, reach the latest messages or read on from a thread you opened normally. Unsent drafts are kept per thread on the device. Swiping back returns to the previous page as you left it: the Feed, Later section and Search query and results reappear at the same scroll position while they refresh. These views are kept in memory for the signed-in account only. Pulling down at the top of any page refreshes it.

Replies stay inside the thread. Any message can be replied to, the agent's or your own; your own is quoted as “my earlier message”. A reply to the agent's latest message, from the thread or its Done card, is not quoted while the thread is idle: it answers what the thread already ends with. Earlier messages and highlighted parts are quoted, and so is any reply while work is in progress or queued, since newer messages may arrive first. The composer shows the quote whenever it will be sent, and **Send later** keeps that decision even if the agent posts again before the scheduled time. **Reply to part** (under More) shows the message as plain text: highlight the lines you mean and only those are quoted, as “part of” the message. The server checks that the excerpt is text the message contains, so the attribution stays true. A whole-message quote longer than 6,000 characters keeps its start and end, with the omitted length marked in between. Inside a conversation, holding text keeps the browser's native selection and copy behavior; Loop55 does not open menus on a long press, including on Send. Use the **Message actions** and **Send later** buttons for those menus. Each message's menu leads with Reply, Save and Remind me; **More** holds replying to part of the message, forking from that message into a new conversation (which copies the conversation, not files: nothing is rewound), reusing it as an editable draft, saving it as a snippet (reusable instructions, inserted with `/` in the composer), copying and sharing its link. **Jump to…** lists the thread's prompts, results, approvals, failures and saved messages, and searches the text of every message in the thread. Conversations show one current [pull request section](#github-pull-requests) above their messages. It belongs to the conversation, so later PR updates do not masquerade as historical run results. Checkout, branch and test badges are omitted from final messages. **Review changes** in the conversation menu still opens the latest recorded Git checkout; tool-reported edits, commands and plans remain in **Tool activity**. Token counts appear when the provider reports usage; Loop55 does not estimate cost.

**Continue with another agent**, in the conversation menu, lets you select messages and edit a prompt for the new agent. **Start continuation** creates the new thread and queues that prompt together, so the selected agent replies without another send. If the connection drops, **Retry continuation** recovers the same thread and run, including after reloading the app or a refused retry. Each request is saved separately so another tab cannot erase its recovery state. If the accepted continuation or its run was removed, Loop55 reports it as unavailable and keeps the server receipt to prevent replay. **New continuation** lets you explicitly prepare separate work, even while an earlier request remains uncertain. Unresolved requests stay in **Saved continuation requests** for recovery. Only selected messages are copied; native sessions and local files stay with their original harness. Older connected workspaces require an update before starting a continuation; the app never retries their non-idempotent copy endpoint.

### Your profile, Later and deferred work

**Your profile** shows your name, an optional @handle and bio (**Edit profile**; an empty name falls back to your account's), and counts of the prompts you sent, your active agents and your top-level projects. Its tabs are **Messages** (every prompt you sent, across projects), **Approvals**, **Answers**, **Files** (described below), **Social** (the feed reader below), and Later's three sections: **Saved**, **Reminders** and **Scheduled**. Handles are unique, case-insensitively. Old `?page=later` links open the profile. **Saved** is one list, newest save first, of every result and message you saved, with a search over their text, thread titles and optional short labels (“Chosen approach”). Saving a reply that has a result card saves that result, so the two are always saved together and listed once. As before, a saved result is included in agent memory by default, which now also applies when you save its reply. Saved follows the project and team filters, and every saved item has Reply, which quotes it in its own thread. **Remind me** on a finished Feed card keeps that card’s message, with its task or reply heading. Cards in the same conversation keep separate reminders; later replies and a renamed thread do not replace the selected message. Opening the reminder returns to that message. The conversation menu can still remind you about the whole thread, and a Feed card with no message yet uses that thread reminder. Work in progress keeps its existing thread reminder; reminders on finished cards do not follow later work in the conversation. Result and message reminders elsewhere keep their selected targets. Reminders never send anything to an agent. A reminder returns at a chosen time, when the thread's agent has no active work, or the next time you open a project, and its card says which. The worker surfaces due items and sends a push notification to subscribed devices. A due reminder can be marked **Done** or snoozed again in place. A conversation reminder snoozes the thread view until it is due; its completed results stay in Done. Saving, unsaving, reminders, scheduled and queued messages confirm with a link to the item and an **Undo** while it can still be reversed: unsaving waits for its Undo before it is sent, Undo of a reminder reopens any reminder it replaced, and Undo of a scheduled or queued message cancels it only if it has not started.

**Approvals** lists approval requests you explicitly accepted or denied in Loop55; **Answers** lists native questions you answered. Both show the request, your response, its date and agent, with a link to the conversation when available. Tap an approval card to reopen its original request and full details alongside your recorded choice. They cover the current workspace and keep each owner's history separate. Long request details and responses are shown as bounded, labelled previews. History saves at most 8 KiB of response text per decision; the harness still receives your complete answer. Opening an approval loads its full saved request; installation credentials and native session context stay private. Approval history records your choice; subsequent tool execution results remain in the conversation. Automatic approvals and requests closed without your response are excluded. Secret answers are never saved in this history. New native responses the harness definitively refuses are removed; unconfirmed deliveries are labelled and never resent from the history. Older decisions appear only where Loop55 retained evidence of your response; missing answer text is marked unavailable, with the request date shown instead of an invented response date. Older connected workspaces show an update explanation for unavailable history or original approval details, without requesting unsupported endpoints.

The composer says who and where a message goes (agent, project, thread). Its **Send later** menu distinguishes **Steer current task** (delivered into the live turn of a running API, subscription, Codex, Claude Code or Pi agent; OpenCode and ACP sessions cannot take input mid-turn, so a reply to them queues for the next turn instead and the option is not offered), **Queue after this task**, and **Send later at a time…**, which confirms the recipient, project, thread and exact local time before scheduling up to 30 days ahead. Later → **Scheduled** lists every scheduled message with its recipient and project, where it can be edited or cancelled; a scheduling confirmation links there. The worker submits scheduled messages with their stored idempotency key, so a retry after a crash cannot send twice. If Loop55 refuses a message when it is due (for example, its agent was retired), it is marked **Not sent** with the reason, in Later → Scheduled and in the Feed's **Needs you** stack (counted apart from messages still waiting); nothing was sent, and it waits until you choose **Send now**, edit it and schedule it again, copy it to a draft, or **Dismiss** it. Other errors leave it scheduled and it is tried again. The composer keeps each send's mode and exact time with its key, so retrying after a lost response repeats the original request and the server returns its receipt, even after the scheduled time. The computer must be awake for scheduled or queued work to start. A queued message waits behind the agent's earlier work, and stays held while that work is paused or awaiting approval; if that work fails or is cancelled, it starts next. Before a queued run starts, you can edit its message, move it up or down within that agent's queue, move it to another agent, or move it back to a draft.

**Your profile → Files** lists the signed-in owner’s published agent files in the current workspace, newest publication first, including files whose results are hidden or archived. Search filenames and titles, filter by type, agent or project, preview and download files, or open the originating conversation. Images, self-contained sandboxed HTML, text and browser-supported videos have previews. Files must be explicitly published with `loop55_publish_file`; workspace files and user uploads are not automatically collected here. Published bytes are snapshots stored under `LOOP55_DATA_DIR/objects` with metadata in `loop55.db`, limited to 25 MB per file. Retain both in backups; access requires the hosting workspace to be online.

An agent profile's **Traces** tab lists its public intermediate updates, commands and tool activity. Its search box matches every word, as a prefix, against trace titles and content and the tool results they link to; traces have their own index, so the Feed and workspace Search stay conversation-first. Each run's **Download run** saves its whole public record, including the final answer, as one JSON file (at most 5,000 traces, marked `truncated` beyond that). Exports exceeding 25 MB are refused; use the paginated Traces tab or download individual traces instead.

A fleet run export requires both **Read agents and conversations** and **Read and share authorized files**, because its JSON includes conversation content.

The composer's dictation button appears only where the browser offers speech recognition; that browser feature may send audio to the browser vendor's service.

A new result's push notification is headed by the agent and the thread's title, and its text is the start of the answer as plain text (for a chart, image or pull request card, what kind of result it is). Pending approvals also send a push notification. The notification carries only the agent name and a link to the conversation, never the request's arguments, and approval always happens inside the app so the device lock still applies. Tapping a notification opens its thread at the message it is about: a new result opens at the answer that produced it. If Loop55 is already open, the service worker focuses it and opens the thread in place.

## Personal prompt history

**Your prompts** (Search, or the account button) is a private, newest-first history of prompts sent across the signed-in owner's projects, with an optional text filter. Entries show their run's receiving agent, project, conversation, attachments, a link to the original message, and Reply, which quotes that prompt in its thread. `/?page=personal` links open this view.

History uses canonical messages and rechecks owner, conversation and project access on every page. Archived work remains readable under the existing retention rules; deleting underlying messages/conversations removes them from history. Agent renames show the current name, while missing agent records show “Recipient unavailable.” Account changes reset the view.

New interactive submissions carry a server-controlled personal-origin marker; internal submissions are excluded. Older messages are included only when they have the submission attachment metadata and an agent run, without native projection/import markers or delegation ancestry. Legacy retry submissions cannot be distinguished reliably from original submissions and may appear; imported or unlinked records without reliable provenance are omitted. The view does not aggregate other owners or deployments.

## Teams

**Team presets.** New team offers **Review code changes**, **Ask an LLM council**, **Build a feature** and **Investigate a bug**, as well as a custom team of existing agents. Choose a project and a connected provider/model; expand the role settings to use different connections. Loop55 creates the manager and workers together and records the preset version, instructions and role assignments. Retrying creation with the same request does not create duplicates. Changes to built-in presets do not rewrite existing teams. Each generated agent remains editable from its profile.

**Local code review.** Choose **Review changes** on a project or a review team's directory entry. In a laptop workspace, select uncommitted changes (including non-ignored new files), staged changes, or committed branch changes against a base. The project must be bound to the Git repository root and have an initial commit. Loop55 captures the diff, baseline versions of changed files and repository context twice, rejecting a capture if the snapshots differ. It does not checkout files, change the index, create a PR or run tests/CI. The three reviewers get fresh conversations and the same immutable snapshot. The lead runs after they finish, with their reports and actual completion states, and verifies and consolidates findings. Existing delegation records provide queue dependencies and cancellation of reviewers with the lead.

**Agent-requested review.** An agent that is not on a review team can ask one to review its work, for example when you tell it to get a review before opening a pull request. Its `loop55_request_review` tool lists the review teams it may use and captures the agent's own checkout — its [worktree](harnesses.md) for native harnesses, otherwise the project's repository — with scope `branch` (default, against `main`), `uncommitted` or `staged`. The checkout must share the project's Git repository. The call returns a durable review ID immediately. Use `loop55_review_status` with that ID to read progress and, once finished, the lead’s consolidated report and each reviewer’s state. Omit the ID to recover this agent’s ten most recent requests, including requests from earlier turns or calls that timed out. Status reads never start another review. Optional `wait: true` waits for completion, but may exceed a harness timeout; recover through the status tool. Edits made after capture are not covered. Cancelling the requester cancels the lead and its reviewers. Retrying the same tool call returns the same review rather than starting another; a new call starts a new snapshot review.

Review teams can use any connection, including harness subscriptions. API reviewers receive the snapshot in their history and expose only `loop55_review_read`, which reads captured text from the owner's review, and reject external MCP calls. Native reviewers receive the snapshot in their first turn and get `loop55_review_read` through Loop55's tool bridge, but they keep their harness's own tools and permissions; read-only access is an instruction, not an enforced boundary. Follow-ups in a review conversation keep the same snapshot binding. Feature-building and bug-investigation presets use normal agent permissions and existing delegation rules.

**LLM council.** Based on Karpathy's [llm-council](https://github.com/karpathy/llm-council). The chair delegates the question to three members, then sends each member the other members' answers, anonymized and in shuffled order, to rank. Members never rank their own answer. The chair adds up the rankings with Borda points, checks the key claims itself and writes one answer, followed by the points, the disagreements and its confidence. The role settings open by default so each member can use a different model. The process lives in the agents' instructions and runs through ordinary delegation; Loop55 does not enforce the anonymization or the shuffling.

The snapshot reader lists omissions: hidden files, common credential files, generated/vendor output, submodules, symlinks, binary files and files over 512 KB. These filename filters are not a content secret scanner; selected source text is sent to the chosen providers. Capture is bounded to 100 changed files, 2,000 repository files, 16 MB of text and about 300 KB of diff. Each review agent has a 180-second execution limit (600 seconds on native harnesses). Oversized captures fail explicitly. The report's status panel shows reviewer failures separately from completed reviews and lists omitted files; no tests are claimed. **Check for newer edits** compares the current repository capture with the reviewed snapshot. That check is a point-in-time observation, not a continuous watch. Applying fixes is a separate task with an editing agent.

A team is a manager and up to 8 workers. Each agent keeps its own provider connection, so one team can mix API agents and native Codex, Claude Code, Pi and OpenCode agents. You talk to the manager in the team thread. Open **Teams** from the desktop workspace sidebar or **Projects → Agent teams** on a phone to browse teams, open a team feed, or add an existing connected agent as a worker. The Feed's team filter also opens a selected team's activity.

Turn off **Show results and threads in feed** in a team's directory entry, or select one team in the Feed's team filter to reach the same setting. Its current and future cards are hidden from **Done** and **Threads** in **All teams**, including project thread lists and a project-filtered Feed. Selecting the team or an agent explicitly still shows its results and threads. **Replies**, **Needs you**, **Working**, **Queued**, project result history, and saved results remain available. The preference is saved per team in its owning workspace, applies across devices, and can be turned back on at any time. An agent's work outside that team is unaffected.

**Delegation.** The manager's `loop55_delegate` tool starts focused tasks for workers, which run in parallel; their updates appear in the team's feed. By default the call waits for every result. With `wait: false` the manager keeps working or finishes its turn, and each worker's result arrives later in the delegating conversation as a turn labelled **Result from @worker**, once per final state. A finished result remains deliverable if its worker is later retired or removed from the team. While the manager is working in another team conversation, results wait rather than start a second session. Cancelling the manager's task also cancels its workers' tasks and any of their results still waiting to be read; results from workers that finished but weren't delivered yet are dropped, so a cancelled manager is never restarted.

Agents can also [discover, message and hand work to one another](#agent-messaging) without a shared team. `loop55_delegate` remains available only to the manager of an active team.

## Markdown agent and team definitions

Choose **Customize → From Markdown** when creating an agent, or **From Markdown** when creating a team. In **Teams → Add worker**, choose **Create worker from Markdown** to create and attach a new worker. Agent creation opens the private library on the selected connection's workspace; team and worker creation use the team's workspace. Libraries belong to their owner on that workspace and are not synced between computers. Create an example, import a `.md` file or paste Markdown, then **Save definition**. Saved definitions can be edited, downloaded or deleted there and reused with different names and connections.

Loop55 stores the original Markdown in `LOOP55_DATA_DIR/loop55.db`, under its owner's account. Keep that database in backups. Importing copies the file; Loop55 does not watch the original file or write to a harness's configuration directories. Existing agents retain their own settings when a definition changes or is deleted. Creating from a definition does not start work; the ordinary agent form still offers an optional initial prompt.

Agent files use YAML frontmatter followed by the instructions, like the basic [Claude Code subagent format](https://code.claude.com/docs/en/sub-agents):

```markdown
---
name: code-reviewer
description: Reviews changes for correctness and missing tests.
---

Read the relevant code, identify concrete bugs, and explain each finding
with file references. Do not edit files.
```

`kind: agent` is optional. `name` follows Loop55's handle rules: 3–32 letters, numbers or hyphens, beginning with a letter; names are normalized to lowercase. `description` is optional library text (up to 1,000 characters). The nonempty Markdown body becomes the agent's instructions. Optional `model` names a model from the selected connection's catalog; omitted or `inherit` uses the model chosen in Loop55. Optional `effort` must be reported by that model; otherwise choose the runtime default or a reported level before creation. If a requested model is unavailable, choose another explicitly in the creation form. Importing an agent fills an editable draft; the saved definition stays unchanged.

A team file defines one manager and one to eight workers. Each role has a unique name, instructions, and optional description, model and effort. The Markdown body is optional shared guidance, prepended to every role's instructions:

```markdown
---
kind: team
name: Feature team
description: Implement and independently review a change.
manager:
  name: feature-lead
  instructions: |
    Implement the change. Use loop55_delegate to request an independent
    review, address confirmed findings, and report changes and checks.
members:
  - name: feature-reviewer
    instructions: |
      Review for correctness and missing tests. Return findings with
      file references. Leave edits to the lead.
---

Follow the project's conventions. Distinguish evidence from assumptions.
```

Choose a project and each role's name, connection and model before creating the team. Every role becomes an ordinary Loop55 agent, editable from its profile and usable with any supported connected harness or API provider. Creation is atomic: invalid settings, duplicate handles or a full team leave no partial agents. Retrying the same creation request returns the recorded result. Worker imports obey the existing eight-worker limit and fixed code-review-team roles.

Files are limited to 128 KB and each agent's resulting instructions to 12,000 characters, including shared team guidance. Unknown fields are rejected; Claude-specific `tools`, `disallowedTools`, hooks, permissions, skills and MCP declarations are not translated. Configure tools and permissions in Loop55 and the selected harness. YAML aliases, custom tags and references to other files are not supported. Use one self-contained team file, or import worker files individually into an existing team.

The authenticated API exposes `GET /api/agent-definitions` for summaries and `GET /api/agent-definitions/:id` for a file and its parsed definition. Save with `PUT /api/agent-definitions/:id`, a client-generated UUID, and `{markdown, version}`: use version `0` for a new definition and the returned version for later edits. Delete with `DELETE` and `{version}`. Stale edits and deletes return 409. Creation uses `POST /api/agent-definitions/:id/create` with `{version, selection: {connectionId, model}, idempotencyKey}`; optional `folderId`, `name`, `teamId` (agent files only), and `roles` keyed by the file's original role names select the destination and override names, connections, models or effort. An explicit role model overrides the file's model; otherwise the file's model precedes the default selection. Omit a worker's `folderId` to inherit its team's project, or pass `null` for Workspace. The definition version is checked before creation; a previously recorded retry remains retrievable after the definition changes or is deleted.

## Agent messaging

Ordinary agent runs have `loop55_agents`, `loop55_message`, `loop55_message_status` and `loop55_handoff` through the shared API/native tool layer ([agent-mail.ts](../src/server/agent-mail.ts)). `loop55_agents` searches and paginates the current owner's non-retired agents on this Loop55 server, returning stable IDs, names, runtime and availability. It does not reveal instruction prompts or connection secrets. Another execution machine behind this server is eligible; another server shown in the unified Feed is a separate source and cannot receive this mail. Disconnected recipients can have accepted mail waiting. Retired agents, unsupported connections and snapshot review targets are refused; review runs keep their restricted tool catalog.

`loop55_message` takes a recipient `to` agent ID and a body of up to 12,000 characters. With no `scope`, a recipient on the sender's active team gets the existing team routing; otherwise the message starts a **direct** thread. Explicit `scope: "direct"` also works between teammates. Explicit `scope: "team"` requires active team membership. Replies pass `threadId`, use its stored scope and reject conflicting scope or target arguments. Sending without `threadId` creates a new mail thread. That shared mail ID links the participants across their separate conversation IDs; each message records its sender and recipient conversations and runs. It is distinct from a manually created card group ID: manual grouping does not rewrite agent mail or automatically add future cards. The automatic Agent thread view follows that mail ID as replies arrive. Sending to oneself is invalid.

Recipient status tools hide unread message subjects and previews while still reporting delivery state. Senders can inspect their own mail; the owner's Agent mail view retains its full history.

A direct thread has two fixed participants and default conversation bindings. The sender is bound to the conversation that started it. Optional `conversationId` selects an eligible recipient conversation; otherwise ordinary delivery creates a dedicated conversation using the recipient's own project and connection, without assigning it to a team. Ordinary replies return to those bindings even when either agent works elsewhere. Sending from another conversation does not replace a binding. An unusable destination fails visibly; start a new thread to contact the agent again. Removing team membership or deleting a team does not invalidate an independent direct thread. Team threads keep their membership rules and prefer the recipient's active team conversation, then the remembered thread/delegation conversation or the manager's team thread, otherwise a new team conversation.

For direct messages, `interrupt: true` automatically selects the recipient's most recent running conversation, including when replying with `threadId`. An explicit `conversationId` takes precedence and may select a different destination for an interrupt in an existing thread. If no task is running, normal routing applies. Loop55 records the selected destination when accepting the message; retries and release from held or pending delivery keep it even if another task starts. The first delivery establishes the recipient's default binding, including when an interrupt starts the thread in an existing user or team conversation. Later interrupts do not replace that binding for ordinary replies. Conversation eligibility checks still apply: an unusable stored binding or selected destination fails visibly instead of selecting another task.

Mail queues behind work in its destination. The worker also prevents mail from starting a competing execution when that agent is busy in another conversation, including paused work or work awaiting approval. Ordinary native user conversations can still run concurrently, and mail that has not started does not block them in unrelated conversations. `interrupt: true` steers only a live run in the selected conversation when its actual runtime takes live input: API/subscription, Codex, Claude Code, Pi and Muse Code. OpenCode, Gemini CLI, Grok Build and ACP queue instead. A manager waiting on blocking delegation is never interrupted. Agents cannot wait synchronously for answers inside a mail call: they should finish their turn so the reply can start the next one.

Acceptance is durable, not proof of reading. **Waiting for recipient availability** means accepted but not yet submitted, for example during disconnection or queue pressure; **Queued** means a recipient turn exists. Recovery retries only undispatched mail or steering definitively never read. An uncertain delivery stays **Delivery unconfirmed, not resent**. Cancelling the recipient turn prevents recovery from recreating it. Refused mail and mail from queued, paused, cancelled, failed or interrupted turns remain in owner-visible history but do not grant later model context, memory or attachment access. If a queued turn's provider is removed, or disconnected and replaced on the agent, delivery fails visibly without switching providers. Direct mail creates no delegation relationship. Delegated results retain their manager cancellation rules.

`loop55_handoff` carries a next task, context summary, workspace reference and published files and requests an acknowledgement in the thread. It does not transfer native sessions, stop the sender, grant manager capabilities or give user approval. Messages appear as **Message from @agent** in conversations and the Feed, explicitly granting no additional authority. Up to 8 files may be included, restricted to files the sender published or can read through attachments to its current conversation; recipients read them with `loop55_read_file`. Owning a file alone does not authorize an agent to forward it. Different runtimes need published/attached files, not assumptions about shared paths. Recipient turns use the recipient's own connection and its subscription limits or API billing; there is no provider or billing fallback.

One run can send 8 messages. A thread pauses after 30 messages, or when a pair reaches 20 messages in an hour across direct and team threads in this owner/source. A paused thread can hold 30 further messages. The workspace can also retain up to 100 accepted, undispatched messages; excess sends are refused explicitly. From an agent profile, **Agent mail** shows direct and team threads, participants, previews, delivery state and available destination links. **Messages** still shows assistant output history. The existing **Team messages** entry filters the same controls to a team. **Resume** releases held messages in order and renews the allowance; a temporary obstruction re-pauses before the blocked message and reports how many were released, refused or remain held. Automatic recovery never releases held messages.

## MCP tools

In Settings → Tools & integrations, choose a catalog integration or add a custom server. Paste `mcpServers` JSON for command or hosted configurations; complete any required OAuth or credential setup. Installation succeeds only after discovery. Catalog definitions are maintained in [catalog-data.ts](../src/server/mcp/catalog-data.ts), not fetched as executable instructions at runtime.

Connections are workspace-wide for that owner, including future agents and teams; other users do not inherit them. Agent-requested installation requires approval. Connected calls follow the workspace approval preference, with ownership, schema, discovered-tool and run-state checks at dispatch. A read-only annotation does not itself grant authorization. Native shell, file and other harness tools follow a separate owner-wide preference, **Settings → Permissions → Agent tool calls** ([permission-modes.ts](../src/shared/permission-modes.ts)), sent with each run. **Never ask** starts Claude Code sessions in `bypassPermissions`. For the other harnesses on your computers, Loop55 answers each tool approval with the harness's one-call allow choice (Codex `accept`, OpenCode `once`, ACP `allow_once`). Codex MCP tool confirmations, including team delegation, also use this one-call approval path; their cards show the request and tool arguments, with native protocol details collapsed. Questions, MCP forms requiring input, URL flows and Pi confirmations still wait for you. **Auto-accept file edits** applies only to Claude Code. A change applies from the agent's next turn; a Claude session restarts to change its launch mode, and requests already waiting keep asking. A permission mode chosen for one session in **Session settings** outranks this preference for that session: Loop55 answers for you only when that session's own mode is `bypassPermissions`. Native approval cards also offer **Fewer approval prompts**, linking to this preference and to the harness's **Session settings** (when it supports permission controls). Allowing connected MCP tools does not change native shell/file permissions, and agent tool calls do not change MCP approvals. Disabling a connection blocks subsequent calls but cannot undo an already dispatched effect. Unknown outcomes are not automatically retried.

Hosted connections use validated network destinations. Private runtime origins require explicit operator configuration. Command MCPs run locally in companion mode and through runtime infrastructure in server mode.

**Provider-key runs and tool search:** Agents running on an OpenAI or Anthropic API key receive connected MCP tools as deferred definitions behind the provider's tool search ([providers.ts](../src/server/providers.ts)). Loop55's own tools stay in the model's context. On Anthropic, a deferred tool's definition enters the context only after the model searches for it; the BM25 tool search tool is used on Claude 4.5 and later (including the 4.6 to 4.8 and 5.x families, Fable and Mythos), and older or unrecognized Claude models keep the full catalog loaded. On OpenAI, `tool_search` applies to `gpt-5.4` and later; OpenAI's deferral keeps each function's name and description visible and defers only its parameter schema until search, so the saving there is schema size, not catalog size. Older OpenAI models keep the full catalog loaded. When a turn called a tool, searched for tools or paused, the provider's complete ordered assistant content (thinking or encrypted reasoning, text, search call, search result and tool-use blocks or items, in the order returned) is stored with the run's checkpoint and replayed unchanged on the following rounds, so signed thinking stays intact and a discovered tool stays available for the rest of the run; Loop55 never executes the search blocks, normalizes OpenAI items through the SDK before replay, and bounds the stored content at 256 KB per turn. If Anthropic pauses its server-side loop (`pause_turn`), Loop55 replays that content as the last message and requests again, at most eight times per run; the paused turns are recorded in the checkpoint so the cap survives approvals, recovery and resumes. Each tool's description carries the server and original tool names because the published name is a hash. Forced projection tools are never deferred. Harness sessions receive the full catalog from the tool bridge and apply their own deferral, if any; the 512-tool / 2 MB catalog budget still applies to both paths.

**Sharing between Loop55 sources:** A Docker runner attached to one Loop55 workspace already uses that workspace's MCP catalog. An older, independent Docker Loop55 server owns a separate catalog and credentials. In **Tools & integrations → Installed**, press **Share tools** beside a discovered, loopback-published Docker source to connect the two catalogs. The paired laptop contacts only that verified local Docker source. Docker-owned MCPs remain on Docker and laptop-owned MCPs remain on the laptop; the browser receives neither provider credentials nor relay tokens. Docker requests for laptop tools wait in a durable queue that the laptop polls through Docker's loopback API, so the laptop opens no network listener. The laptop claims each queued call just before running it, so a call Docker has already reported as uncertain (timed out, cancelled or disconnected) is never run. Each side records call identities before external effects, and uncertain outcomes are never replayed; a call that could not connect sends nothing and stays retryable. New catalog entries refresh within about a minute; if Docker's catalog would exceed the tool budget, the previous catalog stays shared; already running harness sessions may need a new turn or reconnection to list new tools. **Stop sharing**, beside the source or on its shared connection, revokes the relay token and disables both proxy connections; if Docker is offline, the laptop keeps the remote revocation pending until it reconnects. Setup routes accept only local requests from the laptop's source adapter, never through the paired-browser proxy. The Docker server needs a Loop55 version with the federation routes. Other remote hosts need their own securely enrolled source adapter.

**Importing harness-installed MCPs:** On a personal Loop55 (companion or single-user), **Installed → Import from installed harnesses** lists server names found in Codex's JSON CLI catalog, Claude's standard `mcpServers` files, OpenCode's global JSON configuration, and Pi's common `mcp.json` adapter file. The browser receives names and transport kinds only. Choosing **Import** copies that server's configuration into the same source's encrypted Loop55 store, then discovers its tools. OAuth accounts and unsupported native transports may still need reconnecting in Loop55. Custom Pi extensions and other harness-specific stores are not inspected. The existing **Paste MCP JSON configuration** form handles configurations these readers do not recognize. Once imported, a server follows the same owner-scoped catalog and can be shared with a connected Docker source. Native provider homes remain owned by their harnesses. A multi-user server never lists or imports its own harness configurations.

Charts save numeric data and provenance as snapshots; refresh is a new tool operation. Mermaid diagrams use the native renderer. Loop55 does not advertise MCP Apps support or fetch interactive app resources. Tools use ordinary text/structured results and Loop55's normal approval flow. If a server still returns a form-required error, it remains a failed tool result; Loop55 does not claim success or replay the operation. Previously saved app artifacts retain their isolated viewer. These displays do not bypass the tool broker.

### GitHub pull requests

With the official GitHub integration connected (`api.githubcopilot.com/mcp`), the **Pull requests** tab lists your open pull requests across GitHub without involving an agent ([github-pulls.ts](../src/server/github-pulls.ts)). The server reads GitHub with that connection's token, which never reaches the browser or an agent. Filters show **Review requested**, **Yours** and **Involving you**, each with its count, plus each pull request's checks and review state. The search box filters by text, narrows the list to a repository when you type `owner/repo`, and opens any pull request when you paste its link. The list shows the 50 most recently updated. Opening a pull request shows its description, checks, the latest 50 submitted reviews, review threads, comments and the changed files with their diffs. The **Commits** tab shows the latest 100 commits with their authors and dates; expanding one reads its message and file diffs for that exact commit, with links to GitHub. Each commit shows up to 300 changed files; omitted or shortened diffs link to GitHub. Longer histories link to the full list. GitHub's HTML comments are hidden and other HTML shows as plain text. **View file** shows a changed file at the commit being viewed (the head commit in Files), including images and other binary files GitHub shows no diff for. Markdown is rendered like GitHub renders it (**Code** shows the source); its HTML is sanitized, relative images and video load from the same commit, and links to other repository files open in the viewer. External images are shown as links and never loaded. Images and video play inline, and other files show as text with line numbers. Files are served only as images, video, plain text or downloads, never as pages. Each person's copy of a file is kept for a day, and files over 50 MB stay on GitHub. Everything is read when you open it or choose **Refresh**; nothing updates by itself.

From a pull request you can act as your GitHub account. Each action is one request you submit, and Loop55 never retries it:

- **Review**: approve, request changes or comment. Loop55 rereads the head first and refuses if commits arrived since you opened the pull request.
- **Comment**: posts to the conversation after checking that its head still matches the commit you opened. New commits require a refresh first.
- **Merge…**: shown with repository write access. It lists the target, head commit, checks, review state and anything GitHub reports as blocking, then merges with the method you choose, pinned to that head commit. If anything was pushed since, GitHub refuses and you refresh first.

GitHub's own branch rules still apply to every merge. With more than one GitHub connection, these actions are refused rather than picking an account. **Ask an agent** starts a message with the pull request's link, after any draft you have, and sends nothing until you do. **Open in Pull requests** on a PR card in a thread opens that pull request here.

Conversations and Feed reading sheets show PR links independently of automatic watches ([conversation-pulls.ts](../src/server/conversation-pulls.ts)). Confirmed creation results retain their links even without a GitHub connection. Explicit GitHub PR URLs in user and assistant messages, including older transcript pages, saved PR cards and ended watches also appear; merely linking a PR never starts automation. Loop55 never guesses a PR from the agent's checkout or branch. Up to 20 distinct references are shown, with an overflow notice. Links remain usable on GitHub when the connection is missing or a refresh fails.

With GitHub connected, the conversation section reads PR titles, draft/open/merged/closed state, review decisions, requested reviewers and the latest submitted review per person. Reviews attached to earlier commits are labelled; GitHub's review decision remains authoritative for required approvals. Up to 20 reviewers and review requests are read, with omitted information labelled. File and line counts come from the PR on GitHub. The section refreshes when opened, about every minute while visible, on returning to the window, and with **Refresh**. Reads may reuse a result less than a minute old; **Refresh** bypasses that cache for that request. Failed automatic reads wait a minute before retrying, and GitHub rate-limit deadlines apply to both automatic and manual refreshes. Each result shows its read time, and failed reads are labelled without presenting an old approval as current. Linked workspaces read through their own owner-scoped GitHub connection and link out to GitHub.

Tool results from `pull_request_read`, `list_pull_requests` and `search_pull_requests` still appear as saved PR cards. These are snapshots of that tool result, with a link to the Pull requests tab for a current read; the conversation's PR section supplies current review information. Other GitHub results keep the plain tool output, and other servers' results never render as PR cards merely because their tool names match.

API-provider agents with GitHub tools receive guidance on Loop55's rules, plus the `owner/repo#number` references parsed from the latest message. Only the parsed references are added, never the surrounding text. Pull request titles, descriptions, comments, diffs and repository files are untrusted content, not instructions or authorization. Native harnesses keep their own context; the broker rules below still apply to their calls.

An agent's GitHub writes (comments, reviews, edits, pushes, merges) follow the workspace MCP approval preference. With tool approvals set to **Allow**, an agent can carry out a merge authorized in your prompt without an extra confirmation; **Ask** shows the target pull request and action for approval. Switching to Allow also releases pending MCP merge requests on active runs. Loop55 refuses a `merge_pull_request` call without a full 40-character `expectedHeadSha` before requesting approval, so nothing is sent. Permission applies only to that head commit: if new commits arrive, GitHub rejects the merge and the agent must review them and re-check your merge conditions before making a new request under the same policy. Code changes use Git in the agent's workspace; see [harnesses](harnesses.md).

Loop55 watches agent-created PRs by default across Codex, Claude Code, Pi, OpenCode and ACP, without a separate watch setting ([pr-watches.ts](../src/server/pr-watches.ts)). With GitHub connected, a successful `create_pull_request` tool call or `gh pr create` command starts a watch in the originating agent's thread. Direct native and server subscription execution share this behavior. Command detection requires a confirmed successful result with command input and output, tied to the owning run and current session generation; unlinked terminal history, failed commands and truncated results do not start watches. Literal shell wrappers and a preceding `cd directory &&` are supported. A PR merely read or linked in a thread does not start a watch. About once a minute the worker reads the pull request with your GitHub connection's token, which stays on the server. When something new arrives, it queues one follow-up in the thread, labelled **GitHub update**, behind the agent's current work. A follow-up never steers a running task. New items include:

- CI failing on the latest commit, once every check run and every check suite with runs has finished.
- CI turning green after a failure. A first green result is only recorded.
- Reviews, review comments and comments posted since the PR was created. A review counts from when it is submitted, not when its draft was started. Comments from the connected GitHub account (the agent's own) are skipped.

Only accounts with a role in the repository (owner, member or collaborator) are quoted, bots included: any GitHub App can comment as a bot, so a bot account alone does not show the repository trusts it. Comments from anyone else are counted in an update but never quoted, and never start a turn on their own. Quoted comment text is marked as untrusted. Updates wait while the agent is still on the previous one and are then sent together. Each follow-up's idempotency key comes from what it reports (the CI result and the items it covers), and delivered items are tracked by id, so a restart cannot send the same update twice. The Feed labels these follow-ups **GitHub update** too. The agent's pushes, comments and merges still follow the approval preference, and the follow-up tells it never to merge on its own.

Watching stops when the pull request is merged or closed, or when you choose **Stop watching**. It pauses after 5 follow-ups in an hour, so an agent cannot loop on its own pushes, and when GitHub rejects the connection. Nothing is lost while paused; **Resume** continues from where it stopped. One thread watches a pull request at a time. CI results come from GitHub check runs; legacy commit statuses are not read.

## Workflows

The editor uses the bounded JSON `loop55.workflow/v1` format implemented in [server/workflows](../src/server/workflows). A workflow defines inputs, agent roles, sequential agent/approval/save steps, outputs and limits. References may use named inputs or earlier steps; forward references and invalid schemas are rejected. Saved versions and runs retain their selected connection/settings snapshots.

Run a saved version with inputs, review required approval steps and inspect linked child conversations/results. Checkpoints prevent duplicate child submission after restart. Cancellation propagates to the active child. Human approval waits do not occupy a worker slot. Workflow step/time limits apply to native execution, but native internal model calls and token use are not exactly enforceable. The format does not execute arbitrary embedded shell/code.

## Social feeds

Social is a reader for public feeds, under **Your profile → Social**. Its catalog is checked in at [news.ts](../src/shared/news.ts): each entry was read with the shared parser before it was listed, so Social fetches only addresses in that list, and only redirects within a feed's own site. [syndication.ts](../src/server/syndication.ts) reads RSS 2.0 and 0.9x, RSS 1.0 (RDF), Atom and JSON Feed into one kind of card, and adds what a few sites carry beyond the formats: Hacker News points, a Reddit post's linked article and subreddit. Reddit itself is not in the catalog — its logged-out RSS answers 429 and `old.reddit.com` redirects feeds to a sign-in page. Run `npm run feeds:check` to read the whole catalog over the network.

**Feed options.** Search, the Unread and per-feed filters, **Mark all read**, **Follow a word**, **Digest** and **Add feeds** sit in one Feed options card above the stories. It starts closed on every visit, showing how many feeds you follow and how many stories are unread (or that a filter is on); closed, the stories follow the compact options row.

**What is shared and what is yours.** A feed's contents are the same for everyone who added it, so stories are stored once in `feed_stories` with that feed's fetch health in `feed_state`. What is yours stays owner-scoped: which feeds you follow, what you have read, what you saved, your watches and your digests. Stories are shown to you, and reach an agent only through the opt-in tool below.

**Your own feeds.** Beyond the catalog you can add any public feed by address, or paste a site's address and pick from the feeds that page advertises; OPML import brings another reader's list in and export takes it out. A typed address has no warrant, so [feed-sources.ts](../src/server/feed-sources.ts) validates it before Loop55 ever requests it — public HTTPS, no credentials, never an address on this network — and the request goes through the same transport as a catalog feed, which resolves DNS through a public-only dispatcher, refuses any host answering on a private address, follows redirects only within the feed's own site, and reports a feed that redirects to a sign-in page as needing an account. Feeds needing a token or cookie are not supported.

**Freshness.** The worker reads each followed feed about every five minutes, so opening Social is served from the store rather than the network and stays current with the tab closed. It sends `If-None-Match`/`If-Modified-Since`, so a feed that has not changed answers 304 and sends nothing. A feed that fails is retried on a widening delay — two minutes doubling to an hour, or longer if it asked — and its last good stories keep showing meanwhile. A request returns the feeds it already has and names the rest in `pending`, so a page is never held up by its slowest feed; pulling the page down refreshes the feeds themselves, down to a thirty-second floor. Reading stops once a feed has the stories Loop55 keeps, so a full-text feed is not downloaded whole. Each feed keeps its newest 120 stories — plus any you saved — and the stories of a feed nobody follows are dropped a month later.

**Reading.** A story is read when you open it, open its discussion, ask an agent about it, or mark it; "mark all read" is a watermark rather than a row per story. The Social chip carries the unread count. A story can be saved to Later beside a conversation, a result and a message, and comes back at a time. Searching reaches the whole store rather than the page, so a story from last week is still findable; words you mute are hidden from the list, counted, and shown again on request. Pictures a feed offers are off until you turn them on, and when they are on Loop55 fetches them itself rather than letting the browser do it: the page's own policy allows no third-party images, and a picture loaded from the publisher would tell that site who is reading. Only the address stored on a story of a feed you follow is fetched, only real raster images are passed through (never SVG, which can carry script), and they are capped at 5 MB.

**Agents and digests.** An agent can read your feeds only through `loop55_feed`, and only once you turn agent access on — off by default, because a tool that lists your feed puts what you follow into a model's context. It reads the store: it fetches nothing, marks nothing read, and never sees a feed you do not follow. A digest is scheduled per agent at a clock time in your own zone: Loop55 collects what arrived, asks the agent to summarize it, and sends it once a day, labelled **Feed digest** rather than as something you typed. Comparing local days means a daylight-saving change keeps the same clock time and a server that was off for a day sends one digest, not five.

**The worker's pass.** One job: read the feeds that are due, then — once those reads have settled — send any due digest and look for watch matches in what the pass brought in. Running the three in order is what makes a digest cover today's stories rather than yesterday's, and it is one tracked job, so a shutdown waits for all of it.

**Following a word.** A watch matches whole words against stories that arrive — so "ai" finds "AI safety" and not "said" — over the feeds you follow, and never causes a fetch. The first match for a story notifies your phone once; a watch is capped at three notifications an hour and an owner at ten, after which the rest are recorded and summarized in one line. Tapping a notification opens Social on that story. The add form previews what a watch would have caught before you create it.

## Browser and offline behavior

The web app can be installed from an HTTPS origin using the browser's home-screen/app installation flow. A Quick Tunnel origin can change; run `loop55 pair` and add the new page to your home screen.

The service worker caches public shell assets, not private API responses or credentials. Offline relaunch shows reconnect UI; messages are not queued on the device while offline (scheduled sends are stored on the server). The **Open on another device** option in a thread shows a QR code and link for continuing on your computer or phone; the link carries no credentials. Share links create a draft for review rather than silently submitting work. See [pairing](pairing.md) for device access and reconnection.
