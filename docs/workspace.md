# Workspace features

Provider connections determine authentication, models and execution. Agents add instructions and settings; conversations retain their runtime binding. Use [harnesses](harnesses.md) for native execution and [server operation](server.md) for API setup.

Teams and agent messaging, MCP tools and social feeds have their own pages: [teams and agents](teams.md), [MCP tools](mcp.md) and [social feeds](social-feeds.md).

## Conversations and organization

Messages and result bodies render LaTeX math with `$…$` inline, `$$` on separate lines for display equations, or a fenced `math` block. KaTeX and its local styles load when a message may contain math; the original Markdown stays readable while loading. Wide equations scroll within the message on phones. Ordinary code stays literal, invalid math falls back to readable source, and `\$` escapes a literal dollar sign.

An agent can answer with a structured display by writing a fenced `spec` block: one JSON line per element, each adding `/root` or `/elements/<key>` in the format of [json-render](https://json-render.dev)'s inline mode. Loop draws `Card`, `Section`, `Text` (Markdown), `Fields` with `Field`, `Table`, `Divider`, `Actions` with `LinkButton` (http and https links only) and a `Chart` placeholder (charts arrive later), with the same reader everywhere an answer is drawn, including Done and Working cards, but not in GitHub pull request text. Buttons that act, images, state, `visible` and `repeat` are not supported: such an element shows a short note and the rest of the display is drawn. A block that cannot be drawn at all, for example one with no root, is shown as its source with a note, and the answer around it is unchanged. Limits ([display-spec.ts](../src/shared/display-spec.ts)): 64 Ki characters per block, 200 elements, 8 levels, tables of 200 rows and 20 columns, 20,000 table cells, 64 Ki characters of `Text` and 128 Ki drawn characters in all across a display, counting each reference to a shared element. Displays are read by Loop's own code, not a json-render package, and a block that draws today keeps drawing the same way ([fixtures](../test/display-spec-fixtures.ts)); an older Loop shows it as code.

**New agent** opens a simple **New chat** screen. With an account connected, choose **Start chatting** to create an agent with an automatic name and open the message box. The optional **Opening message** sends only when you choose **Start chatting**. **Model & connection** shows the selected model, provider and computer. Expand it to choose a connection card with its account and destination, then a model; larger catalogs can be searched. Effort appears when the model offers adjustable levels. **Customize** reveals the name, instructions, project and Markdown definitions. Both sections start collapsed. Loop selects a connected account and its default model when available. If setup is needed, **Connect an account** leads to it.

New chat uses the connection’s saved model catalog immediately. **Refresh models** checks for provider-side changes; a connection without saved models loads its catalog automatically. Discovery failures require an explicit retry or another connection. A disconnected selected account requires reconnection or an explicit choice of another account. Creation checks the account, model and reported effort levels against the server’s current stored catalog. Opening the form never creates an agent or sends a message.

The **+** button opens the composer with your current or last-used agent, or the same simple creation screen when you have no agents. Write a message and send; photos, files and dictation remain alongside the input. **Chat options** reveals model and effort, native commands and scheduled sends. Closing the composer or changing conversations hides those options again.

The phone layout has five tabs: **Feed**, **Projects**, **Pull requests** ([MCP tools](mcp.md#github-pull-requests)), **Search** and **Your profile** (on desktop the same five sit in the sidebar). The gear at the top right opens Settings, a drawer from the right holding every setting: appearance, connections, tools, agents, memory, notifications, search, import and install, with your account at its foot. Projects organize conversations and artifacts; projects open on Threads and offer Agents, Activity and Files. Each project has a search inside the project (its subfolders and threads included) and routes to its recent outcomes, saved decisions and unfinished work. Native project bindings also select an existing execution directory. Files can be attached to messages or published as private artifacts with versions. Public intermediate progress and structured activities are distinct from completed answers. Replies and follow-ups retain their selected-message context.

Teams coordinate manager/worker agents through bounded delegation and messages between their agents (see [Teams](#teams)). Deleting a team preserves its agents and history. Dismissing a Done card removes only that card from Done; the conversation and its other results are unaffected. Imports bring existing chat exports into Loop; connecting a provider account does not automatically import website history.

Keyword search works without a provider. Semantic search can use a local embedding model/runtime and reports readiness or failure. Optional OpenAI embeddings require an explicitly selected API connection; subscription connections do not authorize embedding API usage. Search offers the same categories as Feed: **Done**, **Working**, **Queued**, **Replies** and **Threads**, alongside its content type, project, agent and date filters. Done searches completed work even when its conversation has newer work; Working and Queued search their respective runs, Replies searches published answers that have not been archived, and Threads searches visible, unsnoozed conversations. **All Feed categories** also includes content outside the Feed. Category filters apply to both keyword and semantic results, and returning to Search restores the selection. In the Everything scope with all categories selected, Search also finds agent profiles by partial name, with or without an `@` prefix, as you type; selecting a match opens that profile. Project and agent filters apply to these matches. Search groups content matches by thread, remembers recent searches on the device and has a **Your prompts** scope for your own sent messages.

The default **Workspace** project collects work without a named project, including ordinary folders outside a project. It appears alongside named projects in Projects. Existing work is included when the default project is first opened; its saved task locations stay intact. Each linked workspace has its own default project.

### Feed and reading position

The Feed tab shows the total of Working, Queued, unread Replies and unread Done (9+ above nine). The Feed keeps completed results in Done and lists active conversations by latest activity ([mobile-return.ts](../src/server/mobile-return.ts)). Each card shows the agent, project, run status and the message for that card's run. Checkout totals, branch details and observed test results stay out of Feed cards. The reading sheet shows the conversation’s current [pull requests](mcp.md#github-pull-requests), including review information.
Work started by teammates and delegated tasks also appears in the Feed, moving through Queued, Working, Done or Needs you with its run. A card's model and [computer name](pairing.md#unified-agents-and-feed) or **Docker** badge come from the connection its run used. The badge appears only for a location Loop recorded when it registered the connection; Loop running in the companion container counts as Docker.
What needs you (approvals, native decisions, messages that could not be sent, and paused, failed or interrupted work) appears above the filters only while something waits: one card with the rest stacked behind it, so acting on it brings up the next, and **Show all** displays only the cards that need you. **Collapse** restores the previous feed; choosing a filter also closes the expanded list.
Its filters are **Done** (the default: every completed result, ordered by when it finished, plus threads with nothing open; each result stays there until you swipe it away, including after later runs finish or the conversation is snoozed), **Working** (only what each current run has written so far), **Queued**, **Replies** (published answers to messages sent during a run), and **Threads** (saved card groups and one latest card per conversation, ordered by latest activity, including working and queued threads; snoozed conversations wait until their reminder is due); old `?filter=all`, `?filter=needs` and `?filter=status` links open Done.
Double-tapping **Feed** in the tab bar returns to the top of Done from any filter or tab. A card's heading is the prompt of the run it shows (on Done, the prompt its answer replies to; while a run works, the prompt that started that task), with whitespace collapsed and at most 200 characters; imported history and an empty prompt fall back to the thread title. The card shows the agent's output so far, or says no update has arrived yet and, for work Loop started, which watched pull request or teammate started it; it never repeats your prompt as an agent preview.
Project thread lists follow the [team visibility setting](#teams); agent thread lists retain team history. Result cards with their files and previews stay on agent profiles and project pages. Tap a Done, Working, Queued, Threads or Replies card (or **Read update**) to open a reading sheet with the same agent header, content layout and fixed **Reply** button as saved results. Finished and queued messages load their full text on opening; live output shows the latest preview, with a conversation link when it reaches the preview limit.
**Reply** opens the matching conversation and focuses its composer. **Review result** also opens the reading sheet. In **Threads**, cards whose latest content is your prompt open the conversation directly so the message keeps its original author. Requests such as **Approve request**, **Answer question** and **Continue draft** still open the conversation directly at the required action; project and agent thread lists retain direct navigation. Swipe a **Done** card left to remove only that card from Done; **Undo** restores that same card.
Dismissal does not affect the conversation, other views, activity counts or future results; an unread dismissed result leaves the Done badge. Failed and interrupted cards in **Needs you** can also be swiped left to acknowledge that failure; this leaves their run state, conversation and Done results intact. Running, queued and waiting cards cannot be swiped away. Long-press for card actions and run controls. A card's menu also has **Save**, which keeps its latest message — and the result card that message produced — in Later → Saved, exactly as saving it inside the thread would.
A “while you were away” card summarizes what finished, failed or needs you since the last visit. Done results are unread until you open them, as replies are: an unread result shows **Unread**, and the Done badge counts unread results in the current project, team or agent view, including members of saved groups. Opening a result marks it read across devices; opening a saved group reads all of its members. A saved group shows **Unread** while any member is unread, including members outside the current view or removed from Done, which the badge does not count.
Results from before read tracking start read, and threads without a result have no read state. Threads, Working and Queued have no read or unread state. Replies track unread publications separately.

Use **All**, **Unread** or **Read** beneath the Done tab to filter results, and **All agents** to narrow them to one agent. The agent picker searches partial names with or without an `@` prefix, and workspace labels when multiple workspaces are connected. The two filters work together with the current project and team scope, including older pages. Agents from connected workspaces are labelled by environment and keep their source identity. **Clear filters** restores all read states and agents. Opening a result or saved group moves it out of Unread and into Read; a group stays unread while any member is unread. Choose **Mark unread** from a result card’s actions to put it back in Unread and update the Done badge across devices. On a saved group, this marks every member unread. An older pending read from another tab or device cannot undo a newer unread choice; opening the refreshed result or group reads it again. Idle conversations and agent exchanges have no read state and appear only under All. These choices apply to Done; other Feed tabs and Needs you keep their own scope.

On Done, hold a result card and release for **Reply**, **Save**, **Remind me**, **Mark unread**, **Select cards**, **Move to…**, **Combine with another card**, and **Remove from Done**. Choose **Select cards**, check the results you want, then use **Mark read** or **Mark unread** to update them together. Selecting a saved group updates all its members. Hold and move onto another Done result to open grouping options; a desktop mouse can drag directly. The destination is highlighted before release. Choose a name and **Combine into a new thread**, or move the selected cards into an existing thread. **Select cards** supports multiple selections followed by **Move to…**; **Combine with another card** provides a menu alternative to dragging. Loop stores these groups directly, without starting an agent run. Each group occupies one Done card and also appears in **Threads**, alongside the original conversation threads. It previews its latest selected result and opens the full original results in chronological order with links to their conversations. In a project, agent or team view, the group appears when it contains a matching result and previews the latest matching member. Its Threads entry remains available when an original conversation has newer work or is beyond the loaded page. Grouping persists across reloads and devices in the same workspace. A thread can contain up to 100 cards from that workspace; future results remain separate until moved into it. **Remove from thread** removes an individual membership; **Ungroup cards** removes the saved group. Dismissing an individual result does not remove it from a saved group, and ungrouping preserves those dismissal choices. An open group reader follows membership changes from other devices and closes if the group is removed. Original messages and conversations are preserved.

Agent exchanges appear automatically as **Agent thread** cards in Done and Threads. Done includes exchanges with at least one dispatched message; Threads also includes exchanges awaiting their first delivery. A card previews the latest mail message and opens the full exchanged messages in chronological order, with earlier history available on demand. New replies update that same card and an open reader. Membership follows the stored mail `threadId` only: sharing a conversation or run never imports its other messages or final output. Two exchanges interrupting the same running task remain separate. Original run results remain individual cards and can be grouped manually. Direct exchanges follow the visibility of their linked conversations in the selected project or team; selecting an agent or team explicitly includes its hidden activity. Delivery labels update when recipient runs or steering receipts change. Attached-file links and links to the exact original incoming messages remain available in the reader. Paused or uncertain mail is displayed without resending it.

If a run stops while waiting for approval, Needs you shows its failure or interruption instead of an obsolete approval action. Requests that were never approved are closed; records of calls with uncertain outcomes are preserved and never automatically replayed. Dismissing the interruption acknowledges it without restarting the task.

A completed result requires a nonempty final assistant answer; prompt-only, commentary-only and empty turns do not become historical result cards. Each run result uses that run’s project for its label and project filtering; an explicit Workspace selection stays in Workspace even if the conversation is assigned to a named project later. Threads without results retain their idle-thread fallback with no answer preview.

**Replies** sits beside Done, Threads, Working and Queued. When you send a message into a running task, Loop delivers its durable message ID and tells the agent to answer with `loop_reply { replyTo, body }`. Each successful publication becomes its own finished reply card, headed by your message, even while the task continues. The reading sheet shows the original message preview and links to it; **Reply** quotes the published answer and steers the same conversation's active task where supported. An unavailable source shows a recoverable error in Replies while healthy sources keep their replies visible. Reading a reply marks it read across devices and reduces the Replies badge. It never removes the card. Swipe left or choose **Archive reply** to remove that reply; **Undo** restores it. Later replies, task completion, snoozing and archiving a Done result do not replace or remove published replies.

Replies require an explicit tool publication: Loop validates that `replyTo` belongs to a user message addressed to the same run and conversation and is no longer pending delivery. A native call can arrive while its steering receipt is still being confirmed, or after acknowledgement failed even though the harness received the message. Publishing the reply does not retry that delivery or change its receipt. Repeating a tool call returns the same reply; a new call creates a new reply, including another answer to the same message. Plain transcript output, quoted message IDs and agent mail do not create Replies cards. Existing transcript history is not retrospectively classified, and an agent that does not call the tool still has its output in the conversation. Ordinary task answers and follow-ups queued as new turns remain results in Done. Steering guidance requests publication only when the runtime offers the tool; Restricted API turns and snapshot review agents retain their restricted tool catalogs.

The Threads tab pages through one current card per conversation and keeps loaded history during refreshes; saved card groups sort into it by their latest matching result. Agent exchanges are listed per owner and source with project, agent and team filters (browser link `?filter=threads`). Done reads independent result cards through the typed Cards API ([feed-cards.ts](../src/client/feed-cards.ts)). Threads and agent-exchange refreshes read the newest page and at most one page of already-loaded history per source, so untouched cards stay visible and older changes reconcile over later refreshes ([feed-done-refresh.ts](../src/client/feed-done-refresh.ts)); Done keeps its own paging window in feed-cards.ts. Swiping, Undo and saving update the local cached card immediately.

A thread remembers where you stopped scrolling and reopens there, saying **Resumed where you left off** with a **Latest** button; at the latest output it opens at the latest messages. Opening a specific message (from Saved, Search, a notification, the Feed or Jump to) highlights it and offers **Back to where I was**. That detour is kept apart from the reading position: the position changes only when you go back, reach the latest messages or read on from a thread you opened normally. Unsent drafts are kept per thread on the device. Swiping back returns to the previous page as you left it: the Feed, Later section and Search query and results reappear at the same scroll position while they refresh. These views are kept in memory for the signed-in account only. Pulling down at the top of any page refreshes it.

Replies stay inside the thread. Any message can be replied to, the agent's or your own; your own is quoted as “my earlier message”. A reply to the agent's latest message, from the thread or its Done card, is not quoted while the thread is idle: it answers what the thread already ends with. Earlier messages and highlighted parts are quoted, and so is any reply while work is in progress or queued, since newer messages may arrive first. The composer shows the quote whenever it will be sent, and **Send later** keeps that decision even if the agent posts again before the scheduled time.
**Reply to part** (under More) shows the message as plain text: highlight the lines you mean and only those are quoted, as “part of” the message. The server checks that the excerpt is text the message contains, so the attribution stays true. A whole-message quote longer than 6,000 characters keeps its start and end, with the omitted length marked in between. Inside a conversation, holding text keeps the browser's native selection and copy behavior; Loop does not open menus on a long press, including on Send. Use the **Message actions** and **Send later** buttons for those menus.
Each message's menu leads with Reply, Save and Remind me; **More** holds replying to part of the message, forking from that message into a new conversation (which copies the conversation, not files: nothing is rewound), reusing it as an editable draft, saving it as a snippet (reusable instructions, inserted with `/` in the composer), copying and sharing its link. **Jump to…** lists the thread's prompts, results, approvals, failures and saved messages, and searches the text of every message in the thread.
Conversations show one current [pull request section](mcp.md#github-pull-requests) above their messages. It belongs to the conversation, so later PR updates do not masquerade as historical run results. Checkout, branch and test badges are omitted from final messages. **Review changes** in the conversation menu still opens the latest recorded Git checkout; tool-reported edits, commands and plans remain in **Tool activity**. Token counts appear when the provider reports usage; Loop does not estimate cost.

**Continue with another agent**, in the conversation menu, lets you select messages and edit a prompt for the new agent. **Start continuation** creates the new thread and queues that prompt together, so the selected agent replies without another send. If the connection drops, **Retry continuation** recovers the same thread and run, including after reloading the app or a refused retry. Each request is saved separately so another tab cannot erase its recovery state. If the accepted continuation or its run was removed, Loop reports it as unavailable and keeps the server receipt to prevent replay. **New continuation** lets you explicitly prepare separate work, even while an earlier request remains uncertain. Unresolved requests stay in **Saved continuation requests** for recovery. Only selected messages are copied; native sessions and local files stay with their original harness. Older connected workspaces require an update before starting a continuation; the app never retries their non-idempotent copy endpoint.

### Your profile, Later and deferred work

**Your profile** shows your name, an optional @handle and bio (**Edit profile**; an empty name falls back to your account's), and counts of the prompts you sent, your active agents and your top-level projects. Its tabs are **Messages** (every prompt you sent, across projects), **Approvals**, **Answers**, **Files** (described below), **Social** (the [feed reader](social-feeds.md)), and Later's three sections: **Saved**, **Reminders** and **Scheduled**. Handles are unique, case-insensitively.
**Saved** is one list, newest save first, of every result and message you saved, with a search over their text, thread titles and optional short labels (“Chosen approach”). Saving a reply that has a result card saves that result, so the two are always saved together and listed once. Results that answer messages you typed yourself are included in agent memory unless you exclude them; results of agent mail, watched pull requests, digests, shared links or text, and reviews are included only when you pin or include them. Saved follows the project and team filters, and every saved item has Reply, which quotes it in its own thread.
**Remind me** on a finished Feed card keeps that card’s message, with its task or reply heading. Cards in the same conversation keep separate reminders; later replies and a renamed thread do not replace the selected message. Opening the reminder returns to that message. The conversation menu can still remind you about the whole thread, and a Feed card with no message yet uses that thread reminder. Work in progress keeps its existing thread reminder; reminders on finished cards do not follow later work in the conversation. Result and message reminders elsewhere keep their selected targets.
Reminders never send anything to an agent. A reminder returns at a chosen time, when the thread's agent has no active work, or the next time you open a project, and its card says which. The worker surfaces due items and sends a push notification to subscribed devices. A due reminder can be marked **Done** or snoozed again in place. A conversation reminder snoozes the thread view until it is due; its completed results stay in Done.
Saving, unsaving, reminders, scheduled and queued messages confirm with a link to the item and an **Undo** while it can still be reversed: unsaving waits for its Undo before it is sent, Undo of a reminder reopens any reminder it replaced, and Undo of a scheduled or queued message cancels it only if it has not started.

**Approvals** lists approval requests you explicitly accepted or denied in Loop; **Answers** lists native questions you answered. Both show the request, your response, its date and agent, with a link to the conversation when available. Tap an approval card to reopen its original request and full details alongside your recorded choice. They cover the current workspace and keep each owner's history separate. Long request details and responses are shown as bounded, labelled previews. History saves at most 8 KiB of response text per decision; the harness still receives your complete answer. Opening an approval loads its full saved request; installation credentials and native session context stay private. Approval history records your choice; subsequent tool execution results remain in the conversation. Automatic approvals and requests closed without your response are excluded. Secret answers are never saved in this history. New native responses the harness definitively refuses are removed; unconfirmed deliveries are labelled and never resent from the history. Older decisions appear only where Loop retained evidence of your response; missing answer text is marked unavailable, with the request date shown instead of an invented response date. Older connected workspaces show an update explanation for unavailable history or original approval details, without requesting unsupported endpoints.

The composer says who and where a message goes (agent, project, thread). Its **Send later** menu distinguishes **Steer current task** (delivered into the live turn of a running API, subscription, Codex, Claude Code or Pi agent; OpenCode and ACP sessions cannot take input mid-turn, so a reply to them queues for the next turn instead and the option is not offered), **Queue after this task**, and **Send later at a time…**, which confirms the recipient, project, thread and exact local time before scheduling up to 30 days ahead. Later → **Scheduled** lists every scheduled message with its recipient and project, where it can be edited or cancelled; a scheduling confirmation links there. The worker submits scheduled messages with their stored idempotency key, so a retry after a crash cannot send twice. If Loop refuses a message when it is due (for example, its agent was retired), it is marked **Not sent** with the reason, in Later → Scheduled and in the Feed's **Needs you** stack (counted apart from messages still waiting); nothing was sent, and it waits until you choose **Send now**, edit it and schedule it again, copy it to a draft, or **Dismiss** it. Other errors leave it scheduled and it is tried again. The composer keeps each send's mode and exact time with its key, so retrying after a lost response repeats the original request and the server returns its receipt, even after the scheduled time. The computer must be awake for scheduled or queued work to start. A queued message waits behind the agent's earlier work, and stays held while that work is paused or awaiting approval; if that work fails or is cancelled, it starts next. Before a queued run starts, you can edit its message, move it up or down within that agent's queue, move it to another agent, or move it back to a draft.

**Your profile → Files** lists the signed-in owner’s published agent files in the current workspace, newest publication first, including files whose results are hidden or archived. Search filenames and titles, filter by type, agent or project, preview and download files, or open the originating conversation. Images, self-contained sandboxed HTML, text and browser-supported videos have previews. Files must be explicitly published with `loop_publish_file`; workspace files and user uploads are not automatically collected here. Published bytes are snapshots stored under `LOOP_DATA_DIR/objects` with metadata in `loop.db`, limited to 25 MB per file. Retain both in backups; access requires the hosting workspace to be online.

An agent profile's **Traces** tab lists its public intermediate updates, commands and tool activity. Its search box matches every word, as a prefix, against trace titles and content and the tool results they link to; traces have their own index, so the Feed and workspace Search stay conversation-first. Each run's **Download run** saves its whole public record, including the final answer, as one JSON file (at most 5,000 traces, marked `truncated` beyond that). Exports exceeding 25 MB are refused; use the paginated Traces tab or download individual traces instead.

A fleet run export requires both **Read agents and conversations** and **Read and share authorized files**, because its JSON includes conversation content.

The composer's dictation button appears only where the browser offers speech recognition; that browser feature may send audio to the browser vendor's service.

A new result's push notification is headed by the agent and the thread's title, and its text is the start of the answer as plain text (for a chart, image or pull request card, what kind of result it is). Pending approvals also send a push notification. The notification carries only the agent name and a link to the conversation, never the request's arguments, and approval always happens inside the app so the device lock still applies. Tapping a notification opens its thread at the message it is about: a new result opens at the answer that produced it. If Loop is already open, the service worker focuses it and opens the thread in place.

## Personal prompt history

**Your prompts** (Search, or the account button) is a private, newest-first history of prompts sent across the signed-in owner's projects, with an optional text filter. Entries show their run's receiving agent, project, conversation, attachments, a link to the original message, and Reply, which quotes that prompt in its thread.

History uses canonical messages and rechecks owner, conversation and project access on every page. Archived work remains readable under the existing retention rules; deleting underlying messages/conversations removes them from history. Agent renames show the current name, while missing agent records show “Recipient unavailable.” Account changes reset the view.

Interactive submissions carry a server-controlled personal-origin marker; only marked user messages linked to their owning run and conversation appear. Internal, imported and unattributed messages are excluded. The view does not aggregate other owners or deployments.

## Notifications

Enable **Settings → Notifications → Enable notifications** on each device.
On iPhone, first add Loop to the Home Screen and open it there. The system permission
request happens only after tapping Enable. This follows [WebKit's Home Screen Web
Push requirements](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).
The app must be served over HTTPS (localhost is supported for development).

Choose **Needs you**, **Completed work**, **Reminders** and **Social watches**
independently on each device. Newly enabled devices start with only **Needs you**
on: approvals, native questions, paused, failed or interrupted work, and scheduled
messages that could not be sent. To receive only action alerts, leave the other
three choices off. Existing subscriptions keep all categories enabled until you
change them. Turning a category off discards its pending alerts; turning it back
on does not replay history. Feed cards remain available regardless of these choices.

With **Completed work** enabled, the worker sends encrypted Web Push when a new completed agent result is published,
including while the app is closed. Notifications include the agent name and result
title; tapping one opens that result. Earlier history, tool calls, imports and
uploaded files do not trigger result alerts. Subscriptions and durable delivery
receipts live in the workspace database; private VAPID and subscription keys use
Loop's existing encryption key. Preserve that key and the data volume on restart.
No third-party notification account or additional deployment secret is required.
`LOOP_PUSH_CONTACT` can optionally set the VAPID contact URL or `mailto:` address.

Delivery has a lease, bounded retries and duplicate-replacing notification tags,
and drops expired subscriptions ([notifications.ts](../src/server/notifications.ts)). Turning
notifications off removes this device's server subscription and browser subscription.

## Browser and offline behavior

The web app can be installed from an HTTPS origin using the browser's home-screen/app installation flow. A Quick Tunnel origin can change; run `loop pair` and add the new page to your home screen.

The service worker caches public shell assets, not private API responses or credentials. Offline relaunch shows reconnect UI; messages are not queued on the device while offline (scheduled sends are stored on the server). The **Open on another device** option in a thread shows a QR code and link for continuing on your computer or phone; the link carries no credentials. Share links create a draft for review rather than silently submitting work. See [pairing](pairing.md) for device access and reconnection.
