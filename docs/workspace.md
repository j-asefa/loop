# Workspace features

Provider connections determine authentication, models and execution. Agents add instructions and settings; conversations retain their runtime binding. Use [harnesses](harnesses.md) for direct execution and [server operation](server.md) for managed subscription/API setup.

## Conversations and organization

The phone layout has four tabs: **Feed**, **Projects**, **Search** and **You**, your profile (on desktop the same four sit in the sidebar). The gear at the top right opens Settings, a drawer from the right holding every setting: appearance, connections, tools, agents, memory, notifications, native conversations, search, import and install, with your account at its foot. Projects organize conversations and artifacts; a project opens on its Threads, with a search inside the project (its subfolders and threads included) and routes to its recent outcomes, saved decisions and unfinished work. Native project bindings also select an existing execution directory. Files can be attached to messages or published as private artifacts with versions. Public intermediate progress and structured activities are distinct from completed answers. Replies and follow-ups retain their selected-message context.

Teams coordinate manager/worker agents through bounded delegation. Deleting a team preserves its agents and history. Archiving affects feed visibility rather than deleting the underlying work. Imports bring existing chat exports into Loop; connecting a provider account does not automatically import website history.

Keyword search works without a provider. Semantic search can use a local embedding model/runtime and reports readiness or failure. Optional OpenAI embeddings require an explicitly selected API connection; subscription connections do not authorize embedding API usage. Search groups matches by thread, remembers recent searches on the device and has a **Your prompts** scope for your own sent messages.

### Feed and reading position

The Feed tab shows how many agents are working right now (9+ above nine). The Feed lists conversations by latest activity ([mobile-return.ts](../src/server/mobile-return.ts)). Each card shows the agent, project, run status and the latest message, which is the result when a run has finished. Its filters are **Done** (the default: every thread's latest finished result, ordered by when it finished, plus threads with nothing open; a result stays there when a follow-up is queued, working or needs you), **Needs you** (approvals, paused, failed or interrupted work), **Working** (only what each current run has written so far) and **Queued**; old `?filter=all` links open Done. Project and agent thread lists still show every thread. Result cards with their files and previews stay on agent profiles and project pages. When a thread waits for something specific, its card offers that one action (**Approve request**, **Answer question**, **Continue draft** for an unsent draft, or **Review result**) and opens the thread at that exact message; otherwise it offers Reply. Swipe a card left to set a reminder; long-press for run controls. A “while you were away” card summarizes what finished, failed or needs you since the last visit. Loop has no read or unread state.

A thread remembers where you stopped scrolling and reopens there, saying **Resumed where you left off** with a **Latest** button; at the latest output it opens at the latest messages. Opening a specific message (from Saved, Search, a notification, the Feed or Jump to) highlights it and offers **Back to where I was**. That detour is kept apart from the reading position: the position changes only when you go back, reach the latest messages or read on from a thread you opened normally. Unsent drafts are kept per thread on the device. Swiping back returns to the previous page as you left it: the Feed, Later section and Search query and results reappear at the same scroll position while they refresh. These views are kept in memory for the signed-in account only. Pulling down at the top of any page refreshes it.

Replies stay inside the thread. Any message can be replied to, the agent's or your own; your own is quoted as “my earlier message”. **Reply to part** (under More) shows the message as plain text: highlight the lines you mean and only those are quoted, as “part of” the message. The server checks that the excerpt is text the message contains, so the attribution stays true. A whole-message quote longer than 6,000 characters keeps its start and end, with the omitted length marked in between. Each message's menu leads with Reply, Save and Remind me; **More** holds replying to part of the message, forking from that message into a new conversation (which copies the conversation, not files: nothing is rewound), reusing it as an editable draft, saving it as a snippet (reusable instructions, inserted with `/` in the composer), copying and sharing its link. **Jump to…** lists the thread's prompts, results, approvals, failures and saved messages, and searches the text of every message in the thread. File activity from a run collapses into one summary that opens a **Reported file activity** review. It lists what the agent's tools reported, edit by edit, rather than a diff of the repository, grouped as applied, proposed, failed, or with no reported outcome; only applied edits are counted, and review prompts cover only files with applied edits. It shows what Loop knows of the run (agent, project, start time, commands the agent reported running); repository, branch and pull request are not reported by harnesses today. Its follow-up buttons only prefill an editable prompt that asks the agent to check the full diff first: Loop never applies, commits or reverts files itself, and harness session commands such as rewind stay in the native terminal. Token counts appear when the provider reports usage; Loop does not estimate cost.

### Your profile, Later and deferred work

**You** shows your profile: your name, an optional @handle and bio (**Edit profile**; an empty name falls back to your account's), and counts of the prompts you sent, your active agents and your top-level projects. Its tabs are **Messages** (every prompt you sent, across projects) and Later's three sections: **Saved**, **Reminders** and **Scheduled**. Handles are unique, case-insensitively. Old `?page=later` links open the profile. **Saved** is one list, newest save first, of every result and message you saved, with a search over their text, thread titles and optional short labels (“Chosen approach”). Saving a reply that has a result card saves that result, so the two are always saved together and listed once. As before, a saved result is included in agent memory by default, which now also applies when you save its reply. Saved follows the project and team filters, and every saved item has Reply, which quotes it in its own thread. **Remind me** brings a thread, result or message back to you; it never sends anything to an agent. A reminder returns at a chosen time, when the thread's agent has no active work, or the next time you open a project, and its card says which. The worker surfaces due items and sends a push notification to subscribed devices. A due reminder can be marked **Done** or snoozed again in place. Threads with a reminder leave the Feed until it is due. Saving, unsaving, reminders, scheduled and queued messages confirm with a link to the item and an **Undo** while it can still be reversed: unsaving waits for its Undo before it is sent, Undo of a reminder reopens any reminder it replaced, and Undo of a scheduled or queued message cancels it only if it has not started.

The composer says who and where a message goes (agent, project, thread). Its **Send later** menu distinguishes **Steer current task** (delivered into the live turn of a running API, subscription, Codex or Claude Code agent; HAPI-managed, Pi, OpenCode and ACP sessions cannot take input mid-turn, so a reply to them queues for the next turn instead and the option is not offered), **Queue after this task**, and **Send later at a time…**, which confirms the recipient, project, thread and exact local time before scheduling up to 30 days ahead. Later → **Scheduled** lists every scheduled message with its recipient and project, where it can be edited or cancelled; a scheduling confirmation links there. The worker submits scheduled messages with their stored idempotency key, so a retry after a crash cannot send twice. If Loop refuses a message when it is due (for example, its agent was retired), it is marked **Not sent** with the reason, in Later → Scheduled and under the Feed's **Needs you** (counted apart from messages still waiting); nothing was sent, and it waits until you choose **Send now**, edit it and schedule it again, copy it to a draft, or **Dismiss** it. Other errors leave it scheduled and it is tried again. The composer keeps each send's mode and exact time with its key, so retrying after a lost response repeats the original request and the server returns its receipt, even after the scheduled time. The computer must be awake for scheduled or queued work to start. A queued message waits behind the agent's earlier work, and stays held while that work is paused or awaiting approval; if that work fails or is cancelled, it starts next. Before a queued run starts, you can edit its message, move it up or down within that agent's queue, move it to another agent, or move it back to a draft.

An agent profile's **Traces** tab lists its public intermediate updates, commands and tool activity. Its search box matches every word, as a prefix, against trace titles and content and the tool results they link to; traces have their own index, so the Feed and workspace Search stay conversation-first. Each run's **Download run** saves its whole public record, including the final answer, as one JSON file (at most 5,000 traces, marked `truncated` beyond that); single traces can still be downloaded on their own.

The composer's dictation button appears only where the browser offers speech recognition; that browser feature may send audio to the browser vendor's service.

Pending approvals also send a push notification. The notification carries only the agent name and a link to the conversation, never the request's arguments, and approval always happens inside the app so the device lock still applies. Tapping a notification opens its thread at the message it is about: a new result opens at the answer that produced it. If Loop is already open, the service worker focuses it and opens the thread in place.

## Personal prompt history

**Your prompts** (Search, or the account button) is a private, newest-first history of prompts sent across the signed-in owner's projects, with an optional text filter. Entries show their run's receiving agent, project, conversation, attachments, a link to the original message, and Reply, which quotes that prompt in its thread. `/?page=personal` links open this view.

History uses canonical messages and rechecks owner, conversation and project access on every page. Archived work remains readable under the existing retention rules; deleting underlying messages/conversations removes them from history. Agent renames show the current name, while missing agent records show “Recipient unavailable.” Account changes reset the view.

New interactive submissions carry a server-controlled personal-origin marker; internal submissions are excluded. Older messages are included only when they have the submission attachment metadata and an agent run, without native projection/import markers or delegation ancestry. Legacy retry submissions cannot be distinguished reliably from original submissions and may appear; imported or unlinked records without reliable provenance are omitted. The view does not aggregate other owners or deployments.

## MCP tools

In Settings → Tools & integrations, choose a catalog integration or add a custom server. Paste `mcpServers` JSON for command or hosted configurations; complete any required OAuth or credential setup. Installation succeeds only after discovery. Catalog definitions are maintained in [catalog-data.ts](../src/server/mcp/catalog-data.ts), not fetched as executable instructions at runtime.

Connections are workspace-wide for that owner, including future agents and teams; other users do not inherit them. Agent-requested installation requires approval. Connected calls follow the workspace approval preference, with ownership, schema, discovered-tool and run-state checks at dispatch. A read-only annotation does not itself grant authorization. Disabling a connection blocks subsequent calls but cannot undo an already dispatched effect. Unknown outcomes are not automatically retried.

Hosted connections use validated network destinations. Private runtime origins require explicit operator configuration. Command MCPs run locally in companion mode and through runtime infrastructure in server mode. Native host configuration is distinct from workspace MCP configuration.

Charts save numeric data and provenance as snapshots; refresh is a new tool operation. Mermaid diagrams use the native renderer. MCP Apps run in an isolated iframe with a restrictive CSP and no same-origin access to the workspace. Unsupported rich content falls back to saved native/text output. These displays do not bypass the tool broker.

### GitHub pull requests

With the official GitHub integration connected (`api.githubcopilot.com/mcp`), agents work on pull requests from a conversation. Paste a pull request link or ask for open PRs: results from `pull_request_read`, `list_pull_requests` and `search_pull_requests` appear as PR cards showing the repository, number, title, state (draft, open, merged or closed), author, branch, head commit, size, merge status and requested reviewers, with a link to GitHub and the time GitHub was read. A card is a snapshot; ask the agent to refresh it. Other GitHub results (diffs, files, comments, checks) keep the plain tool output. Other servers' results never render as PR cards, whatever their tool names.

API-provider agents with GitHub tools receive guidance on Loop's rules, plus the `owner/repo#number` references parsed from the latest message. Only the parsed references are added, never the surrounding text. Pull request titles, descriptions, comments, diffs and repository files are untrusted content, not instructions or authorization. Native harnesses keep their own context; the broker rules below still apply to their calls.

GitHub writes (comments, reviews, edits, pushes) follow the workspace approval preference, and the approval names the target pull request and the action. Merges always wait for an explicit decision: with tool approvals set to Allow, a `merge_pull_request` call still requests approval, and switching to Allow does not approve merges that are already waiting. Loop refuses a `merge_pull_request` call without a full 40-character `expectedHeadSha` before requesting approval, so nothing is sent. An approved merge therefore applies only to the head commit shown in the approval: if new commits arrive, GitHub rejects the merge and the agent must ask again. Code changes use Git in the agent's workspace; see [harnesses](harnesses.md).

**Watch** on an open PR card in a thread sends what happens next on GitHub back to that thread ([pr-watches.ts](../src/server/pr-watches.ts)). Watching starts only when you tap it. About once a minute the worker reads the pull request with your GitHub connection's token, which stays on the server. When something new arrives, it queues one follow-up in the thread, labelled **GitHub update**, behind the agent's current work. A follow-up never steers a running task. New items include:

- CI failing on the latest commit, once every check has finished.
- CI turning green after a failure. A first green result is only recorded.
- Reviews, review comments and comments that other people posted after you started watching. Comments from the connected GitHub account (the agent's own) are skipped.

Quoted comment text is marked as untrusted. Updates wait while the agent is still on the previous one and are then sent together. Each follow-up's idempotency key comes from what it reports, so a restart cannot send the same update twice. The agent's pushes, comments and merges still follow the approval preference, and the follow-up tells it never to merge on its own.

Watching stops when the pull request is merged or closed, or when you choose **Stop watching**. It pauses after 5 follow-ups in an hour, so an agent cannot loop on its own pushes, and when GitHub rejects the connection. Nothing is lost while paused; **Resume** continues from where it stopped. One thread watches a pull request at a time. CI results come from GitHub check runs; legacy commit statuses are not read.

## Workflows

The editor uses the bounded JSON `loop.workflow/v1` format implemented in [server/workflows](../src/server/workflows). A workflow defines inputs, agent roles, sequential agent/approval/save steps, outputs and limits. References may use named inputs or earlier steps; forward references and invalid schemas are rejected. Saved versions and runs retain their selected connection/settings snapshots.

Run a saved version with inputs, review required approval steps and inspect linked child conversations/results. Checkpoints prevent duplicate child submission after restart. Cancellation propagates to the active child. Human approval waits do not occupy a worker slot. Workflow step/time limits apply to native execution, but native internal model calls and token use are not exactly enforceable. The format does not execute arbitrary embedded shell/code.

## Browser and offline behavior

The web app can be installed from an HTTPS origin using the browser's home-screen/app installation flow. A Quick Tunnel origin can change; run `loop pair` and add the new page to your home screen.

The service worker caches public shell assets, not private API responses or credentials. Offline relaunch shows reconnect UI; messages are not queued on the device while offline (scheduled sends are stored on the server). The **Open on another device** option in a thread shows a QR code and link for continuing on your computer or phone; the link carries no credentials. Share links create a draft for review rather than silently submitting work. See [pairing](pairing.md) for device access and reconnection.
