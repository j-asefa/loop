# Workspace features

Provider connections determine authentication, models and execution. Agents add instructions and settings; conversations retain their runtime binding. Use [harnesses](harnesses.md) for native execution and [server operation](server.md) for managed subscription/API setup.

## Conversations and organization

The phone layout has five tabs: **Feed**, **Projects**, **Pull requests** ([below](#github-pull-requests)), **Search** and **You**, your profile (on desktop the same five sit in the sidebar). The gear at the top right opens Settings, a drawer from the right holding every setting: appearance, connections, tools, agents, memory, notifications, search, import and install, with your account at its foot. Projects organize conversations and artifacts; a project opens on its Threads, with a search inside the project (its subfolders and threads included) and routes to its recent outcomes, saved decisions and unfinished work. Native project bindings also select an existing execution directory. Files can be attached to messages or published as private artifacts with versions. Public intermediate progress and structured activities are distinct from completed answers. Replies and follow-ups retain their selected-message context.

Teams coordinate manager/worker agents through bounded delegation and messages between their agents (see [Teams](#teams)). Deleting a team preserves its agents and history. Archiving affects feed visibility rather than deleting the underlying work. Imports bring existing chat exports into Loop; connecting a provider account does not automatically import website history.

Keyword search works without a provider. Semantic search can use a local embedding model/runtime and reports readiness or failure. Optional OpenAI embeddings require an explicitly selected API connection; subscription connections do not authorize embedding API usage. Search groups matches by thread, remembers recent searches on the device and has a **Your prompts** scope for your own sent messages.

### Feed and reading position

The Feed tab shows how many agents are working right now (9+ above nine). The Feed lists conversations by latest activity ([mobile-return.ts](../src/server/mobile-return.ts)). Each card shows the agent, project, run status and the latest message, which is the result when a run has finished. A card's model and **This laptop** or **Docker** badge come from the connection its run used. The badge appears only for a location Loop recorded when it registered the connection; Loop running in the companion container counts as Docker, and remote runners have no badge. Its filters are **Done** (the default: every thread's latest finished result, ordered by when it finished, plus threads with nothing open; a result stays there when a follow-up is queued, working or needs you), **Needs you** (approvals, paused, failed or interrupted work), **Working** (only what each current run has written so far) and **Queued**; old `?filter=all` links open Done. While a run works, its card heading shows the prompt that started that task, with whitespace collapsed and at most 200 characters; an empty prompt falls back to the thread title. The card shows the agent's output so far, or says no update has arrived yet and, for work Loop started, which watched pull request or teammate started it; it never repeats your prompt as an agent preview. Project and agent thread lists still show every thread. Result cards with their files and previews stay on agent profiles and project pages. When a thread waits for something specific, its card offers that one action (**Approve request**, **Answer question**, **Continue draft** for an unsent draft, or **Review result**) and opens the thread at that exact message; otherwise it offers Reply. Swipe a card left to archive it (it stays in history and search); long-press for run controls. A card's menu also has **Save**, which keeps its latest message — and the result card that message produced — in Later → Saved, exactly as saving it inside the thread would. A “while you were away” card summarizes what finished, failed or needs you since the last visit. Loop has no read or unread state.

A thread remembers where you stopped scrolling and reopens there, saying **Resumed where you left off** with a **Latest** button; at the latest output it opens at the latest messages. Opening a specific message (from Saved, Search, a notification, the Feed or Jump to) highlights it and offers **Back to where I was**. That detour is kept apart from the reading position: the position changes only when you go back, reach the latest messages or read on from a thread you opened normally. Unsent drafts are kept per thread on the device. Swiping back returns to the previous page as you left it: the Feed, Later section and Search query and results reappear at the same scroll position while they refresh. These views are kept in memory for the signed-in account only. Pulling down at the top of any page refreshes it.

Replies stay inside the thread. Any message can be replied to, the agent's or your own; your own is quoted as “my earlier message”. **Reply to part** (under More) shows the message as plain text: highlight the lines you mean and only those are quoted, as “part of” the message. The server checks that the excerpt is text the message contains, so the attribution stays true. A whole-message quote longer than 6,000 characters keeps its start and end, with the omitted length marked in between. Each message's menu leads with Reply, Save and Remind me; **More** holds replying to part of the message, forking from that message into a new conversation (which copies the conversation, not files: nothing is rewound), reusing it as an editable draft, saving it as a snippet (reusable instructions, inserted with `/` in the composer), copying and sharing its link. **Jump to…** lists the thread's prompts, results, approvals, failures and saved messages, and searches the text of every message in the thread. File activity from a run collapses into one summary that opens a **Reported file activity** review. It lists what the agent's tools reported, edit by edit, rather than a diff of the repository, grouped as applied, proposed, failed, or with no reported outcome; only applied edits are counted, and review prompts cover only files with applied edits. It shows what Loop knows of the run (agent, project, start time, commands the agent reported running); repository, branch and pull request are not reported by harnesses today. Its follow-up buttons only prefill an editable prompt that asks the agent to check the full diff first: Loop never applies, commits or reverts files itself, and harness session commands such as rewind stay in the native terminal. Token counts appear when the provider reports usage; Loop does not estimate cost.

### Your profile, Later and deferred work

**You** shows your profile: your name, an optional @handle and bio (**Edit profile**; an empty name falls back to your account's), and counts of the prompts you sent, your active agents and your top-level projects. Its tabs are **Messages** (every prompt you sent, across projects) and Later's three sections: **Saved**, **Reminders** and **Scheduled**. Handles are unique, case-insensitively. Old `?page=later` links open the profile. **Saved** is one list, newest save first, of every result and message you saved, with a search over their text, thread titles and optional short labels (“Chosen approach”). Saving a reply that has a result card saves that result, so the two are always saved together and listed once. As before, a saved result is included in agent memory by default, which now also applies when you save its reply. Saved follows the project and team filters, and every saved item has Reply, which quotes it in its own thread. **Remind me** brings a thread, result or message back to you; it never sends anything to an agent. A reminder returns at a chosen time, when the thread's agent has no active work, or the next time you open a project, and its card says which. The worker surfaces due items and sends a push notification to subscribed devices. A due reminder can be marked **Done** or snoozed again in place. Threads with a reminder leave the Feed until it is due. Saving, unsaving, reminders, scheduled and queued messages confirm with a link to the item and an **Undo** while it can still be reversed: unsaving waits for its Undo before it is sent, Undo of a reminder reopens any reminder it replaced, and Undo of a scheduled or queued message cancels it only if it has not started.

The composer says who and where a message goes (agent, project, thread). Its **Send later** menu distinguishes **Steer current task** (delivered into the live turn of a running API, subscription, Codex, Claude Code or Pi agent; OpenCode and ACP sessions cannot take input mid-turn, so a reply to them queues for the next turn instead and the option is not offered), **Queue after this task**, and **Send later at a time…**, which confirms the recipient, project, thread and exact local time before scheduling up to 30 days ahead. Later → **Scheduled** lists every scheduled message with its recipient and project, where it can be edited or cancelled; a scheduling confirmation links there. The worker submits scheduled messages with their stored idempotency key, so a retry after a crash cannot send twice. If Loop refuses a message when it is due (for example, its agent was retired), it is marked **Not sent** with the reason, in Later → Scheduled and under the Feed's **Needs you** (counted apart from messages still waiting); nothing was sent, and it waits until you choose **Send now**, edit it and schedule it again, copy it to a draft, or **Dismiss** it. Other errors leave it scheduled and it is tried again. The composer keeps each send's mode and exact time with its key, so retrying after a lost response repeats the original request and the server returns its receipt, even after the scheduled time. The computer must be awake for scheduled or queued work to start. A queued message waits behind the agent's earlier work, and stays held while that work is paused or awaiting approval; if that work fails or is cancelled, it starts next. Before a queued run starts, you can edit its message, move it up or down within that agent's queue, move it to another agent, or move it back to a draft.

An agent profile's **Traces** tab lists its public intermediate updates, commands and tool activity. Its search box matches every word, as a prefix, against trace titles and content and the tool results they link to; traces have their own index, so the Feed and workspace Search stay conversation-first. Each run's **Download run** saves its whole public record, including the final answer, as one JSON file (at most 5,000 traces, marked `truncated` beyond that); single traces can still be downloaded on their own.

The composer's dictation button appears only where the browser offers speech recognition; that browser feature may send audio to the browser vendor's service.

A new result's push notification is headed by the agent and the thread's title, and its text is the start of the answer as plain text (for a chart, image or pull request card, what kind of result it is). Pending approvals also send a push notification. The notification carries only the agent name and a link to the conversation, never the request's arguments, and approval always happens inside the app so the device lock still applies. Tapping a notification opens its thread at the message it is about: a new result opens at the answer that produced it. If Loop is already open, the service worker focuses it and opens the thread in place.

## Personal prompt history

**Your prompts** (Search, or the account button) is a private, newest-first history of prompts sent across the signed-in owner's projects, with an optional text filter. Entries show their run's receiving agent, project, conversation, attachments, a link to the original message, and Reply, which quotes that prompt in its thread. `/?page=personal` links open this view.

History uses canonical messages and rechecks owner, conversation and project access on every page. Archived work remains readable under the existing retention rules; deleting underlying messages/conversations removes them from history. Agent renames show the current name, while missing agent records show “Recipient unavailable.” Account changes reset the view.

New interactive submissions carry a server-controlled personal-origin marker; internal submissions are excluded. Older messages are included only when they have the submission attachment metadata and an agent run, without native projection/import markers or delegation ancestry. Legacy retry submissions cannot be distinguished reliably from original submissions and may appear; imported or unlinked records without reliable provenance are omitted. The view does not aggregate other owners or deployments.

## Teams

**Team presets.** New team offers **Review code changes**, **Build a feature** and **Investigate a bug**, as well as a custom team of existing agents. Choose a project and a connected provider/model; expand the role settings to use different connections. Loop creates the manager and workers together and records the preset version, instructions and role assignments. Retrying creation with the same request does not create duplicates. Changes to built-in presets do not rewrite existing teams. Each generated agent remains editable from its profile.

**Local code review.** Choose **Review changes** on a project or a review team's directory entry. In a laptop workspace, select uncommitted changes (including non-ignored new files), staged changes, or committed branch changes against a base. The project must be bound to the Git repository root and have an initial commit. Loop captures the diff, baseline versions of changed files and repository context twice, rejecting a capture if the snapshots differ. It does not checkout files, change the index, create a PR or run tests/CI. The three reviewers get fresh conversations and the same immutable snapshot. The lead runs after they finish, with their reports and actual completion states, and verifies and consolidates findings. Existing delegation records provide queue dependencies and cancellation of reviewers with the lead.

Review teams can use any connection, including harness subscriptions. API reviewers receive the snapshot in their history and expose only `loop_review_read`, which reads captured text from the owner's review, and reject external MCP calls. Native reviewers receive the snapshot in their first turn and get `loop_review_read` through Loop's tool bridge, but they keep their harness's own tools and permissions; read-only access is an instruction, not an enforced boundary. Follow-ups in a review conversation keep the same snapshot binding. Feature-building and bug-investigation presets use normal agent permissions and existing delegation rules.

The snapshot reader lists omissions: hidden files, common credential files, generated/vendor output, submodules, symlinks, binary files and files over 512 KB. These filename filters are not a content secret scanner; selected source text is sent to the chosen providers. Capture is bounded to 100 changed files, 2,000 repository files, 16 MB of text and about 300 KB of diff. Each review agent has a 180-second execution limit (600 seconds on native harnesses). Oversized captures fail explicitly. The report's status panel shows reviewer failures separately from completed reviews and lists omitted files; no tests are claimed. **Check for newer edits** compares the current repository capture with the reviewed snapshot. That check is a point-in-time observation, not a continuous watch. Applying fixes is a separate task with an editing agent.

A team is a manager and up to 8 workers. Each agent keeps its own provider connection, so one team can mix API agents and native Codex, Claude Code, Pi and OpenCode agents. You talk to the manager in the team thread. Open **Teams** from the desktop workspace sidebar or **Projects → Agent teams** on a phone to browse teams, open a team feed, or add an existing connected agent as a worker. The Feed's team filter also opens a selected team's activity.

**Delegation.** The manager's `loop_delegate` tool starts focused tasks for workers, which run in parallel; their updates appear in the team's feed. By default the call waits for every result. With `wait: false` the manager keeps working or finishes its turn, and each worker's result arrives later in the delegating conversation as a turn labelled **Result from @worker**, once per final state. While the manager is working in another team conversation, results wait rather than start a second session. Cancelling the manager's task also cancels its workers' tasks and any of their results still waiting to be read; results from workers that finished but weren't delivered yet are dropped, so a cancelled manager is never restarted.

**Messages.** Every team member gets `loop_message`, with a roster of its teammates (id, role and runtime), and `loop_message_status` to check delivery ([agent-mail.ts](../src/server/agent-mail.ts)). Loop submits a message as an ordinary turn in the recipient's conversation, so it is stored durably, delivered once even across retries and restarts, and each harness keeps its own context. Where it lands:

- If the recipient is working on the team, in that conversation, after its current task: a message never starts a second session beside work in progress. With `interrupt`, it goes into the running task instead when the runtime takes live input (API, subscription, Codex, Claude Code and Pi); OpenCode and ACP sessions still get it after the task. A manager waiting on blocking delegation is never interrupted, since a Claude Code steer would cut off its open delegation call.
- Otherwise it wakes the recipient's conversation in that thread, the conversation of the delegation it belongs to or, for the manager, the team thread. Failing those, it starts a new team conversation.

A message delivered into a task that ended without reading it is queued again as a new turn, unless you cancelled that task. A live delivery the harness could not confirm shows as unconfirmed and is never sent twice. A result or requeued message that Loop can't submit yet (a disconnected provider, a full queue) is tried again later; one whose recipient was retired or left the team is marked not delivered. `loop_handoff` transfers an explicit next task, context summary, workspace reference and published files to a teammate, requesting an acknowledgement in the same thread. It does not move native session context, stop the sender, or grant approval. Replies carry the thread id from the message they answer. Messages appear as **Message from @agent**, in the thread and on Feed cards. Their text tells the recipient that the input comes from another agent, not from you, and grants no permission or approval; approvals still follow your settings. A message can carry up to 8 files that the sender published or that are attached to its conversation, which the recipient reads with `loop_read_file`. Agents in different environments (another runtime host, or an API agent and a harness on your computer) are told that the sender's files are not on their machine.

One task can send 8 messages. A thread pauses after 30 messages, or when two agents exchange 20 messages in an hour; later messages in it are held, not dropped. With one team selected in the team filter, **Team messages** lists its threads with each message's delivery state and a link to the recipient's thread. **Resume** sends held messages in order and gives the two agents a fresh allowance; if one can't be sent yet, the thread pauses again before it. Every delivered message is a turn on the recipient's own connection, so it uses that subscription's limits or that API key's billing.

## MCP tools

In Settings → Tools & integrations, choose a catalog integration or add a custom server. Paste `mcpServers` JSON for command or hosted configurations; complete any required OAuth or credential setup. Installation succeeds only after discovery. Catalog definitions are maintained in [catalog-data.ts](../src/server/mcp/catalog-data.ts), not fetched as executable instructions at runtime.

Connections are workspace-wide for that owner, including future agents and teams; other users do not inherit them. Agent-requested installation requires approval. Connected calls follow the workspace approval preference, with ownership, schema, discovered-tool and run-state checks at dispatch. A read-only annotation does not itself grant authorization. Native shell, file and other harness tools follow a separate owner-wide preference, **Settings → Permissions → Agent tool calls** ([permission-modes.ts](../src/shared/permission-modes.ts)), sent with each run. **Never ask** starts Claude Code sessions in `bypassPermissions`. For the other harnesses on your computers, Loop answers each tool approval with the harness's one-call allow choice (Codex `accept`, OpenCode `once`, ACP `allow_once`). Questions, elicitations and Pi confirmations still wait for you. **Auto-accept file edits** applies only to Claude Code. A change applies from the agent's next turn; a Claude session restarts to change its launch mode, and requests already waiting keep asking. A permission mode chosen for one session in **Session settings** outranks this preference for that session: Loop answers for you only when that session's own mode is `bypassPermissions`.  Native approval cards also offer **Fewer approval prompts**, linking to this preference and to the harness's **Session settings** (when it supports permission controls). Allowing connected MCP tools does not change native shell/file permissions, and agent tool calls do not change MCP approvals. Disabling a connection blocks subsequent calls but cannot undo an already dispatched effect. Unknown outcomes are not automatically retried.

Hosted connections use validated network destinations. Private runtime origins require explicit operator configuration. Command MCPs run locally in companion mode and through runtime infrastructure in server mode.

**Sharing between Loop sources:** A Docker runner attached to one Loop workspace already uses that workspace's MCP catalog. An older, independent Docker Loop server owns a separate catalog and credentials. In **Tools & integrations → Installed**, press **Share tools** beside a discovered, loopback-published Docker source to connect the two catalogs. The paired laptop contacts only that verified local Docker source. Docker-owned MCPs remain on Docker and laptop-owned MCPs remain on the laptop; the browser receives neither provider credentials nor relay tokens. Docker requests for laptop tools wait in a durable queue that the laptop polls through Docker's loopback API, so the laptop opens no network listener. The laptop claims each queued call just before running it, so a call Docker has already reported as uncertain (timed out, cancelled or disconnected) is never run. Each side records call identities before external effects, and uncertain outcomes are never replayed; a call that could not connect sends nothing and stays retryable. New catalog entries refresh within about a minute; if Docker's catalog would exceed the tool budget, the previous catalog stays shared; already running harness sessions may need a new turn or reconnection to list new tools. **Stop sharing**, beside the source or on its shared connection, revokes the relay token and disables both proxy connections; if Docker is offline, the laptop keeps the remote revocation pending until it reconnects. Setup routes accept only local requests from the laptop's source adapter, never through the paired-browser proxy. The Docker server needs a Loop version with the federation routes. Other remote hosts need their own securely enrolled source adapter.

**Importing harness-installed MCPs:** On a personal Loop (companion or single-user), **Installed → Import from installed harnesses** lists server names found in Codex's JSON CLI catalog, Claude's standard `mcpServers` files, OpenCode's global JSON configuration, and Pi's common `mcp.json` adapter file. The browser receives names and transport kinds only. Choosing **Import** copies that server's configuration into the same source's encrypted Loop store, then discovers its tools. OAuth accounts and unsupported native transports may still need reconnecting in Loop. Custom Pi extensions and other harness-specific stores are not inspected. The existing **Paste MCP JSON configuration** form handles configurations these readers do not recognize. Once imported, a server follows the same owner-scoped catalog and can be shared with a connected Docker source. Native provider homes remain owned by their harnesses. A multi-user server never lists or imports its own harness configurations.

Charts save numeric data and provenance as snapshots; refresh is a new tool operation. Mermaid diagrams use the native renderer. Loop does not advertise MCP Apps support or fetch interactive app resources. Tools use ordinary text/structured results and Loop's normal approval flow. If a server still returns a form-required error, it remains a failed tool result; Loop does not claim success or replay the operation. Previously saved app artifacts retain their isolated viewer. These displays do not bypass the tool broker.

### GitHub pull requests

With the official GitHub integration connected (`api.githubcopilot.com/mcp`), the **Pull requests** tab lists your open pull requests across GitHub without involving an agent ([github-pulls.ts](../src/server/github-pulls.ts)). The server reads GitHub with that connection's token, which never reaches the browser or an agent. Filters show **Review requested**, **Yours** and **Involving you**, each with its count, plus each pull request's checks and review state. The search box filters by text, narrows the list to a repository when you type `owner/repo`, and opens any pull request when you paste its link. The list shows the 50 most recently updated. Opening a pull request shows its description, checks, the latest 50 submitted reviews, review threads, comments and the changed files with their diffs. The **Commits** tab shows the latest 100 commits with their authors and dates; expanding one reads its message and file diffs for that exact commit, with links to GitHub. Each commit shows up to 300 changed files; omitted or shortened diffs link to GitHub. Longer histories link to the full list. GitHub's HTML comments are hidden and other HTML shows as plain text. **View file** shows a changed file at the commit being viewed (the head commit in Files), including images and other binary files GitHub shows no diff for. Markdown is rendered like GitHub renders it (**Code** shows the source); its HTML is sanitized, relative images and video load from the same commit, and links to other repository files open in the viewer. External images are shown as links and never loaded. Images and video play inline, and other files show as text with line numbers. Files are served only as images, video, plain text or downloads, never as pages. Each person's copy of a file is kept for a day, and files over 50 MB stay on GitHub. Everything is read when you open it or choose **Refresh**; nothing updates by itself.

From a pull request you can act as your GitHub account. Each action is one request you submit, and Loop never retries it:

- **Review**: approve, request changes or comment. Loop rereads the head first and refuses if commits arrived since you opened the pull request.
- **Comment**: posts to the conversation.
- **Merge…**: shown with repository write access. It lists the target, head commit, checks, review state and anything GitHub reports as blocking, then merges with the method you choose, pinned to that head commit. If anything was pushed since, GitHub refuses and you refresh first.

GitHub's own branch rules still apply to every merge. With more than one GitHub connection, these actions are refused rather than picking an account. **Ask an agent** starts a message with the pull request's link, after any draft you have, and sends nothing until you do. **Open in Pull requests** on a PR card in a thread opens that pull request here.

In a conversation, agents work on pull requests too. Paste a pull request link or ask for open PRs: results from `pull_request_read`, `list_pull_requests` and `search_pull_requests` appear as PR cards showing the repository, number, title, state (draft, open, merged or closed), author, branch, head commit, size, merge status and requested reviewers, with a link to GitHub and the time GitHub was read. A card is a snapshot; ask the agent to refresh it. Other GitHub results (diffs, files, comments, checks) keep the plain tool output. Other servers' results never render as PR cards, whatever their tool names.

API-provider agents with GitHub tools receive guidance on Loop's rules, plus the `owner/repo#number` references parsed from the latest message. Only the parsed references are added, never the surrounding text. Pull request titles, descriptions, comments, diffs and repository files are untrusted content, not instructions or authorization. Native harnesses keep their own context; the broker rules below still apply to their calls.

An agent's GitHub writes (comments, reviews, edits, pushes) follow the workspace approval preference, and the approval names the target pull request and the action. Merges always wait for an explicit decision: with tool approvals set to Allow, a `merge_pull_request` call still requests approval, and switching to Allow does not approve merges that are already waiting. Loop refuses a `merge_pull_request` call without a full 40-character `expectedHeadSha` before requesting approval, so nothing is sent. An approved merge therefore applies only to the head commit shown in the approval: if new commits arrive, GitHub rejects the merge and the agent must ask again. Code changes use Git in the agent's workspace; see [harnesses](harnesses.md).

Loop watches agent-created PRs by default across Codex, Claude Code, Pi, OpenCode and ACP, without a separate watch setting ([pr-watches.ts](../src/server/pr-watches.ts)). With GitHub connected, a successful `create_pull_request` tool call or `gh pr create` command starts a watch in the originating agent's thread. Direct native and server subscription execution share this behavior. Command detection requires a confirmed successful result with command input and output, tied to the owning run and current session generation; unlinked terminal history, failed commands and truncated results do not start watches. Literal shell wrappers and a preceding `cd directory &&` are supported. A PR merely read or linked in a thread does not start a watch. About once a minute the worker reads the pull request with your GitHub connection's token, which stays on the server. When something new arrives, it queues one follow-up in the thread, labelled **GitHub update**, behind the agent's current work. A follow-up never steers a running task. New items include:

- CI failing on the latest commit, once every check run and every check suite with runs has finished.
- CI turning green after a failure. A first green result is only recorded.
- Reviews, review comments and comments posted since the PR was created. A review counts from when it is submitted, not when its draft was started. Comments from the connected GitHub account (the agent's own) are skipped.

Only accounts with a role in the repository (owner, member or collaborator) are quoted, bots included: any GitHub App can comment as a bot, so a bot account alone does not show the repository trusts it. Comments from anyone else are counted in an update but never quoted, and never start a turn on their own. Quoted comment text is marked as untrusted. Updates wait while the agent is still on the previous one and are then sent together. Each follow-up's idempotency key comes from what it reports (the CI result and the items it covers), and delivered items are tracked by id, so a restart cannot send the same update twice. The Feed labels these follow-ups **GitHub update** too. The agent's pushes, comments and merges still follow the approval preference, and the follow-up tells it never to merge on its own.

Watching stops when the pull request is merged or closed, or when you choose **Stop watching**. It pauses after 5 follow-ups in an hour, so an agent cannot loop on its own pushes, and when GitHub rejects the connection. Nothing is lost while paused; **Resume** continues from where it stopped. One thread watches a pull request at a time. CI results come from GitHub check runs; legacy commit statuses are not read.

## Workflows

The editor uses the bounded JSON `loop.workflow/v1` format implemented in [server/workflows](../src/server/workflows). A workflow defines inputs, agent roles, sequential agent/approval/save steps, outputs and limits. References may use named inputs or earlier steps; forward references and invalid schemas are rejected. Saved versions and runs retain their selected connection/settings snapshots.

Run a saved version with inputs, review required approval steps and inspect linked child conversations/results. Checkpoints prevent duplicate child submission after restart. Cancellation propagates to the active child. Human approval waits do not occupy a worker slot. Workflow step/time limits apply to native execution, but native internal model calls and token use are not exactly enforceable. The format does not execute arbitrary embedded shell/code.

## Social feeds

Social is a reader for public feeds, under the Feed's **Social** filter. Its catalog is checked in at [news.ts](../src/shared/news.ts): each entry was read with the shared parser before it was listed, so Social fetches only addresses in that list, and only redirects within a feed's own site. [syndication.ts](../src/server/syndication.ts) reads RSS 2.0 and 0.9x, RSS 1.0 (RDF), Atom and JSON Feed into one kind of card, and adds what a few sites carry beyond the formats: Hacker News points, a Reddit post's linked article and subreddit. Reddit itself is not in the catalog — its logged-out RSS answers 429 and `old.reddit.com` redirects feeds to a sign-in page. Run `npm run feeds:check` to read the whole catalog over the network.

**What is shared and what is yours.** A feed's contents are the same for everyone who added it, so stories are stored once in `feed_stories` with that feed's fetch health in `feed_state`. What is yours stays owner-scoped: which feeds you follow, what you have read, what you saved, your watches and your digests. Stories are shown to you, and reach an agent only through the opt-in tool below.

**Your own feeds.** Beyond the catalog you can add any public feed by address, or paste a site's address and pick from the feeds that page advertises; OPML import brings another reader's list in and export takes it out. A typed address has no warrant, so [feed-sources.ts](../src/server/feed-sources.ts) validates it before Loop ever requests it — public HTTPS, no credentials, never an address on this network — and the request goes through the same transport as a catalog feed, which resolves DNS through a public-only dispatcher, refuses any host answering on a private address, follows redirects only within the feed's own site, and reports a feed that redirects to a sign-in page as needing an account. Feeds needing a token or cookie are not supported.

**Freshness.** The worker reads each followed feed about every five minutes, so opening Social is served from the store rather than the network and stays current with the tab closed. It sends `If-None-Match`/`If-Modified-Since`, so a feed that has not changed answers 304 and sends nothing. A feed that fails is retried on a widening delay — two minutes doubling to an hour, or longer if it asked — and its last good stories keep showing meanwhile. A request returns the feeds it already has and names the rest in `pending`, so a page is never held up by its slowest feed; pulling the page down refreshes the feeds themselves, down to a thirty-second floor. Reading stops once a feed has the stories Loop keeps, so a full-text feed is not downloaded whole. Each feed keeps its newest 120 stories — plus any you saved — and the stories of a feed nobody follows are dropped a month later.

**Reading.** A story is read when you open it, open its discussion, ask an agent about it, or mark it; "mark all read" is a watermark rather than a row per story. The Social chip carries the unread count. A story can be saved to Later beside a conversation, a result and a message, and comes back at a time. Searching reaches the whole store rather than the page, so a story from last week is still findable; words you mute are hidden from the list, counted, and shown again on request. Pictures a feed offers are off until you turn them on, and when they are on Loop fetches them itself rather than letting the browser do it: the page's own policy allows no third-party images, and a picture loaded from the publisher would tell that site who is reading. Only the address stored on a story of a feed you follow is fetched, only real raster images are passed through (never SVG, which can carry script), and they are capped at 5 MB.

**Agents and digests.** An agent can read your feeds only through `loop_feed`, and only once you turn agent access on — off by default, because a tool that lists your feed puts what you follow into a model's context. It reads the store: it fetches nothing, marks nothing read, and never sees a feed you do not follow. A digest is scheduled per agent at a clock time in your own zone: Loop collects what arrived, asks the agent to summarize it, and sends it once a day, labelled **Feed digest** rather than as something you typed. Comparing local days means a daylight-saving change keeps the same clock time and a server that was off for a day sends one digest, not five.

**The worker's pass.** One job: read the feeds that are due, then — once those reads have settled — send any due digest and look for watch matches in what the pass brought in. Running the three in order is what makes a digest cover today's stories rather than yesterday's, and it is one tracked job, so a shutdown waits for all of it.

**Following a word.** A watch matches whole words against stories that arrive — so "ai" finds "AI safety" and not "said" — over the feeds you follow, and never causes a fetch. The first match for a story notifies your phone once; a watch is capped at three notifications an hour and an owner at ten, after which the rest are recorded and summarized in one line. Tapping a notification opens Social on that story. The add form previews what a watch would have caught before you create it.

## Browser and offline behavior

The web app can be installed from an HTTPS origin using the browser's home-screen/app installation flow. A Quick Tunnel origin can change; run `loop pair` and add the new page to your home screen.

The service worker caches public shell assets, not private API responses or credentials. Offline relaunch shows reconnect UI; messages are not queued on the device while offline (scheduled sends are stored on the server). The **Open on another device** option in a thread shows a QR code and link for continuing on your computer or phone; the link carries no credentials. Share links create a draft for review rather than silently submitting work. See [pairing](pairing.md) for device access and reconnection.
