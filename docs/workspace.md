# Workspace features

Provider connections determine authentication, models and execution. Agents add instructions and settings; conversations retain their runtime binding. Use [harnesses](harnesses.md) for native execution and [server operation](server.md) for managed subscription/API setup.

## Conversations and organization

**New agent** opens a simple **New chat** screen. With an account connected, choose **Start chatting** to create an agent with an automatic name and open the message box. The optional **First message** sends only when you choose **Start chatting**. **Customize** reveals the name, instructions, project, provider, model, effort and Markdown definitions; these settings start collapsed. Loop selects a connected account and its default model when available. If setup is needed, **Connect an account** leads to it.

The **+** button opens the composer with your current or last-used agent, or the same simple creation screen when you have no agents. Write a message and send; photos, files and dictation remain alongside the input. **Chat options** reveals model and effort, native commands and scheduled sends. Closing the composer or changing conversations hides those options again.

The phone layout has five tabs: **Feed**, **Projects**, **Pull requests** ([below](#github-pull-requests)), **Search** and **Your profile** (on desktop the same five sit in the sidebar). The gear at the top right opens Settings, a drawer from the right holding every setting: appearance, connections, tools, agents, memory, notifications, search, import and install, with your account at its foot. Projects organize conversations and artifacts; projects open on Threads and offer Agents, Activity and Files. Each project has a search inside the project (its subfolders and threads included) and routes to its recent outcomes, saved decisions and unfinished work. Native project bindings also select an existing execution directory. Files can be attached to messages or published as private artifacts with versions. Public intermediate progress and structured activities are distinct from completed answers. Replies and follow-ups retain their selected-message context.

Teams coordinate manager/worker agents through bounded delegation and messages between their agents (see [Teams](#teams)). Deleting a team preserves its agents and history. Dismissing a Done card removes only that card from Done; the conversation and its other results are unaffected. Imports bring existing chat exports into Loop; connecting a provider account does not automatically import website history.

Keyword search works without a provider. Semantic search can use a local embedding model/runtime and reports readiness or failure. Optional OpenAI embeddings require an explicitly selected API connection; subscription connections do not authorize embedding API usage. In the All scope, Search also finds agent profiles by partial name, with or without an `@` prefix, as you type; selecting a match opens that profile. Project and agent filters apply to these matches. Search groups content matches by thread, remembers recent searches on the device and has a **Your prompts** scope for your own sent messages.

The default **Workspace** project collects work without a named project, including ordinary folders outside a project. It appears alongside named projects in Projects. Existing work is included when the default project is first opened; its saved task locations stay intact. Each linked workspace has its own default project.

### Feed and reading position

The Feed tab shows how many agents are working right now (9+ above nine). The Feed keeps completed results in Done and lists active conversations by latest activity ([mobile-return.ts](../src/server/mobile-return.ts)). Each card shows the agent, project, run status and the message for that card's run. A single-line footer below the actions shows abbreviated diff totals for changes during that run and check counts; tap either for full details. Historical cumulative diffs appear as **Earlier checkout**; see [checkout records](harnesses.md#agent-worktrees). Empty check summaries and unchanged checkouts are omitted. A linked pull request's number appears even before CI reports a result; its recorded CI status is added when available. Tapping opens the pull request in this workspace. Older-head results, reruns, paused watches and failed refreshes are labelled so a previous pass is not presented as current; a linked workspace's CI status is informational. Branch names, commit counts and remote status stay out of the card. Work started by teammates, delegated tasks and workflow steps also appears in the Feed, moving through Queued, Working, Done or Needs you with its run. A card's model and [computer name](pairing.md#unified-agents-and-feed) or **Docker** badge come from the connection its run used. The badge appears only for a location Loop recorded when it registered the connection; Loop running in the companion container counts as Docker, and remote runners have no badge. What needs you (approvals, native decisions, messages that could not be sent, and paused, failed or interrupted work) appears above the filters only while something waits: one card with the rest stacked behind it, so acting on it brings up the next, and **Show all** displays only the cards that need you. **Collapse** restores the previous feed; choosing a filter also closes the expanded list. Its filters are **Done** (the default: every completed result, ordered by when it finished, plus threads with nothing open; each result stays there until you swipe it away, including after later runs finish or the conversation is snoozed), **Threads** (one latest card per conversation, ordered by latest activity, including working and queued threads; snoozed threads wait until their reminder is due), **Working** (only what each current run has written so far), and **Queued**; old `?filter=all`, `?filter=needs` and `?filter=status` links open Done. Double-tapping **Feed** in the tab bar returns to the top of Done from any filter or tab. A card's heading is the prompt of the run it shows (on Done, the prompt its answer replies to; while a run works, the prompt that started that task), with whitespace collapsed and at most 200 characters; imported history and an empty prompt fall back to the thread title. The card shows the agent's output so far, or says no update has arrived yet and, for work Loop started, which watched pull request or teammate started it; it never repeats your prompt as an agent preview. Project and agent thread lists still show every thread. Result cards with their files and previews stay on agent profiles and project pages. Tap a Done, Replies, Threads, Working or Queued card (or **Read update**) to open a reading sheet with the same agent header, content layout and fixed **Reply** button as saved results. Finished and queued messages load their full text on opening; live output shows the latest preview, with a conversation link when it reaches the preview limit. Recorded changes and checks also appear in the reading sheet; their badges open details above the preview, and closing the details returns to the same reading position. **Reply** opens the matching conversation and focuses its composer. **Review result** also opens the reading sheet. In **Threads**, cards whose latest content is your prompt open the conversation directly so the message keeps its original author. Requests such as **Approve request**, **Answer question** and **Continue draft** still open the conversation directly at the required action; project and agent thread lists retain direct navigation. Swipe a **Done** card left to remove only that card from Done; **Undo** restores that same card. Dismissal does not affect the conversation, other views, activity counts or future results. Failed and interrupted cards in **Needs you** can also be swiped left to acknowledge that failure; this leaves their run state, conversation and Done results intact. Running, queued and waiting cards cannot be swiped away. Long-press for run controls. A card's menu also has **Save**, which keeps its latest message — and the result card that message produced — in Later → Saved, exactly as saving it inside the thread would. A “while you were away” card summarizes what finished, failed or needs you since the last visit. Done, Threads, Working and Queued have no read or unread state. Replies track unread publications separately.

If a run stops while waiting for approval, Needs you shows its failure or interruption instead of an obsolete approval action. Requests that were never approved are closed; records of calls with uncertain outcomes are preserved and never automatically replayed. Dismissing the interruption acknowledges it without restarting the task.

A completed result requires a nonempty final assistant answer; prompt-only, commentary-only and empty turns do not become historical result cards. Each run result uses that run’s project for its label and project filtering; an explicit Workspace selection stays in Workspace even if the conversation is assigned to a named project later. Threads without results retain their idle-thread fallback with no answer preview.

**Replies** sits beside Done, Threads, Working and Queued. When you send a message into a running task, Loop delivers its durable message ID and tells the agent to answer with `loop_reply { replyTo, body }`. Each successful publication becomes its own finished reply card, headed by your message, even while the task continues. The reading sheet shows the original message preview and links to it; **Reply** quotes the published answer and steers the same conversation's active task where supported. Older connected environments show an update notice in Replies; supported environments still show their replies. Refreshing recognizes an upgrade. Reading a reply marks it read across devices and reduces the Replies badge. It never removes the card. Swipe left or choose **Archive reply** to remove that reply; **Undo** restores it. Later replies, task completion, snoozing and archiving a Done result do not replace or remove published replies.

Replies require an explicit tool publication: Loop validates that `replyTo` belongs to a user message addressed to the same run and conversation and is no longer pending delivery. A native call can arrive while its steering receipt is still being confirmed, or after acknowledgement failed even though the harness received the message. Publishing the reply does not retry that delivery or change its receipt. Repeating a tool call returns the same reply; a new call creates a new reply, including another answer to the same message. Plain transcript output, quoted message IDs and agent mail do not create Replies cards. Existing transcript history is not retrospectively classified, and an agent that does not call the tool still has its output in the conversation. Ordinary task answers and follow-ups queued as new turns remain results in Done. Steering guidance requests publication only when the runtime offers the tool; API workflow turns and snapshot review agents retain their restricted tool catalogs.

The Threads tab uses `/api/feed?filter=all` to page through one current card per conversation, and retains loaded history during refreshes. Its browser link is `?filter=threads`. The Feed requests `/api/feed?filter=done&expand=results` for independent result cards. Requests without `expand=results` keep the previous single-card-per-conversation response and two-field cursors for older open tabs. Updated Loop sources are required to serve the expanded history. Each refresh reads the newest page and at most one page of already-loaded history per source; untouched cards stay visible, and older changes reconcile across subsequent refreshes. Swiping, Undo and saving update the local cached card immediately.

A thread remembers where you stopped scrolling and reopens there, saying **Resumed where you left off** with a **Latest** button; at the latest output it opens at the latest messages. Opening a specific message (from Saved, Search, a notification, the Feed or Jump to) highlights it and offers **Back to where I was**. That detour is kept apart from the reading position: the position changes only when you go back, reach the latest messages or read on from a thread you opened normally. Unsent drafts are kept per thread on the device. Swiping back returns to the previous page as you left it: the Feed, Later section and Search query and results reappear at the same scroll position while they refresh. These views are kept in memory for the signed-in account only. Pulling down at the top of any page refreshes it.

Replies stay inside the thread. Any message can be replied to, the agent's or your own; your own is quoted as “my earlier message”. A reply to the agent's latest message, from the thread or its Done card, is not quoted while the thread is idle: it answers what the thread already ends with. Earlier messages and highlighted parts are quoted, and so is any reply while work is in progress or queued, since newer messages may arrive first. The composer shows the quote whenever it will be sent, and **Send later** keeps that decision even if the agent posts again before the scheduled time. **Reply to part** (under More) shows the message as plain text: highlight the lines you mean and only those are quoted, as “part of” the message. The server checks that the excerpt is text the message contains, so the attribution stays true. A whole-message quote longer than 6,000 characters keeps its start and end, with the omitted length marked in between. Inside a conversation, holding text keeps the browser's native selection and copy behavior; Loop does not open menus on a long press, including on Send. Use the **Message actions** and **Send later** buttons for those menus. Each message's menu leads with Reply, Save and Remind me; **More** holds replying to part of the message, forking from that message into a new conversation (which copies the conversation, not files: nothing is rewound), reusing it as an editable draft, saving it as a snippet (reusable instructions, inserted with `/` in the composer), copying and sharing its link. **Jump to…** lists the thread's prompts, results, approvals, failures and saved messages, and searches the text of every message in the thread. A native run's final message carries one **checkout** chip with the Git changes Loop observed in the agent's [worktree](harnesses.md#agent-worktrees). File counts, line totals and the file-by-file patch all come from that same saved checkout record. **Review changes** in the conversation menu opens the latest recorded checkout; each result's chip opens its own run. The review includes the branch, commits since the run started, untracked files, remote-tracking observation and capture caveats. Older cumulative comparisons remain labelled as historical in the review. Tool-reported edits stay in **Tool activity** alongside commands and plans; they do not supply a second diff total. API-provider agents have no checkout chip, and pending or failed captures never fall back to tool-edit counts. Beside it, a **verification** chip says which test, type-check or lint commands the agent ran and the exit Loop saw for each (passed, failed or unknown), or **No checks observed** when a run with a checkout ran none; tapping it lists the commands with their output tails. Loop recognises common runners and scripts (`npm test`, `vitest`, `tsc`, `eslint`, `pytest`, `go test`, `cargo test` and the like) in literal commands and `&&` chains; multi-line commands, pipelines, fallbacks and expansions are never read, and a syntax-only `bash -n` is not unwrapped. A zero exit means every step ran and passed; a nonzero exit from a single command is a failure, while a nonzero exit from a chain of several steps is recorded as unknown, because which step failed, or whether the checks ran at all, cannot be known. Loop never runs these commands itself, and a passing check shows that command passed, not that the right tests exist. A third chip shows the thread's pull request as its [watch](#github-pull-requests) last saw it: the number, whether checks passed, failed or are still pending for the head GitHub reported (a conclusion for an older head is shown as stale, never as current), whether the watch is paused or its last read failed, and when Loop last looked; it opens the pull request in the Pull requests tab. A run with a checkout but no watched pull request shows **No PR linked**. The Git review’s follow-up buttons only prefill an editable prompt that asks the agent to check the full diff first: Loop never applies, commits or reverts files itself, and harness session commands such as rewind stay in the native terminal. Token counts appear when the provider reports usage; Loop does not estimate cost.

### Your profile, Later and deferred work

**Your profile** shows your name, an optional @handle and bio (**Edit profile**; an empty name falls back to your account's), and counts of the prompts you sent, your active agents and your top-level projects. Its tabs are **Messages** (every prompt you sent, across projects), **Approvals**, **Answers**, **Files** (described below), **Social** (the feed reader below), and Later's three sections: **Saved**, **Reminders** and **Scheduled**. Handles are unique, case-insensitively. Old `?page=later` links open the profile. **Saved** is one list, newest save first, of every result and message you saved, with a search over their text, thread titles and optional short labels (“Chosen approach”). Saving a reply that has a result card saves that result, so the two are always saved together and listed once. As before, a saved result is included in agent memory by default, which now also applies when you save its reply. Saved follows the project and team filters, and every saved item has Reply, which quotes it in its own thread. **Remind me** brings a thread, result or message back to you; it never sends anything to an agent. A reminder returns at a chosen time, when the thread's agent has no active work, or the next time you open a project, and its card says which. The worker surfaces due items and sends a push notification to subscribed devices. A due reminder can be marked **Done** or snoozed again in place. A conversation reminder snoozes the thread view until it is due; its completed results stay in Done. Saving, unsaving, reminders, scheduled and queued messages confirm with a link to the item and an **Undo** while it can still be reversed: unsaving waits for its Undo before it is sent, Undo of a reminder reopens any reminder it replaced, and Undo of a scheduled or queued message cancels it only if it has not started.

**Approvals** lists approval requests you explicitly accepted or denied in Loop; **Answers** lists native questions you answered. Both show the request, your response, its date and agent, with a link to the conversation when available. They cover the current workspace and keep each owner's history separate. Long request details and responses are shown as bounded, labelled previews. History saves at most 8 KiB of response text per decision; the harness still receives your complete answer, and the conversation retains the full request. Approval history records your choice; subsequent tool execution results remain in the conversation. Automatic approvals and requests closed without your response are excluded. Secret answers are never saved in this history. New native responses the harness definitively refuses are removed; unconfirmed deliveries are labelled and never resent from the history. Older decisions appear only where Loop retained evidence of your response; missing answer text is marked unavailable, with the request date shown instead of an invented response date. Older connected workspaces show an update explanation without requesting an unsupported history endpoint.

The composer says who and where a message goes (agent, project, thread). Its **Send later** menu distinguishes **Steer current task** (delivered into the live turn of a running API, subscription, Codex, Claude Code or Pi agent; OpenCode and ACP sessions cannot take input mid-turn, so a reply to them queues for the next turn instead and the option is not offered), **Queue after this task**, and **Send later at a time…**, which confirms the recipient, project, thread and exact local time before scheduling up to 30 days ahead. Later → **Scheduled** lists every scheduled message with its recipient and project, where it can be edited or cancelled; a scheduling confirmation links there. The worker submits scheduled messages with their stored idempotency key, so a retry after a crash cannot send twice. If Loop refuses a message when it is due (for example, its agent was retired), it is marked **Not sent** with the reason, in Later → Scheduled and in the Feed's **Needs you** stack (counted apart from messages still waiting); nothing was sent, and it waits until you choose **Send now**, edit it and schedule it again, copy it to a draft, or **Dismiss** it. Other errors leave it scheduled and it is tried again. The composer keeps each send's mode and exact time with its key, so retrying after a lost response repeats the original request and the server returns its receipt, even after the scheduled time. The computer must be awake for scheduled or queued work to start. A queued message waits behind the agent's earlier work, and stays held while that work is paused or awaiting approval; if that work fails or is cancelled, it starts next. Before a queued run starts, you can edit its message, move it up or down within that agent's queue, move it to another agent, or move it back to a draft.

**Your profile → Files** lists the signed-in owner’s published agent files in the current workspace, newest publication first, including files whose results are hidden or archived. Search filenames and titles, filter by type, agent or project, preview and download files, or open the originating conversation. Images, self-contained sandboxed HTML, text and browser-supported videos have previews. Files must be explicitly published with `loop_publish_file`; workspace files and user uploads are not automatically collected here. Published bytes are snapshots stored under `LOOP_DATA_DIR/objects` with metadata in `loop.db`, limited to 25 MB per file. Retain both in backups; access requires the hosting workspace to be online.

An agent profile's **Traces** tab lists its public intermediate updates, commands and tool activity. Its search box matches every word, as a prefix, against trace titles and content and the tool results they link to; traces have their own index, so the Feed and workspace Search stay conversation-first. Each run's **Download run** saves its whole public record, including the final answer, as one JSON file (at most 5,000 traces, marked `truncated` beyond that); single traces can still be downloaded on their own.

The composer's dictation button appears only where the browser offers speech recognition; that browser feature may send audio to the browser vendor's service.

A new result's push notification is headed by the agent and the thread's title, and its text is the start of the answer as plain text (for a chart, image or pull request card, what kind of result it is). Pending approvals also send a push notification. The notification carries only the agent name and a link to the conversation, never the request's arguments, and approval always happens inside the app so the device lock still applies. Tapping a notification opens its thread at the message it is about: a new result opens at the answer that produced it. If Loop is already open, the service worker focuses it and opens the thread in place.

## Personal prompt history

**Your prompts** (Search, or the account button) is a private, newest-first history of prompts sent across the signed-in owner's projects, with an optional text filter. Entries show their run's receiving agent, project, conversation, attachments, a link to the original message, and Reply, which quotes that prompt in its thread. `/?page=personal` links open this view.

History uses canonical messages and rechecks owner, conversation and project access on every page. Archived work remains readable under the existing retention rules; deleting underlying messages/conversations removes them from history. Agent renames show the current name, while missing agent records show “Recipient unavailable.” Account changes reset the view.

New interactive submissions carry a server-controlled personal-origin marker; internal submissions are excluded. Older messages are included only when they have the submission attachment metadata and an agent run, without native projection/import markers or delegation ancestry. Legacy retry submissions cannot be distinguished reliably from original submissions and may appear; imported or unlinked records without reliable provenance are omitted. The view does not aggregate other owners or deployments.

## Teams

**Team presets.** New team offers **Review code changes**, **Ask an LLM council**, **Build a feature** and **Investigate a bug**, as well as a custom team of existing agents. Choose a project and a connected provider/model; expand the role settings to use different connections. Loop creates the manager and workers together and records the preset version, instructions and role assignments. Retrying creation with the same request does not create duplicates. Changes to built-in presets do not rewrite existing teams. Each generated agent remains editable from its profile.

**Local code review.** Choose **Review changes** on a project or a review team's directory entry. In a laptop workspace, select uncommitted changes (including non-ignored new files), staged changes, or committed branch changes against a base. The project must be bound to the Git repository root and have an initial commit. Loop captures the diff, baseline versions of changed files and repository context twice, rejecting a capture if the snapshots differ. It does not checkout files, change the index, create a PR or run tests/CI. The three reviewers get fresh conversations and the same immutable snapshot. The lead runs after they finish, with their reports and actual completion states, and verifies and consolidates findings. Existing delegation records provide queue dependencies and cancellation of reviewers with the lead.

**Agent-requested review.** An agent that is not on a review team can ask one to review its work, for example when you tell it to get a review before opening a pull request. Its `loop_request_review` tool lists the review teams it may use and captures the agent's own checkout — its [worktree](harnesses.md) for native harnesses, otherwise the project's repository — with scope `branch` (default, against `main`), `uncommitted` or `staged`. The checkout must share the project's Git repository. The call returns a durable review ID immediately. Use `loop_review_status` with that ID to read progress and, once finished, the lead’s consolidated report and each reviewer’s state. Omit the ID to recover this agent’s ten most recent requests, including requests from earlier turns or calls that timed out. Status reads never start another review. Optional `wait: true` waits for completion, but may exceed a harness timeout; recover through the status tool. Edits made after capture are not covered. Cancelling the requester cancels the lead and its reviewers. Retrying the same tool call returns the same review rather than starting another; a new call starts a new snapshot review.

Review teams can use any connection, including harness subscriptions. API reviewers receive the snapshot in their history and expose only `loop_review_read`, which reads captured text from the owner's review, and reject external MCP calls. Native reviewers receive the snapshot in their first turn and get `loop_review_read` through Loop's tool bridge, but they keep their harness's own tools and permissions; read-only access is an instruction, not an enforced boundary. Follow-ups in a review conversation keep the same snapshot binding. Feature-building and bug-investigation presets use normal agent permissions and existing delegation rules.

**LLM council.** Based on Karpathy's [llm-council](https://github.com/karpathy/llm-council). The chair delegates the question to three members, then sends each member the other members' answers, anonymized and in shuffled order, to rank. Members never rank their own answer. The chair adds up the rankings with Borda points, checks the key claims itself and writes one answer, followed by the points, the disagreements and its confidence. The role settings open by default so each member can use a different model. The process lives in the agents' instructions and runs through ordinary delegation; Loop does not enforce the anonymization or the shuffling.

The snapshot reader lists omissions: hidden files, common credential files, generated/vendor output, submodules, symlinks, binary files and files over 512 KB. These filename filters are not a content secret scanner; selected source text is sent to the chosen providers. Capture is bounded to 100 changed files, 2,000 repository files, 16 MB of text and about 300 KB of diff. Each review agent has a 180-second execution limit (600 seconds on native harnesses). Oversized captures fail explicitly. The report's status panel shows reviewer failures separately from completed reviews and lists omitted files; no tests are claimed. **Check for newer edits** compares the current repository capture with the reviewed snapshot. That check is a point-in-time observation, not a continuous watch. Applying fixes is a separate task with an editing agent.

A team is a manager and up to 8 workers. Each agent keeps its own provider connection, so one team can mix API agents and native Codex, Claude Code, Pi and OpenCode agents. You talk to the manager in the team thread. Open **Teams** from the desktop workspace sidebar or **Projects → Agent teams** on a phone to browse teams, open a team feed, or add an existing connected agent as a worker. The Feed's team filter also opens a selected team's activity.

Turn off **Show results in feed** in a team's directory entry, or select one team in the Feed's team filter to reach the same setting. Its current and future completed cards are hidden from **Done** in **All teams**, including a project-filtered Feed. Selecting the team explicitly still shows its results. **Replies**, **Needs you**, **Working**, **Queued**, project and agent history, and saved results remain available. The preference is saved per team in its owning workspace, applies across devices, and can be turned back on at any time. An agent's work outside that team is unaffected.

**Delegation.** The manager's `loop_delegate` tool starts focused tasks for workers, which run in parallel; their updates appear in the team's feed. By default the call waits for every result. With `wait: false` the manager keeps working or finishes its turn, and each worker's result arrives later in the delegating conversation as a turn labelled **Result from @worker**, once per final state. A finished result remains deliverable if its worker is later retired or removed from the team. While the manager is working in another team conversation, results wait rather than start a second session. Cancelling the manager's task also cancels its workers' tasks and any of their results still waiting to be read; results from workers that finished but weren't delivered yet are dropped, so a cancelled manager is never restarted.

Agents can also [discover, message and hand work to one another](#agent-messaging) without a shared team. `loop_delegate` remains available only to the manager of an active team.

## Markdown agent and team definitions

Choose **Customize → From Markdown** when creating an agent, or **From Markdown** when creating a team. In **Teams → Add worker**, choose **Create worker from Markdown** to create and attach a new worker. Agent creation opens the private library on the selected connection's workspace; team and worker creation use the team's workspace. Libraries belong to their owner on that workspace and are not synced between computers. Create an example, import a `.md` file or paste Markdown, then **Save definition**. Saved definitions can be edited, downloaded or deleted there and reused with different names and connections.

Loop stores the original Markdown in `LOOP_DATA_DIR/loop.db`, under its owner's account. Keep that database in backups. Importing copies the file; Loop does not watch the original file or write to a harness's configuration directories. Existing agents retain their own settings when a definition changes or is deleted. Creating from a definition does not start work; the ordinary agent form still offers an optional initial prompt.

Agent files use YAML frontmatter followed by the instructions, like the basic [Claude Code subagent format](https://code.claude.com/docs/en/sub-agents):

```markdown
---
name: code-reviewer
description: Reviews changes for correctness and missing tests.
---

Read the relevant code, identify concrete bugs, and explain each finding
with file references. Do not edit files.
```

`kind: agent` is optional. `name` follows Loop's handle rules: 3–32 letters, numbers or hyphens, beginning with a letter; names are normalized to lowercase. `description` is optional library text (up to 1,000 characters). The nonempty Markdown body becomes the agent's instructions. Optional `model` names a model from the selected connection's catalog; omitted or `inherit` uses the model chosen in Loop. Optional `effort` must be reported by that model; otherwise choose the runtime default or a reported level before creation. If a requested model is unavailable, choose another explicitly in the creation form. Importing an agent fills an editable draft; the saved definition stays unchanged.

A team file defines one manager and one to eight workers. Each role has a unique name, instructions, and optional description, model and effort. The Markdown body is optional shared guidance, prepended to every role's instructions:

```markdown
---
kind: team
name: Feature team
description: Implement and independently review a change.
manager:
  name: feature-lead
  instructions: |
    Implement the change. Use loop_delegate to request an independent
    review, address confirmed findings, and report changes and checks.
members:
  - name: feature-reviewer
    instructions: |
      Review for correctness and missing tests. Return findings with
      file references. Leave edits to the lead.
---

Follow the project's conventions. Distinguish evidence from assumptions.
```

Choose a project and each role's name, connection and model before creating the team. Every role becomes an ordinary Loop agent, editable from its profile and usable with any supported connected harness or API provider. Creation is atomic: invalid settings, duplicate handles or a full team leave no partial agents. Retrying the same creation request returns the recorded result. Worker imports obey the existing eight-worker limit and fixed code-review-team roles.

Files are limited to 128 KB and each agent's resulting instructions to 12,000 characters, including shared team guidance. Unknown fields are rejected; Claude-specific `tools`, `disallowedTools`, hooks, permissions, skills and MCP declarations are not translated. Configure tools and permissions in Loop and the selected harness. YAML aliases, custom tags and references to other files are not supported. Use one self-contained team file, or import worker files individually into an existing team.

The authenticated API exposes `GET /api/agent-definitions` for summaries and `GET /api/agent-definitions/:id` for a file and its parsed definition. Save with `PUT /api/agent-definitions/:id`, a client-generated UUID, and `{markdown, version}`: use version `0` for a new definition and the returned version for later edits. Delete with `DELETE` and `{version}`. Stale edits and deletes return 409. Creation uses `POST /api/agent-definitions/:id/create` with `{version, selection: {connectionId, model}, idempotencyKey}`; optional `folderId`, `name`, `teamId` (agent files only), and `roles` keyed by the file's original role names select the destination and override names, connections, models or effort. An explicit role model overrides the file's model; otherwise the file's model precedes the default selection. Omit a worker's `folderId` to inherit its team's project, or pass `null` for Workspace. The definition version is checked before creation; a previously recorded retry remains retrievable after the definition changes or is deleted.

## Agent messaging

Ordinary agent runs have `loop_agents`, `loop_message`, `loop_message_status` and `loop_handoff` through the shared API/native tool layer ([agent-mail.ts](../src/server/agent-mail.ts)). `loop_agents` searches and paginates the current owner's non-retired agents on this Loop server, returning stable IDs, names, runtime and availability. It does not reveal instruction prompts or connection secrets. Another execution machine behind this server is eligible; another server shown in the unified Feed is a separate source and cannot receive this mail. Disconnected recipients can have accepted mail waiting. Retired agents, unsupported connections and snapshot review targets are refused; review runs keep their restricted tool catalog.

`loop_message` takes a recipient `to` agent ID and a body of up to 12,000 characters. With no `scope`, a recipient on the sender's active team gets the existing team routing; otherwise the message starts a **direct** thread. Explicit `scope: "direct"` also works between teammates. Explicit `scope: "team"` requires active team membership. Replies pass `threadId`, use its stored scope and reject conflicting scope or target arguments. Sending to oneself is invalid.

Recipient status tools hide unread message subjects and previews while still reporting delivery state. Senders can inspect their own mail; the owner's Agent mail view retains its full history.

A direct thread has two fixed participants and default conversation bindings. The sender is bound to the conversation that started it. Optional `conversationId` selects an eligible recipient conversation; otherwise ordinary delivery creates a dedicated conversation using the recipient's own project and connection, without assigning it to a team. Ordinary replies return to those bindings even when either agent works elsewhere. Sending from another conversation does not replace a binding. An unusable destination fails visibly; start a new thread to contact the agent again. Removing team membership or deleting a team does not invalidate an independent direct thread. Team threads keep their membership rules and prefer the recipient's active team conversation, then the remembered thread/delegation conversation or the manager's team thread, otherwise a new team conversation.

For direct messages, `interrupt: true` automatically selects the recipient's most recent running conversation, including when replying with `threadId`. An explicit `conversationId` takes precedence and may select a different destination for an interrupt in an existing thread. If no task is running, normal routing applies. Loop records the selected destination when accepting the message; retries and release from held or pending delivery keep it even if another task starts. The first delivery establishes the recipient's default binding, including when an interrupt starts the thread in an existing user or team conversation. Later interrupts do not replace that binding for ordinary replies. Conversation eligibility checks still apply: an unusable stored binding or selected destination fails visibly instead of selecting another task.

Mail queues behind work in its destination. The worker also prevents mail from starting a competing execution when that agent is busy in another conversation, including paused work or work awaiting approval. Ordinary native user conversations can still run concurrently, and mail that has not started does not block them in unrelated conversations. `interrupt: true` steers only a live run in the selected conversation when its actual runtime takes live input: API/subscription, Codex, Claude Code, Pi and Muse Code. OpenCode, Gemini CLI, Grok Build and ACP queue instead. A manager waiting on blocking delegation is never interrupted. Agents cannot wait synchronously for answers inside a mail call: they should finish their turn so the reply can start the next one.

Acceptance is durable, not proof of reading. **Waiting for recipient availability** means accepted but not yet submitted, for example during disconnection or queue pressure; **Queued** means a recipient turn exists. Recovery retries only undispatched mail or steering definitively never read. An uncertain delivery stays **Delivery unconfirmed, not resent**. Cancelling the recipient turn prevents recovery from recreating it. Refused mail and mail from queued, paused, cancelled, failed or interrupted turns remain in owner-visible history but do not grant later model context, memory or attachment access. If a queued turn's provider is removed, or disconnected and replaced on the agent, delivery fails visibly without switching providers. Direct mail creates no delegation relationship. Delegated results retain their manager cancellation rules.

`loop_handoff` carries a next task, context summary, workspace reference and published files and requests an acknowledgement in the thread. It does not transfer native sessions, stop the sender, grant manager capabilities or give user approval. Messages appear as **Message from @agent** in conversations and the Feed, explicitly granting no additional authority. Up to 8 files may be included, restricted to files the sender published or can read through attachments to its current conversation; recipients read them with `loop_read_file`. Owning a file alone does not authorize an agent to forward it. Different runtimes need published/attached files, not assumptions about shared paths. Recipient turns use the recipient's own connection and its subscription limits or API billing; there is no provider or billing fallback.

One run can send 8 messages. A thread pauses after 30 messages, or when a pair reaches 20 messages in an hour across direct and team threads in this owner/source. A paused thread can hold 30 further messages. The workspace can also retain up to 100 accepted, undispatched messages; excess sends are refused explicitly. From an agent profile, **Agent mail** shows direct and team threads, participants, previews, delivery state and available destination links. **Messages** still shows assistant output history. The existing **Team messages** entry filters the same controls to a team. **Resume** releases held messages in order and renews the allowance; a temporary obstruction re-pauses before the blocked message and reports how many were released, refused or remain held. Automatic recovery never releases held messages.

## MCP tools

In Settings → Tools & integrations, choose a catalog integration or add a custom server. Paste `mcpServers` JSON for command or hosted configurations; complete any required OAuth or credential setup. Installation succeeds only after discovery. Catalog definitions are maintained in [catalog-data.ts](../src/server/mcp/catalog-data.ts), not fetched as executable instructions at runtime.

Connections are workspace-wide for that owner, including future agents and teams; other users do not inherit them. Agent-requested installation requires approval. Connected calls follow the workspace approval preference, with ownership, schema, discovered-tool and run-state checks at dispatch. A read-only annotation does not itself grant authorization. Native shell, file and other harness tools follow a separate owner-wide preference, **Settings → Permissions → Agent tool calls** ([permission-modes.ts](../src/shared/permission-modes.ts)), sent with each run. **Never ask** starts Claude Code sessions in `bypassPermissions`. For the other harnesses on your computers, Loop answers each tool approval with the harness's one-call allow choice (Codex `accept`, OpenCode `once`, ACP `allow_once`). Codex MCP tool confirmations, including team delegation, also use this one-call approval path; their cards show the request and tool arguments, with native protocol details collapsed. Questions, MCP forms requiring input, URL flows and Pi confirmations still wait for you. **Auto-accept file edits** applies only to Claude Code. A change applies from the agent's next turn; a Claude session restarts to change its launch mode, and requests already waiting keep asking. A permission mode chosen for one session in **Session settings** outranks this preference for that session: Loop answers for you only when that session's own mode is `bypassPermissions`.  Native approval cards also offer **Fewer approval prompts**, linking to this preference and to the harness's **Session settings** (when it supports permission controls). Allowing connected MCP tools does not change native shell/file permissions, and agent tool calls do not change MCP approvals. Disabling a connection blocks subsequent calls but cannot undo an already dispatched effect. Unknown outcomes are not automatically retried.

Hosted connections use validated network destinations. Private runtime origins require explicit operator configuration. Command MCPs run locally in companion mode and through runtime infrastructure in server mode.

**Provider-key runs and tool search:** Agents running on an OpenAI or Anthropic API key receive connected MCP tools as deferred definitions behind the provider's tool search ([providers.ts](../src/server/providers.ts)). Loop's own tools stay in the model's context. On Anthropic, a deferred tool's definition enters the context only after the model searches for it; the BM25 tool search tool is used on Claude 4.5 and later (including the 4.6 to 4.8 and 5.x families, Fable and Mythos), and older or unrecognized Claude models keep the full catalog loaded. On OpenAI, `tool_search` applies to `gpt-5.4` and later; OpenAI's deferral keeps each function's name and description visible and defers only its parameter schema until search, so the saving there is schema size, not catalog size. Older OpenAI models keep the full catalog loaded. When a turn called a tool, searched for tools or paused, the provider's complete ordered assistant content (thinking or encrypted reasoning, text, search call, search result and tool-use blocks or items, in the order returned) is stored with the run's checkpoint and replayed unchanged on the following rounds, so signed thinking stays intact and a discovered tool stays available for the rest of the run; Loop never executes the search blocks, normalizes OpenAI items through the SDK before replay, and bounds the stored content at 256 KB per turn. If Anthropic pauses its server-side loop (`pause_turn`), Loop replays that content as the last message and requests again, at most eight times per run; the paused turns are recorded in the checkpoint so the cap survives approvals, recovery and resumes. Each tool's description carries the server and original tool names because the published name is a hash. Forced projection tools are never deferred. Harness sessions receive the full catalog from the tool bridge and apply their own deferral, if any; the 120-tool catalog budget still applies to both paths.

**Sharing between Loop sources:** A Docker runner attached to one Loop workspace already uses that workspace's MCP catalog. An older, independent Docker Loop server owns a separate catalog and credentials. In **Tools & integrations → Installed**, press **Share tools** beside a discovered, loopback-published Docker source to connect the two catalogs. The paired laptop contacts only that verified local Docker source. Docker-owned MCPs remain on Docker and laptop-owned MCPs remain on the laptop; the browser receives neither provider credentials nor relay tokens. Docker requests for laptop tools wait in a durable queue that the laptop polls through Docker's loopback API, so the laptop opens no network listener. The laptop claims each queued call just before running it, so a call Docker has already reported as uncertain (timed out, cancelled or disconnected) is never run. Each side records call identities before external effects, and uncertain outcomes are never replayed; a call that could not connect sends nothing and stays retryable. New catalog entries refresh within about a minute; if Docker's catalog would exceed the tool budget, the previous catalog stays shared; already running harness sessions may need a new turn or reconnection to list new tools. **Stop sharing**, beside the source or on its shared connection, revokes the relay token and disables both proxy connections; if Docker is offline, the laptop keeps the remote revocation pending until it reconnects. Setup routes accept only local requests from the laptop's source adapter, never through the paired-browser proxy. The Docker server needs a Loop version with the federation routes. Other remote hosts need their own securely enrolled source adapter.

**Importing harness-installed MCPs:** On a personal Loop (companion or single-user), **Installed → Import from installed harnesses** lists server names found in Codex's JSON CLI catalog, Claude's standard `mcpServers` files, OpenCode's global JSON configuration, and Pi's common `mcp.json` adapter file. The browser receives names and transport kinds only. Choosing **Import** copies that server's configuration into the same source's encrypted Loop store, then discovers its tools. OAuth accounts and unsupported native transports may still need reconnecting in Loop. Custom Pi extensions and other harness-specific stores are not inspected. The existing **Paste MCP JSON configuration** form handles configurations these readers do not recognize. Once imported, a server follows the same owner-scoped catalog and can be shared with a connected Docker source. Native provider homes remain owned by their harnesses. A multi-user server never lists or imports its own harness configurations.

Charts save numeric data and provenance as snapshots; refresh is a new tool operation. Mermaid diagrams use the native renderer. Loop does not advertise MCP Apps support or fetch interactive app resources. Tools use ordinary text/structured results and Loop's normal approval flow. If a server still returns a form-required error, it remains a failed tool result; Loop does not claim success or replay the operation. Previously saved app artifacts retain their isolated viewer. These displays do not bypass the tool broker.

### GitHub pull requests

With the official GitHub integration connected (`api.githubcopilot.com/mcp`), the **Pull requests** tab lists your open pull requests across GitHub without involving an agent ([github-pulls.ts](../src/server/github-pulls.ts)). The server reads GitHub with that connection's token, which never reaches the browser or an agent. Filters show **Review requested**, **Yours** and **Involving you**, each with its count, plus each pull request's checks and review state. The search box filters by text, narrows the list to a repository when you type `owner/repo`, and opens any pull request when you paste its link. The list shows the 50 most recently updated. Opening a pull request shows its description, checks, the latest 50 submitted reviews, review threads, comments and the changed files with their diffs. The **Commits** tab shows the latest 100 commits with their authors and dates; expanding one reads its message and file diffs for that exact commit, with links to GitHub. Each commit shows up to 300 changed files; omitted or shortened diffs link to GitHub. Longer histories link to the full list. GitHub's HTML comments are hidden and other HTML shows as plain text. **View file** shows a changed file at the commit being viewed (the head commit in Files), including images and other binary files GitHub shows no diff for. Markdown is rendered like GitHub renders it (**Code** shows the source); its HTML is sanitized, relative images and video load from the same commit, and links to other repository files open in the viewer. External images are shown as links and never loaded. Images and video play inline, and other files show as text with line numbers. Files are served only as images, video, plain text or downloads, never as pages. Each person's copy of a file is kept for a day, and files over 50 MB stay on GitHub. Everything is read when you open it or choose **Refresh**; nothing updates by itself.

From a pull request you can act as your GitHub account. Each action is one request you submit, and Loop never retries it:

- **Review**: approve, request changes or comment. Loop rereads the head first and refuses if commits arrived since you opened the pull request.
- **Comment**: posts to the conversation.
- **Merge…**: shown with repository write access. It lists the target, head commit, checks, review state and anything GitHub reports as blocking, then merges with the method you choose, pinned to that head commit. If anything was pushed since, GitHub refuses and you refresh first.

GitHub's own branch rules still apply to every merge. With more than one GitHub connection, these actions are refused rather than picking an account. **Ask an agent** starts a message with the pull request's link, after any draft you have, and sends nothing until you do. **Open in Pull requests** on a PR card in a thread opens that pull request here.

In a conversation, agents work on pull requests too. Paste a pull request link or ask for open PRs: results from `pull_request_read`, `list_pull_requests` and `search_pull_requests` appear as PR cards showing the repository, number, title, state (draft, open, merged or closed), author, branch, head commit, size, merge status and requested reviewers, with a link to GitHub and the time GitHub was read. A card is a snapshot; ask the agent to refresh it. Other GitHub results (diffs, files, comments, checks) keep the plain tool output. Other servers' results never render as PR cards, whatever their tool names.

API-provider agents with GitHub tools receive guidance on Loop's rules, plus the `owner/repo#number` references parsed from the latest message. Only the parsed references are added, never the surrounding text. Pull request titles, descriptions, comments, diffs and repository files are untrusted content, not instructions or authorization. Native harnesses keep their own context; the broker rules below still apply to their calls.

An agent's GitHub writes (comments, reviews, edits, pushes, merges) follow the workspace MCP approval preference. With tool approvals set to **Allow**, an agent can carry out a merge authorized in your prompt without an extra confirmation; **Ask** shows the target pull request and action for approval. Switching to Allow also releases pending MCP merge requests on active runs. Loop refuses a `merge_pull_request` call without a full 40-character `expectedHeadSha` before requesting approval, so nothing is sent. Permission applies only to that head commit: if new commits arrive, GitHub rejects the merge and the agent must review them and re-check your merge conditions before making a new request under the same policy. Code changes use Git in the agent's workspace; see [harnesses](harnesses.md).

Loop watches agent-created PRs by default across Codex, Claude Code, Pi, OpenCode and ACP, without a separate watch setting ([pr-watches.ts](../src/server/pr-watches.ts)). With GitHub connected, a successful `create_pull_request` tool call or `gh pr create` command starts a watch in the originating agent's thread. Direct native and server subscription execution share this behavior. Command detection requires a confirmed successful result with command input and output, tied to the owning run and current session generation; unlinked terminal history, failed commands and truncated results do not start watches. Literal shell wrappers and a preceding `cd directory &&` are supported. A PR merely read or linked in a thread does not start a watch. About once a minute the worker reads the pull request with your GitHub connection's token, which stays on the server. When something new arrives, it queues one follow-up in the thread, labelled **GitHub update**, behind the agent's current work. A follow-up never steers a running task. New items include:

- CI failing on the latest commit, once every check run and every check suite with runs has finished.
- CI turning green after a failure. A first green result is only recorded.
- Reviews, review comments and comments posted since the PR was created. A review counts from when it is submitted, not when its draft was started. Comments from the connected GitHub account (the agent's own) are skipped.

Only accounts with a role in the repository (owner, member or collaborator) are quoted, bots included: any GitHub App can comment as a bot, so a bot account alone does not show the repository trusts it. Comments from anyone else are counted in an update but never quoted, and never start a turn on their own. Quoted comment text is marked as untrusted. Updates wait while the agent is still on the previous one and are then sent together. Each follow-up's idempotency key comes from what it reports (the CI result and the items it covers), and delivered items are tracked by id, so a restart cannot send the same update twice. The Feed labels these follow-ups **GitHub update** too. The agent's pushes, comments and merges still follow the approval preference, and the follow-up tells it never to merge on its own.

Watching stops when the pull request is merged or closed, or when you choose **Stop watching**. It pauses after 5 follow-ups in an hour, so an agent cannot loop on its own pushes, and when GitHub rejects the connection. Nothing is lost while paused; **Resume** continues from where it stopped. One thread watches a pull request at a time. CI results come from GitHub check runs; legacy commit statuses are not read.

## Workflows

The editor uses the bounded JSON `loop.workflow/v1` format implemented in [server/workflows](../src/server/workflows). A workflow defines inputs, agent roles, sequential agent/approval/save steps, outputs and limits. References may use named inputs or earlier steps; forward references and invalid schemas are rejected. Saved versions and runs retain their selected connection/settings snapshots.

Run a saved version with inputs, review required approval steps and inspect linked child conversations/results. Checkpoints prevent duplicate child submission after restart. Cancellation propagates to the active child. Human approval waits do not occupy a worker slot. Workflow step/time limits apply to native execution, but native internal model calls and token use are not exactly enforceable. The format does not execute arbitrary embedded shell/code.

## Social feeds

Social is a reader for public feeds, under **Your profile → Social**. Its catalog is checked in at [news.ts](../src/shared/news.ts): each entry was read with the shared parser before it was listed, so Social fetches only addresses in that list, and only redirects within a feed's own site. [syndication.ts](../src/server/syndication.ts) reads RSS 2.0 and 0.9x, RSS 1.0 (RDF), Atom and JSON Feed into one kind of card, and adds what a few sites carry beyond the formats: Hacker News points, a Reddit post's linked article and subreddit. Reddit itself is not in the catalog — its logged-out RSS answers 429 and `old.reddit.com` redirects feeds to a sign-in page. Run `npm run feeds:check` to read the whole catalog over the network.

**Feed options.** Search, the Unread and per-feed filters, **Mark all read**, **Follow a word**, **Digest** and **Add feeds** sit in one Feed options card above the stories. It starts closed on every visit, showing how many feeds you follow and how many stories are unread (or that a filter is on); closed, the stories follow the compact options row.

**What is shared and what is yours.** A feed's contents are the same for everyone who added it, so stories are stored once in `feed_stories` with that feed's fetch health in `feed_state`. What is yours stays owner-scoped: which feeds you follow, what you have read, what you saved, your watches and your digests. Stories are shown to you, and reach an agent only through the opt-in tool below.

**Your own feeds.** Beyond the catalog you can add any public feed by address, or paste a site's address and pick from the feeds that page advertises; OPML import brings another reader's list in and export takes it out. A typed address has no warrant, so [feed-sources.ts](../src/server/feed-sources.ts) validates it before Loop ever requests it — public HTTPS, no credentials, never an address on this network — and the request goes through the same transport as a catalog feed, which resolves DNS through a public-only dispatcher, refuses any host answering on a private address, follows redirects only within the feed's own site, and reports a feed that redirects to a sign-in page as needing an account. Feeds needing a token or cookie are not supported.

**Freshness.** The worker reads each followed feed about every five minutes, so opening Social is served from the store rather than the network and stays current with the tab closed. It sends `If-None-Match`/`If-Modified-Since`, so a feed that has not changed answers 304 and sends nothing. A feed that fails is retried on a widening delay — two minutes doubling to an hour, or longer if it asked — and its last good stories keep showing meanwhile. A request returns the feeds it already has and names the rest in `pending`, so a page is never held up by its slowest feed; pulling the page down refreshes the feeds themselves, down to a thirty-second floor. Reading stops once a feed has the stories Loop keeps, so a full-text feed is not downloaded whole. Each feed keeps its newest 120 stories — plus any you saved — and the stories of a feed nobody follows are dropped a month later.

**Reading.** A story is read when you open it, open its discussion, ask an agent about it, or mark it; "mark all read" is a watermark rather than a row per story. The Social chip carries the unread count. A story can be saved to Later beside a conversation, a result and a message, and comes back at a time. Searching reaches the whole store rather than the page, so a story from last week is still findable; words you mute are hidden from the list, counted, and shown again on request. Pictures a feed offers are off until you turn them on, and when they are on Loop fetches them itself rather than letting the browser do it: the page's own policy allows no third-party images, and a picture loaded from the publisher would tell that site who is reading. Only the address stored on a story of a feed you follow is fetched, only real raster images are passed through (never SVG, which can carry script), and they are capped at 5 MB.

**Agents and digests.** An agent can read your feeds only through `loop_feed`, and only once you turn agent access on — off by default, because a tool that lists your feed puts what you follow into a model's context. It reads the store: it fetches nothing, marks nothing read, and never sees a feed you do not follow. A digest is scheduled per agent at a clock time in your own zone: Loop collects what arrived, asks the agent to summarize it, and sends it once a day, labelled **Feed digest** rather than as something you typed. Comparing local days means a daylight-saving change keeps the same clock time and a server that was off for a day sends one digest, not five.

**The worker's pass.** One job: read the feeds that are due, then — once those reads have settled — send any due digest and look for watch matches in what the pass brought in. Running the three in order is what makes a digest cover today's stories rather than yesterday's, and it is one tracked job, so a shutdown waits for all of it.

**Following a word.** A watch matches whole words against stories that arrive — so "ai" finds "AI safety" and not "said" — over the feeds you follow, and never causes a fetch. The first match for a story notifies your phone once; a watch is capped at three notifications an hour and an owner at ten, after which the rest are recorded and summarized in one line. Tapping a notification opens Social on that story. The add form previews what a watch would have caught before you create it.

## Browser and offline behavior

The web app can be installed from an HTTPS origin using the browser's home-screen/app installation flow. A Quick Tunnel origin can change; run `loop pair` and add the new page to your home screen.

The service worker caches public shell assets, not private API responses or credentials. Offline relaunch shows reconnect UI; messages are not queued on the device while offline (scheduled sends are stored on the server). The **Open on another device** option in a thread shows a QR code and link for continuing on your computer or phone; the link carries no credentials. Share links create a draft for review rather than silently submitting work. See [pairing](pairing.md) for device access and reconnection.
