# Architecture

Loop has one React UI, workspace API and SQLite migration set. The companion workspace uses device pairing and a local host-owned worker. It runs directly on the host or in the Docker companion.

This page is the source map and core boundaries. Detailed topics have their own pages: [execution paths](execution.md), [workspace updates](workspace-updates.md) and [fleet architecture](fleet-architecture.md).

## Saved rows

[Typed readers](../src/server/row-schemas.ts) validate persisted execution payloads and JSON metadata once, preserving owner predicates. Team setup, saved agent definitions, workspace content and continuation routes, artifact filing and PR-watch registration use the [owner-scoped readers](../src/server/domain.ts) before changing configuration or organization. The generic ownership guard returns `unknown`; execution uses one parsed `Run` and the [legal state map](../src/shared/run-state.ts). New records and update patches are strict; subscription status refresh preserves existing validated metadata while validating its new status fields. Saved execution payloads reject unknown fields. Metadata readers retain additional fields used by imported content while rejecting malformed identity, routing, permission and credential fields. Model catalog entries are strict; only an absent model display name defaults to its ID. Execution projects known fields into new output, leaving the saved historical payload intact. Invalid records fail closed with their row ID; malformed team configuration also remains unavailable for deletion and filtering. Artifact responses retain serialized metadata; continuation copies validate selected messages before creating a conversation and preserve historical extras inside their original metadata. Folder ancestry is validated when changing the parent; renames do not depend on unrelated ancestor display fields. Import cancellation checks ownership and scalar run identities without interpreting execution payloads or damaged import display fields; starting an import still validates its record.

Cancellation, dismissal, approval rejection, revocation and native interruption use owner-checked control fields without executing or repairing an invalid payload. Resuming or retrying saved work still requires its full validated row. A new turn validates only the prior folder and review identity it carries forward, then builds a fresh snapshot from the current agent and connection; invalid carried identities remain unavailable. Subscription logout validates owner, provider and routing separately from unused catalog, display and provider-secret fields. Explicit disconnect clears recovery markers in valid metadata even when routing is invalid, so startup cannot reconnect it. Teammate listings mark each damaged connection unavailable without blocking healthy peers. Background-result delivery reads owner-checked sender identities and outcome fields without executing its payload; uncertain sender locations are labelled unverified, while recipients still validate fresh execution data. Worker failures can end only the lease they still own; unleased malformed queue entries are rejected before dispatch. Public projections retain serialized JSON and never expose credential rows.

The shared [message metadata](../src/shared/message-metadata.ts), [run payload](../src/shared/run-payload.ts) and [artifact metadata](../src/shared/artifact-metadata.ts) modules own their columns' schemas and JSON codecs. The [JSON-column boundary check](../test/json-column-boundaries.test.ts), included in `npm run check`, validates literal SQL paths against those schemas and rejects direct codecs on column-named values outside their owners or named file exemptions. It resolves locally composed constant SQL and query aliases, including correlated subqueries; runtime/imported SQL builders, computed paths and arbitrary JavaScript renaming remain outside this syntactic check. The [closed-field check](../test/discriminating-fields.test.ts) covers these shared schemas, including message delivery.

## Published Results

A [Result](../src/shared/result.ts) is the immutable record of a published answer: run answers, explicit steering replies, imported answers and fork or continuation copies. [Publication](../src/server/result-publication.ts) seals its stimulus, outcome, attachments, provenance and lineage with a content digest; republishing identical facts is idempotent and a conflicting reuse of the identity is refused. Provenance records the producing agent, provider and model and, from schema version 2, the answer's `origin`: produced by a run, an external import, a copy that names the root original Result it came from, or unknown. A copy keeps its source's author rather than the receiving agent's; a missing or another owner's source is recorded as an unavailable copy with unknown authorship. Version 1 records keep their original digest serialization and record no origin.

[Result attachments](../src/server/result-attachments.ts) are uploads, whose objects are never rewritten, or published files, whose content-addressed objects are insert-only; message attachments cannot reference live text artifacts. A Result seals the object or published checksum it attached. Card preview and download both resolve those bytes under the owner's current artifact access; when they can no longer be identified, including a published reference without a checksum, the attachment is `unavailable` and only an explicit action opens the current artifact.

Done result cards and Replies enumerate sealed Results only; Saved shows a saved published answer's sealed Result. Result cards are projections rebuilt from those Results with mutable overlays (reads, dismissals, Trails, saves); raw transcripts decide neither which answers are published nor what they say. Eligibility is the rule Done always used: assistant output that is not a progress update and is not blank. Done is attributed to the sealed author, while folder filters and moves follow current organization: the folder the run recorded, otherwise the conversation's current folder. A card whose recorded publication project differs from its current one shows `produced_in`. Idle-thread, Working, Queued and approval cards remain operational state. Upgrades seal answers earlier builds listed without a Result, then rebuild result cards.

An imported answer's stimulus is the nearest question on its own export branch: parent pointers name provider node IDs, and one dropped node, such as a tool call, is bridged through its stored parent's children. Formats without parent pointers are linear and use the latest earlier question. A branch that cannot be followed (a missing node, a cycle or consecutive dropped nodes) has an unknown stimulus rather than another branch's question. Lineage `parentResultId` is the chronological predecessor, independent of stimulus and supplied context: the latest Result of any kind, sealed before this one, whose creation time is not later. Earlier history imported later therefore starts its own link, and sealed successors keep theirs.

[Result history](../src/server/result-history.ts) runs one-time passes inside the migration transaction. Upgrades from releases without Results seal standalone, imported and copied answers with the live publication policy, marking them `migrated_backfill` with an unknown publication placement. Databases whose Results were sealed by earlier builds are checked against retained evidence instead; disagreements — copies attributed to the receiving agent, imported answers sealed with another branch's question, and imported answers chained past an intervening Result — become append-only `result_defects` findings beside the untouched original record and digest. No pass invokes a provider, reruns work or replays an external effect.

## Workspace HTTP contracts

The [workspace contracts](../src/shared/workspace-api.ts) describe the public bootstrap, agent, connection, message, personal, Feed, Later, saved, scheduled-send, conversation, run, Results, folder, artifact, upload, search, preference, import, approval, native-decision and session-control endpoints. The [registrar](../src/server/registrar.ts) keeps each Express router private and exposes only its mount handler. Contracts are the only registration path; [Contract rules](contracts.md) defines the authoring rules. Contract handlers validate inputs through the existing error middleware and validate and project JSON responses. Undeclared response fields are removed; invalid output produces an unavailable-response error without exposing its contents. Attachment routes use `kind: "stream"`: inputs are validated, the existing response writer is preserved, and typed browser helpers return a Blob. Browser file links use `routeUrl`; previews that need attachment headers use the stream-only `fetchStream` helper. Binary redirects are accepted by the Blob reader only when the final response stays on the same origin and workspace API source. Multipart routes declare `multipart: true`: the body schema describes text fields, and the typed client sends one Blob part named `file` without setting a JSON content type. Existing upload middleware still owns size limits and runs before contract validation. Query arrays retain repeated keys. Authorization stays with the paired-device admission and owner-scoped handlers. App-level registrars defer automatic `OPTIONS` responses to the enclosing admission and fallback chain; existing child routers keep their method responses. Feed, conversation and Results handlers remain synchronous inside their existing snapshot transaction so their bodies and watermarks describe the same committed state.

These schemas describe wire data independently of storage rows. Existing JSON columns remain serialized and nullable joins stay nullable. Every response requires fields emitted by all current producers; optional fields represent current conditional metadata, never implied capabilities. A missing Feed pull status remains unknown, distinct from an explicit null meaning no watch. A public run state may include presentation values such as `waiting_children`; reading it does not authorize execution. Session controls share a public catalog schema with the execution boundary, without exposing its private operations or credential contracts. The [client helpers](../src/client/workspace-api.ts) infer request and response types, preserve source-bound transport and read cancellation, and never retry writes automatically. The exported transport helpers accept only contracts. Local input-validation failures are definite refusals with readable messages; a malformed acknowledgement remains uncertain.

The single [workspace registry](../src/shared/workspace-api.ts) defines workspace and Cards contracts and generates [OpenAPI](openapi.json) plus its [event-channel companion](openapi-channels.json), checked by `npm run openapi:check`; integration bearer access follows each mounted contract’s `{ admits }` values at both the server and paired host, as described in the [Integration API](cards-api.md). Transports, peer and fleet routes refuse integration bearers; read grants admit only declared read contracts. `status` and `additionalStatuses` document existing response statuses without changing handler status selection; scheduled-send creation uses 201 for a new row and 200 for an idempotent replay, while health reports its structured readiness response at 200 or 503.

Application discovery, health, build identity, diagnostic runs and HTTP event polling use the same contracts. The event fallback retains its array of owner-scoped rows and serialized payload text. Automatic snapshot reads that exhaust transient server retries or fail on a network error register recovery interest for their source and owner generation. The shared watcher probes HTTP while that interest exists, even with a connected socket; a successful empty poll invalidates the failed source too.
Recovery interest is tracked per request path within each view signal: a successful read clears that path without clearing another failed read, and only the newest overlapping request may settle its interest. Cancellation drops the view’s interest, owner changes discard it, and successful recovery returns to push-only operation. Permanent refusals and writes do not register recovery. Recovery invalidates the whole source because the shared reader does not own collection subscription identities. Persistent failures therefore cause repeated refreshes of healthy collections too.
Requests retain their bounded transient-error delays and source notifications are throttled, but recovery cycles have no increasing backoff or terminal retry cap: a cap could leave a quiet failed view stale indefinitely. Readers outside the collection hook, including Approvals, still cancel on each relevant signal and can delay a slow response under sustained invalidation. Ordinary socket frames leave recovery probes running; resets and socket readiness still cancel obsolete fallback probes.
Collection reads coalesce automatic invalidations received during a pending request into one trailing refresh, so repeated recovery cannot starve a slow healthy read; selection changes, unmounts and explicit retries retain cancellation. A contract declaring `kind: "transport"` hands its protocol handler raw requests, including validation, errors and streaming; no workspace route currently does. The paired host authorizes devices, origins and CSRF before forwarding, and the app serves the paired owner. The session GET projects only the shell's user id/name and the `paired` mode.

## Activities

Plans, tool lifecycle, diffs, command output, settings and command catalogs share [agent-activities.ts](../src/shared/agent-activities.ts). [server/activities.ts](../src/server/activities.ts) validates and persists trusted owner/conversation/run scope and serves paginated projections. [activity-bridge.ts](../src/activity-bridge.ts) supplies the shared mapping for native activity projections and historical records.

The client uses [activityView.ts](../src/client/activityView.ts) to accumulate full snapshot pages and apply incremental updates. Native tool items and MCP calls persist durable activities when they arrive; activity reads do not synthesize records from execution traces. Conversation transcripts show human messages and public agent output, including progress updates. Tool calls, raw native events and activity records stay out of the transcript, except native failure and uncertain-delivery notices. Tool calls, command output and plan progress are available from the conversation's **Tool activity** option; saved tool traces are in the agent profile’s Traces tab. Session settings stay in **Session settings**. A link to a hidden row opens the conversation where that row was. Activities are display data: Loop never applies a reported diff or uses these records as native model context.

[Conversation transcripts](../src/server/conversation-messages.ts) page through an indexed display projection whose ordering keys are maintained in the same transaction as messages. Public assistant updates live in the message store with idempotent per-run producer keys; transcripts, reply quotes and reading positions do not read execution traces. Migration 073 copies older public updates into messages while preserving their IDs and ordering cursors. Message sequences remain stable through deletion and database compaction.
A run's updates group under its prompt, or under the run's first stored message when imported or replayed history has none. The page is selected before loading its content and current run/delivery state. Opening a thread loads confirmed session controls. File summaries load separately as their messages come into view; file contents download when opened. Opening **Tool activity** loads its recent activity snapshot; **Load earlier activity** requests older durable records, and is offered only while older records that view can show remain.
File-change records are loaded for runs in the displayed transcript so older result chips retain their file reviews. Memory source and native-history detail selections use scoped queries. Memory editing keeps a separate draft and its revision while read snapshots refresh; changing owner/source resets that view’s drafts. A note-save acknowledgement closes only its original selection and reconciles a reselected target. Closing Memory Used cancels its receipt read and any cooldown wait.
Social watch and digest settings use separate shared snapshot queries for watches, digests and feed-access preferences; a failed read retains its own notice and retry without hiding the other snapshots. Their forms reset with the owner session, and closing the sheet cancels reads and cooldowns. The main Social snapshot keeps its owner cache and optimistic story updates while the shared executor coalesces notifications into one trailing read. Filter changes, dismissals and post-mutation reconciliation supersede obsolete snapshots; the explicit refresh still asks the feeds for new items.
Search keeps its 200 ms input debounce with a separate query-scoped executor and read notice. Pull-request inbox and detail reads use the shared executor; the connected inbox snapshot remains in the owner cache with its source and filter key, so returning from a detail view can reuse it. File and commit reads include the pull identity and requested SHA, and commit responses must match that SHA before display. A file query error alone does not replace its matching-head cached diffs or their open file sheets; the read notice appears alongside them.
The existing parent-refresh policy is separate: a successful detail read with a new fetchedAt replaces the file-list scope and closes its sheet even if the head SHA is unchanged. File-query retention does not span that successful parent refresh. Immutable commit diffs use one-shot shared execution and retain their loaded data instead of subscribing to metadata refreshes. Expanded commit rows keep the commit SHA as their identity across background detail refreshes; a fetch timestamp does not reset that interaction.
Successful explicit refresh and post-command reconciliation invalidate the loaded commit views. Thread watch queries are idle without a conversation, clear obsolete scope data and expose read failures separately from watch commands. Native-history fork receipts and command identities remain separate from preview reads.

Activity history and live-update cursors are independent. [ActivityHistory](../src/client/activityHistory.ts) uses the shared read executor for each page’s I/O, cancellation and owner-generation publication checks. Its domain queue still serializes recent, update, earlier and displayed-run file reads; refresh signals coalesce across a complete multi-page pass. Failed earlier, file and live operations keep separate retry targets, so another operation’s success cannot hide their error. Continuing live and file pages must advance their cursor; a non-advancing continuation stops with a retry notice. Closing or changing the owner/source/thread disposes its executor, including a pending Retry-After wait.

Records are bounded, versioned and keyed by producer identity. Sequence/revision checks prevent stale updates overwriting newer state; generation checks reject stale producers. Re-delivery is idempotent. Replay does not advance live tool lifecycle. Capabilities distinguish supported, unsupported and undiscovered behavior instead of fabricating results.

## Memory, tools and files

Workspace MCP connections belong to the owner and are shared by that owner's agents. Broker dispatch checks discovery, schema, ownership, connection and approval state. Command MCPs run as local subprocesses of the companion. Rich MCP Apps run in isolated iframes. See [workspace](workspace.md).

Artifact metadata is one strict schema per role (D5): the role column selects the arm the producer parses on write and the saved-row reader validates on read, and the 2b migration removed the fields no producer or reader uses. Search supports local keyword indexing in [memory.ts](../src/server/memory.ts). The worker captures changed messages and saved artifacts; SQLite triggers update the local index with each source change. Artifact content and versions remain live during streaming, but a streamed answer's search index and feed revisions keep their last snapshot until the run finishes: the artifact itself carries no partial flag (its role is declared at insert), and the churn guard follows the linked message's partial flag, so interrupted streams keep the last indexed snapshot until finalized. Results revisions likewise skip repeated partial updates. Scope, inclusion, revision and tombstone checks apply again before returning indexed candidates. Recall is untrusted historical evidence, never current authorization. Versioned notes preserve edit history.

Message attachments reach the model as file references read through `loop_read_file`. Before upload, the browser scales HEIC photos and images over 1.5 MB to at most 2048 pixels on the longest side and re-encodes them as JPEG ([imageUpload.ts](../src/client/imageUpload.ts)); GIFs, SVGs and images it cannot decode are sent unchanged. An upload error that is not Loop's JSON (a tunnel or proxy page) is shown with its HTTP status. API-key connections also receive the current turn's images and PDFs inline. Native turns receive upload references and use `loop_read_file` through the private tool bridge.

File publication validates the selected file/path, size and digest, then stores private content under the workspace data directory. Downloads require owner access. A worker path alone is not a published file. Credentials remain in encrypted server storage or their native provider homes; neither belongs in public projections.

## Dependencies and boundaries

Workspace HTTP routes are defined in [workspace-api.ts](../src/shared/workspace-api.ts) and registered only through the server [registrar](../src/server/registrar.ts), which exposes contract registration and mounting. The native paired host dispatches its device and source-management routes from the same registry, behind pairing and CSRF checks. Protocol-owned authentication and MCP transports are explicit contracts. Browser API requests use [client/workspace-api.ts](../src/client/workspace-api.ts): `callRoute` for one-shot calls, `readRoute` for cancellable reads, and contract-bound `routeUrl`/`fetchStream` for file addresses and bytes. Raw request transport stays private; pairing and CSRF bootstrap remain outside `/api`. Socket frames and paths use the registry's event channel. `npm run openapi:check` verifies the generated HTTP and event-channel documents; see [development](development.md#manual-verification) for the verification gate. Typed client commands use `CommandRouteContract`; `callRoute` rejects GET contracts before dispatch, and `useSourceRoute` exposes only commands. JSON and blob GETs use `readRoute`, with owner/source scoped workflow reads bound through `useProjectionRoute`. Migrated one-shot reads use once mode, which reports the first error including cooldowns. Manual retries wait through Retry-After without a transient 5xx retry budget; automatic snapshots also retry at most two transient 5xx failures. These policies belong to the GET transport. App-level artifact links enter the existing artifact reader directly, sharing its cancellation and notice lifecycle.

[deployment/versions.json](../deployment/versions.json) owns container provider pins. [host-control.ts](../src/host-control.ts) owns installed harness version checks. [package.json](../package.json) pins the ACP SDK. Validate each seam when updating it.

Dependencies retain their upstream licenses.

The application host is a single point of failure. Native tools are not a multi-tenant sandbox. Fixture tests establish protocol behavior, not provider availability, billing entitlement, device acceptance or deployment capacity. See [development](development.md) for verification boundaries.

Domain SQL moves into one module per primary table under `src/server/sql/`. Modules prepare statements lazily per supplied connection and parse returned rows with `parseRecord` and the canonical `QueryRecords` in [sql/rows.ts](../src/server/sql/rows.ts); partial and joined selections declare their columns beside the query. Callers retain ownership checks and transaction scopes, including `.immediate()`. The [SQL inventory](../test/sql-inventory.test.ts), run by `npm run check`, has a named file allowance that only shrinks: new files must use query modules, and a file leaves the allowance when its last direct call moves. The [column-parity check](../test/row-schema-columns.test.ts) compares every declared table record with a freshly migrated database. Migration runners, change publication and feed-projector infrastructure have explicit permanent exemptions; migrations remain point-in-time SQL.

### Recipe: add or extend a SQL table module

Canonical example: [sql/mcp-preferences.ts](../src/server/sql/mcp-preferences.ts), its caller [mcp/approval-policy.ts](../src/server/mcp/approval-policy.ts), and the route test that exercises it, [mcp-route-contracts.test.ts](../test/mcp-route-contracts.test.ts).

1. Search the generated [SQL index](sql-index.md) for the table and the function you need, and extend the module that owns the table. Only for a new primary table, start with `npm run new:sql-module -- <table>`, which writes the module in this shape and prints the remaining steps. Run `npm run sql-index` after changing a module.
2. Declare each query with `statement()` from [sql/statement.ts](../src/server/sql/statement.ts) and call it with the connection the caller supplies. Do not call `prepare` at module load or import `db` into the module.
3. Take the owner as a parameter and filter by `owner_id` in the SQL when the table has one. Do not open transactions in the module; callers keep `.immediate()` and their ownership checks.
4. Parse rows with `parseRecord` and `QueryRecords.<table>`, using `pick` or `extend` for partial and joined selections. For a new table, add its migration and `QueryRecords` entry; [row-schema-columns.test.ts](../test/row-schema-columns.test.ts) compares them.
5. Import the module as a namespace by its path from the caller (`import * as <table>Queries from "./sql/<table>.js"` in `src/server/`, `"../sql/<table>.js"` one level down) and test it through its production caller. The [SQL inventory](../test/sql-inventory.test.ts) must stay green.

If a step can't be followed, say which and why in the PR instead of working around it.
