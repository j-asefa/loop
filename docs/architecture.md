# Architecture

Loop has one React UI, workspace API and SQLite migration set, with two authorization profiles. The companion profile uses device pairing and a local host-owned worker. The server profile uses local/gateway/account access and an independently runnable worker. Runtime selection is separate from authorization profile.

## Saved rows

[Typed readers](../src/server/row-schemas.ts) validate persisted execution payloads and JSON metadata once, preserving owner predicates. Team setup, saved agent definitions, workspace content and continuation routes, artifact filing and PR-watch registration use the [owner-scoped readers](../src/server/domain.ts) before changing configuration or organization. The generic ownership guard returns `unknown`; execution uses one parsed `Run` and the [legal state map](../src/shared/run-state.ts). New records and update patches are strict; subscription status refresh preserves existing validated metadata while validating its new status fields. Reads retain unknown top-level run-payload and metadata fields but reject malformed present identity, routing, permission and credential fields. Model catalog entries are strict; only an absent model display name defaults to its ID. Execution projects known fields into new output, leaving the saved historical payload intact. Invalid records fail closed with their row ID; malformed team configuration also remains unavailable for deletion and filtering. Artifact responses retain serialized metadata; continuation copies validate selected messages before creating a conversation and preserve historical extras inside their original metadata. Folder ancestry is validated when changing the parent; renames do not depend on unrelated ancestor display fields. Import cancellation checks ownership and scalar run identities without interpreting execution payloads or damaged import display fields; starting an import still validates its record.

Cancellation, dismissal, approval rejection, revocation and native interruption use owner-checked control fields without executing or repairing an invalid payload. Resuming or retrying saved work still requires its full validated row. A new turn validates only the prior folder and review identity it carries forward, then builds a fresh snapshot from the current agent and connection; invalid carried identities remain unavailable. Subscription logout validates owner, provider and routing separately from unused catalog, display and provider-secret fields. Explicit disconnect clears recovery markers in valid metadata even when routing is invalid, so startup cannot reconnect it. Teammate listings mark each damaged connection unavailable without blocking healthy peers. Background-result delivery reads owner-checked sender identities and outcome fields without executing its payload; uncertain sender locations are labelled unverified, while recipients still validate fresh execution data. Worker failures can end only the lease they still own; unleased malformed queue entries are rejected before dispatch. Public projections retain serialized JSON and never expose credential rows.

## Workspace HTTP contracts

The [workspace contracts](../src/shared/workspace-api.ts) describe the public bootstrap, Feed, conversation, run, Results, approval, native-decision and session-control endpoints. The thin [Express helper](../src/server/route.ts) validates inputs through the existing error middleware and validates and projects JSON responses. Undeclared response fields are removed; invalid output produces an unavailable-response error without exposing its contents. Authorization stays with the existing owner/profile middleware and handlers. Feed, conversation and Results handlers remain synchronous inside their existing snapshot transaction so their bodies and watermarks describe the same committed state.

These schemas describe wire data independently of storage rows. Existing JSON columns remain serialized, optional display and handoff fields stay optional, and nullable joins stay nullable. Older linked catalogs may omit team, environment-label, identity-provider and capability additions; missing capability data grants no capability. A missing Feed pull status remains unknown, distinct from an explicit null meaning no watch. A public run state may include presentation values such as `waiting_children`; reading it does not authorize execution. Session controls share a public catalog schema with the execution boundary, without exposing its private operations or credential contracts. The [client helpers](../src/client/workspace-api.ts) infer request and response types, preserve source-bound transport and read cancellation, and never retry writes automatically. Local input-validation failures are definite refusals with readable messages; a malformed acknowledgement remains uncertain.

The workspace contracts are separate from [Cards OpenAPI](cards-api.md): these owner-session and paired-device routes include execution controls and internal UI projections, whereas the generated document publishes the Cards integration and token-management surface. Cards bearer tokens do not grant access to workspace endpoints. `cards:check` continues to check that document against the Cards schemas and routes; it does not validate these workspace contracts.

## Execution paths

### Agent sources and execution environments

An agent belongs to one owner on one Loop API source and has a connection that selects its execution environment. The paired client reads each available source's owner-scoped agent, run and Feed projections and merges the Feed by activity time. Source IDs qualify agent, conversation and run identities in the client; source-scoped writes go only to the owning API. A late response from a prior signed-in owner is discarded. Project and team filters remain scoped to their source. The source's database, credentials and dispatch identities are never copied to the companion host. Opening a conversation on another source keeps the Feed mounted. The thread binds its reads, controls, uploads and file links to that source; the shell retains its original source. Drafts and pending send receipts include the owner, source and conversation, and late responses cannot overwrite the newly opened thread. Source failures appear in the thread with a retry action.

[agent-sources.ts](../src/agent-sources.ts) maps opaque source IDs to adapters. Its current Docker adapter discovers only local loopback-published single-user Loop containers and forwards paired requests once. Unknown IDs cannot nominate a network destination. [MCP Docker sharing](../src/mcp-docker-sharing.ts) separately enrolls a discovered source after an explicit paired-device action. Source-owned tools are exposed through a token-scoped MCP endpoint or a reverse queue polled by the laptop; no companion API is bound beyond loopback for sharing. The calling broker applies its owner's approval preference; the owning source rechecks its tool catalog and schema. Both sides persist call identities and uncertain outcomes rather than replaying effects. Other Loop hosts need an adapter with secure discovery/enrollment and owner authorization; remote runtime hosts connected to a Loop source are accessed through that source. The client uses the same source-keyed Feed and **Run on** form regardless of adapter kind.

API connections use Loop's model loop. Native connections dispatch through native adapters, and server subscription connections through their configured runtime. Native context belongs to its harness; Loop persists the display projection, dispatch identity, approvals and tool receipts. Codex, Claude Code, Pi and Muse Code support live input; OpenCode, Gemini CLI, Grok Build and ACP queue follow-ups. Each native conversation has an independent session and serialized turns.

The private native tool bridge gives ordinary harness runs the same owner-scoped agent directory, direct/team mail, handoff, memory and published-file tools; delegation remains a team-manager operation and snapshot reviews keep their restricted catalog. [Agent messaging](workspace.md#agent-messaging) stays within one owner and Loop API source. Direct threads have two fixed participants and conversation bindings. Pending mail is durable; the atomic queue claim serializes mail against conflicting agent work and rechecks authorization before dispatch. Team mail retains membership checks. Handoffs transfer a task and context summary without transferring a provider session or additional authority, and file access is checked on forwarding and reading.

An earlier release ran harnesses through HAPI; that code is gone. Migration 080 made its leftover records inert once: active HAPI runs were interrupted without replay and their pending approvals rejected, HAPI connections stay disconnected and no longer present as subscriptions, and HAPI conversations keep their memory inclusion as an explicit policy. Their history remains readable. No uncertain external effect is replayed automatically.

### Companion execution authority

The companion host calls a private execution boundary for operations that need live native state. The authority owns the scheduler, native sessions, tool bridge, sign-ins and upgrade reservations. It runs in a child process started by the companion host over inherited Node IPC, using the same profile and data directory. Both sides validate the same operation schemas and JSON envelopes: requests have unique IDs, an authority generation, readiness checks and a limit of the public HTTP body size (12 MiB) plus 64 KiB for envelope metadata; responses have matching identities and a 64 MiB limit to accommodate native frames and their derived catalogs. Disconnect rejects outstanding requests. The client never silently switches authority or resends a command. Unknown and completed command outcomes remain explicit through the HTTP boundary, including a completed command whose cached response expired. Runtime setup, sign-in and session settings retain the original command for retries. After checking current status, the user can explicitly start a new verification, sign-in or setting request.

The child holds an exclusive transaction on `execution/ownership.sqlite` for its entire lifetime. This separate rollback-mode SQLite file uses an [OS file lock](https://www.sqlite.org/lockingv3.html#locking); it never holds a transaction on the application database. The lock file is never unlinked and ownership has no expiry. A paused holder remains the owner. Before a replacement can recover runs, it acquires that lock, confirms the prior worker identity has exited, and stops or confirms the recorded native process groups. On Linux, namespace identity includes its init process's identity because namespace inode numbers can be reused. On macOS, a validated kernel boot-session UUID identifies the host lifetime; a copied workspace cannot supply that identity. New macOS process timestamps use UTC and a fixed locale, so environment changes cannot look like PID reuse. Legacy timestamps that no longer match remain uncertain and are retained. Startup refuses an unavailable current identity, and retained records without host identity require explicit recovery. Unreadable identities, another PID namespace lifetime, or unidentifiable surviving groups refuse takeover and retain the records for inspection. Retained records after an unclean host reboot, container restart or workspace move have an explicit [ownership recovery procedure](pairing.md#recovering-retained-execution-ownership); a free lock alone never authorizes discarding them. Forced stop validates every process registry before signalling, preserves unreadable evidence, and retires a confirmed stopped owner while holding its lock. Graceful shutdown and replacement also remove resolved execution child and stop records under that lock. Cleanup never installs an execution generation of its own; a failed final validation preserves the original worker identity for inspection. Claims, lifecycle commands and native controls check the worker generation.

The API rejects pending IPC requests on disconnect and restarts a crashed worker with bounded backoff (250 ms to 5 seconds), including a spawn error that emits no exit event. A replacement becomes publicly ready only after restoring scheduling and origin configuration; failed restoration stops that child and retries. Coalesced origin updates have bounded reserved IPC capacity, so saturated user requests cannot silently drop an address change. Native actions are never replayed. Recovery interrupts owned native turns and preserves uncertain decisions and commands. On shutdown, claims stop before native IO is terminated. Detached native groups are recorded under `execution/`; worker shutdown, replacement and `loop stop` verify and clean them. Loss of the parent IPC channel stops the worker and its children. The API continues serving local database reads while execution is restarting; SQLite writer contention and synchronous work in API handlers remain shared limits.

| Caller | Authority operations |
| --- | --- |
| Companion routes | Runtime discovery, registration and enablement; sign-in catalog, status, start, input and cancellation; upgrade status, start, recovery and dismissal; native decisions and session controls/settings |
| Core routes and subscription refresh | Native connection refresh, command catalogs, Pi trust, package filters/actions/inspection/rollback and prompt preview |
| Local harness setup and WorkspaceHost | Initial registration, execution startup, scheduling and shutdown |

Database and filesystem reads such as workspace registrations, project paths, directory browsing, native history and Pi configuration remain local. Pi mutations return small acknowledgments across the boundary; the API then reads the configuration from shared database/filesystem state, preserving the complete HTTP response even for large configurations. Routes send owned identities; the authority resolves agents, conversations and connections itself. Native tool tickets and their live generation checks stay beside the supervisor. Upgrade reservations use the same authority state as queue claims, including while discovery is awaiting a probe.

Settings and enablement retain command identities across client retries. Durable receipts record intent before execution; a completed receipt can supply the prior result, while an interrupted or uncertain command is never applied again. Response bodies are retained for at most 64 commands and 4 MiB per owner; compacting a response preserves its command identity and outcome, so an old retry requires inspecting current state instead of repeating the effect. The authority also retains identities for Pi mutations and sign-in input/cancel. Those HTTP routes allocate a fresh command for each call, so their receipts do not deduplicate separate HTTP requests. Their callers must inspect current state after a lost response before issuing another action; the transport does not replay them. Routine model and status refreshes rederive the existing registration without creating command receipts.

Explicit pre-dispatch refusals release the command for retry because no native effect was attempted. Failed prompt-free verification can also be retried once its adapter has shut down, before registration changes. Native decisions and upgrades retain their existing durable identities. Sign-in receipts store a process-local keyed digest and outcome without credentials or short-lived codes; only the originating live authority can reconcile the original attempt. A new command after an unknown result requires inspecting the native state first. Sign-in attempts carry their originating command ID so recovery cannot mistake an older completed login for a requested account change; a fresh authority reloads its provider catalog during inspection when needed.

## Workspace updates

The signed-in UI subscribes to authenticated WebSockets for each execution source. The server profile exposes `/api/events/ws`; the paired host also retains `/ws` and forwards source event connections through its existing discovery and device authorization boundary. Cards integration tokens cannot open these connections. Owner-scoped change-log cursors notify projections when committed data changes, including saves, dismissals, metadata, mail, Social and pull-request state. The API observes the shared SQLite database so updates from a separate worker are included.

Each process owns one [ordered change drain](../src/server/changes.ts) on its database connection. Local event inserts schedule a macrotask; one shared check of `PRAGMA data_version` and `total_changes()` every 250 ms wakes the same drain for foreign commits and local SQL-trigger producers (`LOOP_CHANGE_POLL_MS` configures that interval). At startup it reads the committed event tip; consumers obtain older state through their own initial snapshots or replay. Subsequent ascending reads alone advance the cursor, so rolled-back savepoints never publish and a local commit cannot skip an earlier foreign row. Failed reads retry after 100 ms independently of the foreign-poll interval; invalid timer values use the default interval. Bounded pages yield between deliveries. Publications contain row identities and types; payloads stay behind each consumer's byte limits. Owner subscriptions do not replay history on demand: sockets retain independent durable cursors and drain their own replay pages. Source-row triggers write identity-only invalidations in the same transaction as the existing Cards and Done compatibility revisions. Later also tracks target content, agent and project labels, run folder context, and story-feed access. Healthy Social refresh timestamps and cache validators do not publish changes; story content and feed-health changes do. Social digest settings and worker status changes also invalidate Social. Deletes write tombstones before cascades using a surviving collection subject and no run foreign key. Before an owner has any events, HTTP clocks read an implicit zero watermark from a persisted database identity without writing. The first event or socket initialization stores that same epoch in the owner’s row. A durable per-owner `change_watermark` retains its epoch and last event ID even when events are pruned; sockets reconcile holes without sending empty event frames. Socket authentication, session checks and overflow resets remain at the transport boundary. Existing owners connect without a writer lock; failed first-clock initialization closes the socket and releases its subscription and owner reservation.

Workspace writes use the synchronous boundary in [projected-database.ts](../src/server/projected-database.ts). Use `db.transaction(...).immediate()` for a group of changes; standalone prepared writes are wrapped automatically. The Feed projector drains deduplicated dirty conversation/result identities before that outer transaction commits, together with its `feed.card` events. Nested rollback and projector failure roll back source rows, projection rows and events together. Both API and worker import this database boundary. Direct SQL transaction-control statements and lazy write iterators bypass that contract and are rejected. Approval and stopped-watch timestamps remain read-time predicates rather than stored expiry flags.

The worker coalesces scheduling wakes from queue and run-state publications, with a two-second fallback. Releasing an execution slot wakes scheduling again because a terminal publication can precede slot release. An empty claim does not schedule itself again. Stale-run recovery stays in the scheduling tick; other maintenance schedules remain independent.

Active consumers share one [run subscription](../src/server/run-signal.ts) per run and process, released when its last consumer finishes. Committed run and provider-connection changes abort managed/native IO with a readable cause; steering, approval and delegation waits subscribe to changes. One two-second fallback per held run recovers missed notifications. Connection status and its owner-scoped event commit together, contain no credentials, and need no run identity. Run subjects retain their run foreign key and cascade behavior. Steering retains claim-before-delivery and never replays an uncertain handoff. Reverse MCP waiters register by durable call ID, then recheck the result; completion, cancellation, peer revocation and explicit deadlines settle every waiter. Approval expiry has its own deadline. Mail and artifact publications also wake the worker's three-second maintenance pass, which remains responsible for Later and scheduled sends.

Thread openings reuse the owner's cached transcript and linked-source metadata while reconciling with the server. Only an initial unanchored read sends `resume=1`; the conversation route chooses an older saved-position page in that response and reports `resumed`, while ordinary refreshes continue to return the latest page. Explicit message anchors and history cursors keep their existing behavior. Older linked servers without the `resumed` response marker retain their compatibility anchor read. Owner changes clear cached views, and source/conversation generations discard stale responses. A source's HTTP 429 `Retry-After` pauses its reads, including fallback polls; domain refusals without that header retain their actionable error and do not impose a cooldown. Scheduled-send and review-status reads also recover at the deadline with view-bound cancellation. Zero, past, or malformed retry deadlines have a one-second minimum. Approval polling reports cooldowns quietly and clears recovered read failures independently of action errors. Cached threads stay readable and retry at the deadline. Failed linked metadata refreshes retain a visible connection retry alongside the transcript, so updated agent settings can recover without reopening. Linked Docker responses preserve the header. Writes are never automatically retried by this mechanism.


The [workspace event contract](../src/shared/workspace-events.ts) validates emitted types and their strict, bounded payloads before insertion. Native display events share ingress's 256,000-byte budget, including 64,000 bytes per request; provider IDs and list lengths remain accepted within those totals. Subjects identify owned runs, conversations, messages, artifacts, approvals, decisions, Later items, scheduled sends, mail threads, connections, agents, folders, teams, Social sources or collections. `emit` checks ownership; deletion producers can retain immutable ownership evidence captured before removal. Events carry one or more projection scopes; tombstones require authoritative reconciliation of those scopes, because removing a bookmark or nested record does not necessarily delete its underlying object. Typed message upserts, append chunks and removals name the displayed message and its content revision; native decision lifecycle events name the server decision and retain the adapter request identity as display data. Other events invalidate run, connection, conversation or collection state. Browsers request `v=3`, including through linked Docker sources. V3 frames carry parsed events with explicit scopes; invalid historical rows and unknown future event types invalidate all collections. Message upserts and decision payloads over 60 KiB become scoped invalidations before the event transaction commits; their complete content stays in the authoritative source row. Other oversized wire events become scoped invalidations without changing durable payloads. Message subjects remain available so clients can refetch retained older pages. Replay pages retain the 64 KiB per-event and 512 KiB batch budgets. Cached clients without `v=3` retain the existing v2 frames and oversized-batch reset behavior.

V3 resets advertise each source's own invalidation coverage, deadlines and transcript/Feed/results delivery modes. Current sources report complete invalidation coverage and delta delivery for transcripts and Results, with Feed snapshots. Deadline reset metadata requires the `clock=1` query extension, which the browser requests and the linked Docker proxy forwards; unextended v3 clients retain their strict reset envelope and see deadline capability disabled. Notifications coalesce by source and scope, so a Feed-only invalidation does not reload a thread or another collection. Complete producers name the affected collections explicitly; message chunks update the transcript reducer without a broad refresh. A `projection=1` extension also requests capabilities on the first replay frame, so a reconnect to an older deployment restores fallback polls even without a reset.

Conversation pages subscribe before reading and buffer events per owner, source, epoch and request generation. The shared transcript reducer installs per-entity revisions, replays events beyond that page’s watermark, deduplicates chunks by event ID and chunk index, and checks the base revision and UTF-8 offset. A chunk gap requests the affected message’s page without expanding the displayed page ranges. Recovery tracks each missing row’s latest event cursor. Returned rows and the explicitly requested anchor are acknowledged only through the snapshot watermark, including an anchor that became hidden; typed removals clear pending recovery. Newer invalidations received during the read remain pending. Buffered gaps for messages outside a fetched page do not prevent that page from hydrating; its own gaps still require a retry. Upserts for unloaded older history remain hidden until those pages are requested. An observed row beyond an anchored page’s end requests the latest page once, after which live appends update it in place; Jump to latest also fetches that page. Invalid snapshot rows stop with a retry action; supported imported fractional timestamps remain valid. Rejected handoffs retry at most twice with backoff before showing an error. An HTTP clock from a replacement database resets the source while sockets are down, without claiming a build identity or delta capability; earlier HTTP responses and obsolete socket callbacks cannot restore the old epoch. A reset or bounded-buffer overflow requests a fresh snapshot; when a reset replaces loaded pages, pagination restarts at the new snapshot’s cursor. Each page declares its ordering range so absent rows can be removed without acknowledging older retained pages, and older responses cannot resurrect a deletion. Managed output commits display rows and their events together at most every 250 ms and flushes at terminal boundaries; native output retains its one-second batch. Large appends become ordered bounded durable events, each with its own reconnect cursor.

Owners whose Social reads encounter an in-progress refresh receive a completion invalidation even when stories and health are unchanged; routine worker refreshes remain quiet. Feed notifications continue to reconcile complete HTTP pages with their existing timer and source/page recovery. Results and Cards drain continuation pages in a bounded pass; a non-progressing cursor fails and an excessive drain restarts from a snapshot.

Complete sources use scoped signals for transcript, Results, activity, usage, decisions, approvals, saved items, Later, Social, pull watches, workflow steps and memory preferences. Their compensating collection polls stop only while that source advertises complete coverage, deadlines and the required delta capability. Older sources retain those polls. Unavailable sockets retain HTTP event polling; visibility, online, pageshow, explicit refresh and the single deadline wake still reconcile authoritative state. Read-only snapshots recover from header-limited responses with a cancellable Retry-After wait and retry a transient server failure at most twice, including empty or HTML proxy errors. Transcript and history reads and run file lists use these bounded reads even after a run finishes. Exhausted workspace metadata/run reads retain independent visible errors and activate recovery until their own read succeeds. External source discovery, harness availability, deployment health, search-index/import jobs and authentication progress retain their separate probes. Neither transport replays commands or other writes.

Pending approvals and stopped pull-request watches have persisted expiry obligations. Each process seeds its owner timers from durable rows, including overdue ones; SQLite serializes expiry processing across API and worker processes. Ordinary notifications first check a read-only snapshot; they acquire a write transaction only when expiry or deadline publication needs durable changes, then recheck under that lock. Expiry marks the obligation processed, invalidates the affected collections, and publishes the next deadline or explicit null in the same transaction. Approval refusal and watch visibility retain their existing read-time timestamp predicates; expiry does not authorize an external effect or invent a run-state transition. Native decisions have generation-bound expiry and no timestamp TTL. Later and scheduled sends retain worker maintenance, whose durable updates enter the same log.

Every v3 reset negotiated with `clock=1` carries `serverNow` and nullable `nextDeadline`. Successful owner-session JSON snapshots preserve their existing bodies and carry `X-Loop-Server-Now`, `X-Loop-Next-Deadline` (`null` when absent), `X-Loop-Change-Epoch` and `X-Loop-Change-Cursor`; linked Docker forwards these headers. Scoped Cards-token responses omit this owner-wide metadata, including when an owner cookie accompanies the token. The client owns one deadline timer per owner/source subscription, replaces it on newer clock metadata, and invalidates Feed, Results, approvals and pulls when it fires. It uses the received server-relative delay and a monotonic local timer, rejects stale responses, and checks owner/source/epoch generations. Only the resulting authoritative reads determine expiry. Conversation, Feed and Results responses read their body, entity revisions and owner watermark in one SQLite read transaction; this pins the snapshot to the same committed state as its cursor. Other JSON clock headers remain notification metadata and do not claim that projection handoff.

## Activities

Plans, tool lifecycle, diffs, command output, settings and command catalogs share [agent-activities.ts](../src/agent-activities.ts). [server/activities.ts](../src/server/activities.ts) validates and persists trusted owner/conversation/run scope and serves paginated projections. [activity-bridge.ts](../src/activity-bridge.ts) supplies the shared mapping for native activity projections and historical records.

The client uses [activityView.ts](../src/client/activityView.ts) to accumulate full snapshot pages and apply incremental updates. Read-only projections of older trace rows preserve old history without executing it again. Conversation transcripts show human messages and public agent output, including progress updates. Tool calls, raw native events and activity records stay out of the transcript, except native failure and uncertain-delivery notices. Tool calls, command output and plan progress are available from the conversation's **Tool activity** option, including managed native tool activity that arrived outside a Loop turn; saved tool traces are in the agent profile’s Traces tab. Session settings stay in **Session settings**. A link to a hidden row opens the conversation where that row was. Activities are display data: Loop never applies a reported diff or uses these records as native model context.

[Conversation transcripts](../src/server/conversation-messages.ts) page through an indexed display projection whose ordering keys are maintained in the same transaction as messages. Public assistant updates live in the message store with idempotent per-run producer keys; transcripts, reply quotes and reading positions do not read execution traces. Migration 073 copies older public updates into messages while preserving their IDs and ordering cursors. Message sequences remain stable through deletion and database compaction. A run's updates group under its prompt, or under the run's first stored message when imported or replayed history has none. The page is selected before loading its content and current run/delivery state. Opening a thread loads confirmed session controls. File summaries load separately as their messages come into view; file contents download when opened. Opening **Tool activity** loads its recent activity snapshot; **Load earlier activity** requests older records, including legacy traces, and is offered only while older records that view can show remain. File-change records are loaded for runs in the displayed transcript so older result chips retain their file reviews. Activity history and live-update cursors are independent.

Records are bounded, versioned and keyed by producer identity. Sequence/revision checks prevent stale updates overwriting newer state; generation checks reject stale producers. Re-delivery is idempotent. Replay does not advance live tool lifecycle. Capabilities distinguish supported, unsupported and undiscovered behavior instead of fabricating results.

## Memory, tools and files

Workspace MCP connections belong to the owner and are shared by that owner's agents. Broker dispatch checks discovery, schema, ownership, connection and approval state. Companion command MCPs use local subprocesses; server command MCPs use runtime infrastructure. Rich MCP Apps run in isolated iframes. See [workspace](workspace.md).

Search supports keyword and optional semantic indexing. Managed native recall uses [memory.ts](../src/server/memory.ts) and the optional MemSearch service; laptop startup can run without it. Artifact content and versions remain live during streaming, but artifact search indexes retain their last indexed snapshot until the partial flag clears; failed or paused partial drafts retain that snapshot until finalized. Results revisions likewise skip repeated partial updates. Scope, inclusion, revision and tombstone checks apply again before returning indexed candidates. Recall is untrusted historical evidence, never current authorization. Versioned notes and an outbox preserve update ordering.

Message attachments reach the model as file references read through `loop_read_file`. Before upload, the browser scales HEIC photos and images over 1.5 MB to at most 2048 pixels on the longest side and re-encodes them as JPEG ([imageUpload.ts](../src/client/imageUpload.ts)); GIFs, SVGs and images it cannot decode are sent unchanged. An upload error that is not Loop's JSON (a tunnel or proxy page) is shown with its HTTP status. API-key connections also receive the current turn's images and PDFs inline. Native turns receive upload references and use `loop_read_file` through the private tool bridge.

File publication validates the selected file/path, size and digest, then stores private content under the workspace data directory. Downloads require owner access. A worker path alone is not a published file. Credentials remain in encrypted server storage or their native provider homes; neither belongs in public projections.

## Dependencies and boundaries

[deployment/versions.json](../deployment/versions.json) owns container provider and MemSearch pins. [host-control.ts](../src/host-control.ts) owns installed harness version checks. [package.json](../package.json) pins the ACP SDK. Validate each seam when updating it.

Dependencies retain their upstream licenses.

The application host is a single point of failure. Native tools are not a multi-tenant sandbox. Fixture tests establish protocol behavior, not provider availability, billing entitlement, device acceptance or deployment capacity. See [development](development.md) for verification boundaries.
